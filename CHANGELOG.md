# Changelog

Notable changes, newest first. This project is pre-1.0 and follows no compatibility promise until it has one, per `spec/18-package-layout.md`. The storage format version is stated in every release, because a file outlives the build that wrote it.

The version number says how far through the plan we are. **The minor version is the number of milestones finished**, so 0.0.y is work inside M0, 0.1.0 is the release where M0's exit criterion passed, 0.1.y is work inside M1, and so on. Patch releases happen whenever enough has landed to be worth a tag, which in practice is every few pull requests. The one exception is at the end: when M10 closes the version is 1.0.0 rather than 0.11.0, because that milestone is named 1.0 and pretending otherwise would be silly. The milestones are the issues at https://github.com/tamnd/rudb/issues.

## 0.2.31

The release where a column name that DuckDB writes in quotes comes back in quotes here too. Three changes, and the middle one is the reason to believe the other two, because it found that the conformance corpus had spent some number of runs checking a published build rather than the tree it was pointed at. The storage format version is unchanged, because nothing here writes a file.

- An identifier inside a generated name is quoted wherever DuckDB quotes one. `SELECT min(name) FROM t` comes back from the pinned `v2.0.0-dev84237 (cc7e7bac7f)` in a column called `min("name")` and came back here as `min(name)`, and the same went for `substring`, `position`, `nullif`, `trim` and every other word upstream treats that way, so a tool that reads column names off a result saw a different name than it would have. There are two rules and they were both read off the binary rather than guessed. One is that the folded word is in the keyword table with a class mask that is not zero, which is why `name` and `action` are quoted as unreserved words, `left` and `right` as function or type names, `nullif`, `overlay`, `position`, `row`, `substring` and `trim` as column names, and why `alias` is not quoted at all, since it is spelled by a rule and is in no class, and neither are `banana`, `substr`, `strpos`, `lower`, `length`, `abs`, `chr` or `concat`, which are not keywords. The other is that the text is not one word the tokenizer would read back, so `my col`, `9x` and `é` keep their quotes and an embedded quote is doubled. What upstream does not quote on is case, so `min(UserID)` stays exactly like that even though reading it again would fold it, and that is the whole reason the ninety nine column ClickBench names agree between the two engines, so this does not quote on case either. The rule is the parser's own keyword table through `classes(lookup(text))` and not a list in the deparser, so a keyword somebody adds later is covered the day it is added.
- The conformance corpus says which rudb it conformed, and refuses to run if the answer is the wrong one. `cargo xtask conform` builds the harness in tamnd/rudb-compat against this tree through a `[patch]`, and the harness lock file pins a version, so once this tree's version moved past the pinned one cargo quietly dropped the patch, printed `warning: patch for rudb ... was not used in the crate graph` in the middle of a few hundred lines of build output, and ran the whole corpus against rudb 0.2.29 downloaded from git. Every run was green and none of them were measuring anything. It was proven with `cargo tree --invert rudb --depth 0` under the same config, which printed the git checkout and not the path. The step now reads that line before it runs anything, repoints the harness with `cargo update -p rudb` when the line is not this tree, reads it again, and stops with an error naming what it resolved to rather than running a corpus whose result would mean nothing. The harness lock file is the one thing conform writes, which the module documentation now says, because it used to say nothing is written. Verified by putting the compat lock back to 0.2.28, watching conform repoint it and run against 0.2.30 from the tree, running it again to see it do nothing, and watching the count of that warning go from one to zero.
- `chr`, `left`, `right`, `concat` and `replace` have signature rows, so they resolve. All five were kernels with nothing to bind them and answered `Not implemented Error`. Every rule in them was measured one statement at a time on the pinned binary rather than taken from the documentation. `left` and `right` count characters and not bytes, a negative count means all but that many from the other end so `left('abc', -1)` is `ab` and `right('abc', -1)` is `bc`, and a count past either end clamps instead of raising. `replace` with an empty needle changes nothing and returns the text, and any null argument makes the whole thing null. `concat` skips its nulls instead of propagating them, so `concat('a', 1, NULL)` is `a1` and `concat(NULL)` is the empty string, which is the one function here where a null does not win. `chr` is a code point and not a byte, so `chr(233)` is one `é` and `chr(0)` is a string of length one, and the three ways to be outside the range all raise in upstream's words, `Invalid UTF8 Codepoint` followed by the number, including the surrogate half at 55296. Argument types are checked the way upstream checks them, so `chr(65::BIGINT)`, `chr(65.9)`, `chr(TRUE)` and `left('abc', 2::DOUBLE)` are binder errors here as well. All twenty six answers and seven error messages are the same text on both engines, with two known gaps left over: `chr('a')` raises a binder error where upstream raises a conversion error, which is the untyped string literal this parser does not have yet, and a list handed to `concat` or `||` comes back as the text the list prints as where upstream refuses the call, filed as #358.

## 0.2.30

The release where a string written with a letter in front of it stops answering with the query. Four changes, the first two are the two halves of one wrong answer, and the third is the first time this repository has written down a place where DuckDB is wrong and we are not. The storage format version is unchanged, because nothing here writes a file.

- A prefixed string literal is decoded instead of being handed back as its own source text. `SELECT E'a'` answered with the four characters `E'a'`, `SELECT B'101'` with `B'101'`, and a filter written against `E'\n'` found nothing and reported, accurately and uselessly, that it had found nothing. The cause was one arm: `string_value` stripped the quotes off a token and fell through to pushing the text when the token did not start with a quote, which is what every prefixed spelling does. That arm is gone and there is no replacement for it, because a default that silently answers with the query is a default that will do this again with the next spelling somebody adds, so a spelling the transformer does not know raises. `E'...'` is a C style escaped string and every rule in it was read off the pinned `v2.0.0-dev84237 (cc7e7bac7f)` one escape at a time through `hex()`, so that nothing could be hidden by the rendering. The named escapes are `\n`, `\t`, `\r`, `\b` and `\f`, and `\v` is not one of them however much it looks like one. `\x` takes one or two hex digits and `\0` through `\7` take one to three octal digits, and both write a byte rather than a character, so `\xc3\xa9` is one `é` and `\377` is not a string at all. `\uHHHH` wants all four digits and writes the character they name, and a short one, a non hex one, a surrogate half and a NUL all fall back to the rule that covers everything else, which is that the backslash is dropped and the character is kept. So `\q` is `q` and `😀` is the ten characters it was written as. The two ways the result is not a string raise in upstream's own words, `Null character not permitted in escape string literal` and `Invalid UTF-8 in escape string literal at byte offset 1: byte mismatch`, where the offset is where the bytes stop being a string and not where the escape was written. `N'abc'` is a cast of the string to VARCHAR and not a plain string, which the column name proves, since the binary answers it in a column called `CAST('abc' AS VARCHAR)`, so it is built as that cast. `B'101'` is the one the issue asked to measure rather than assume, and it is not a bit string: upstream answers the four characters `b101` as a VARCHAR, `B'abc'` is `babc` and `B''` is the single letter `b`.
- A hex string is read as the blob it is. `x'4142'` is a BLOB and not a VARCHAR, so the half above left it raising rather than answering it as a string, which would have been a second wrong answer of the same kind as the one it fixed. What goes in the AST is the text a blob prints as and not the text it was written as, because the binary names the column after the value: `x'4142'` is `'AB'::BLOB` and `x'ff41'` is `'\xFFA'::BLOB`. That printed form is also the form the string to blob cast reads bytes back from, so one text serves the name and the value and the two cannot disagree, and it is `Value` that prints it, so this cannot drift from the way a blob prints anywhere else. The errors fall out of the same arrangement. Upstream writes `\xHH` for every pair without looking at the digits and lets the cast refuse the ones that are not hex, which is why `x'4'` is `Parser Error: Hex string literal must have an even number of hex digits` and `x'41zz'` is a conversion error one step later naming `\xzz`, and doing the same thing here gives both messages in the same words for nothing. The pairs are bytes and not characters, which is how upstream counts them, so `x'éé'` is four bytes and two pairs and says so in its own error. Every statement was run through both shells on server2 and the answers, the column names and both errors are the same text on both engines. The four spellings went into `corpus/dialect.sql` in the harness at tamnd/rudb-compat#34, which is fifteen of fifteen through the shells now.
- The specification has somewhere to write down that DuckDB is wrong. The ClickBench sweep over the full ninety nine million row file has been reporting that query 4 differs, and the difference is not ours: `SELECT AVG(UserID) FROM hits` is wrong on the pinned binary and right here. Document 02.4 pointed at 14.4 for the list of permitted divergences, 14.4 is about function level differential testing and there was no list, so 14.10 is the list and the pointer aims at it. An entry has to carry a reproduction with both answers and an argument for which is right that does not appeal to our own implementation, a reason for not matching, since matching is the default and somebody migrating depends on the behaviour they have, somewhere upstream it is tracked, because an entry with no upstream report is one nobody has finished, and a note that it is temporary, since the ledger getting shorter is the healthy direction. The first entry is the ungrouped sum of a BIGINT column off a parquet scan dropping carries out of the high word of its 128 bit accumulator, short by exactly `282 * 2^64` over that file, which is not what a wrong value looks like. The binary disagrees with itself four ways, since `SUM(UserID::HUGEINT)`, `SUM(UserID::DECIMAL(38,0))`, the same column summed out of a table and the sum of its own per counter group sums all give the answer we give. It reduces to two statements over a 1.3 MB one column file, and narrowing says it is a function of how far the accumulator has gone rather than a bad row, is identical at one and sixteen threads so it is not the parallel combine, and follows the encoding rather than the order, since every file that loses a carry is dictionary encoded.
- The gate stops measuring against whatever pull request was merged an hour ago. `scripts/gate` worked out its base as the merge base with the trunk and fell back to `HEAD~1` when that came out equal to HEAD, and the base equals HEAD whenever nothing is committed on top of the trunk, which is the state every branch starts in and the state the gate is run in most often, because the gate is what you run before you commit. So editing two markdown files produced a changed list of seven paths, five of them from somebody else's merge, and the focus correctly followed those into six crates and compiled and tested all of them to check that a specification paragraph was still a specification paragraph. The two cases are now split: with a dirty tree the uncommitted work is the whole of the change and HEAD is what to measure against, and with a clean tree there is no other reading than what the last commit did. The other half is a line per part saying how long it took, because there was no way to answer why the gate is slow except by guessing. On server3 with a warm target the parts are clippy at 77.3s, test at 82.3s, doc at 76.3s and corpus at 84.4s, and the repeat with nothing changed is the interesting column: clippy goes to 3.2s, so its time is compilation and cargo caches it, and test does not move at all, so its time is the tests running, which is `rudb` at 25.0s and `rudb-cli` at 15.1s against three to four seconds each for the rest.

## 0.2.29

The release where a group by on a string that came through a join stops answering one group per row. Three changes, and the first one is a wrong answer. The storage format version is unchanged, because nothing here writes a file.

- Grouping a string that arrived as one value for the whole chunk finds its group again. `SELECT s, count(*) FROM a, b WHERE a.k = b.k GROUP BY s` over nine rows and three distinct strings answered with nine groups, each with a count of one. A cross product hands the left row down as constant vectors, one value standing for the whole chunk, which is what makes pairing one left row with a thousand right ones cost one value per left column rather than a thousand. `Vector::text_at` has nothing to hand back for that form and says so with `None`, and `Table::holds` was reading that `None` as a difference, so the probe hashed the row into the right bucket, found the group already sitting there, compared it, decided it was not the same string and opened another group, every row, forever. The hash was never wrong and neither was the bucket. `fold` in the same file already falls through to `value_at` for the forms that have no run of bytes to walk, and so does `set` in `group.rs`, and this was the one caller that did not. Found by running TPC-H at SF 0.01 against the pinned `v2.0.0-dev84237 (cc7e7bac7f)` on server2, where q05 came back with 103 rows against 25 nations and numbers a twelfth of the right ones, q07 with 46 against 4, and q10 with duplicate customer keys. All three are byte for byte identical with the reference now. Nothing on ClickBench ever showed it, because ClickBench has no joins, and a `JOIN ... ON` never showed it either, because that path materializes its output and hands down flat vectors.
- The regular expression engine gets a backtracker and a prefilter. Pike's machine runs every possibility at once, which is what makes it linear and also what makes it slow on the patterns people write, because `^https?://(?:www\.)?([^/]+)/.*$` over a URL has exactly one way on at nearly every position and the machine is paying for a thread list to hold one thread. `bitstate.rs` is RE2's `BitState`: it walks the one way on, keeps the capture slots in one array with an undo record beside every branch that writes to it, and reuses its three buffers out of a thread local, so a column is not a hundred million allocations of the same three things. What keeps it linear is the memo, one bit per instruction per position, because whether the rest of the program can match from a position does not depend on where the groups have been on the way there, so `(a+)+b` against two thousand `a`s is still answered at once. A program times a text over a quarter of a megabyte of bits goes to Pike's machine instead, which needs no memo because it never visits a pair twice. The prefilter is the other half: `compile.rs` works out the set of bytes a match may begin with and an unanchored search skips to one of them rather than running the whole program from every byte. On server2 over the one million row ClickBench partition, against the pinned binary's 1.02s, ClickBench query 29 as written goes from 9.28s to 2.26s, a global replace from 17.04s to 1.89s, and `count(*) where regexp_matches(Referer, 'yandex')` from 6.79s to 0.53s against the binary's 0.16s. Every answer is byte identical in all four.
- A type in front of a string is read as a cast of that string. `DATE '1995-09-01'` said `is not supported yet, the grammar rule is TypeLiteral`. It is the cast written the other way round and upstream it is the same node, which the column name proves: the pinned binary answers `date '1995-09-01'`, `CAST('1995-09-01' AS DATE)` and `'1995-09-01'::DATE` all three in a column called `CAST('1995-09-01' AS DATE)`. So the transformer builds the cast node and nothing else, which means every type the cast already takes is a typed literal from today, parameters and all, and the two spellings cannot drift apart because there is only one of them below the parser. TPC-H q14 is the query that wanted it, and at SF 0.01 it now runs and matches the reference byte for byte, which takes TPC-H from twelve of twenty two to thirteen.

## 0.2.28

The release where a query that is told to stop stops. Three changes and the one worth reading is the third. The storage format version is unchanged, because nothing here writes a file.

- The nested loop join checks the cancellation token inside its own loop. Every operator is wrapped in a check that runs between the chunks it produces, and the argument for putting it there rather than in each operator is that one line in one place is not a decision somebody gets wrong when they add the twentieth operator. That argument is still right and it had a hole in it, which is an operator that produces no chunks until it has finished, because for that one a check between chunks is a check at the end. The join is that operator: it reads both sides, runs the whole join, and hands back its first chunk when there is nothing left to do. The compatibility harness measured a hundred thousand left rows against thirty thousand right ones running for sixty two seconds after being told at one second to stop, and then reporting, accurately and uselessly, that it had gone past a one second limit. So the join holds the token and checks it once per left row, in the same place and at the same granularity as the reservation it already grows there, which means a query can overshoot its clock by one pass over the right side and no more. Nothing else needs it, because every other operator that buffers reads its input through a child operator and the child is wrapped, so it is checked all the way through the reading. Measured on server2 against four upstream corpus files the harness had been killing, with a ten second clock on a statement, `hash_join_dict_surviving.test` goes from 329 seconds to 32, `test_prefix_range_filter_pushdown.test` from 124 to 20, and the two that barely move are files where several statements each run out their own ten seconds, which is the limit working rather than the limit being missed.
- The committed corpus is a gate in this repository too. `tamnd/rudb-compat` owns two corpora and they are two different things: the upstream sqllogictest files are a measurement that moves when somebody else adds a file, and the files under `corpus/slt` are ours, they say what rudb can do today, and they are never allowed to go down. The second one ran in that repository only, against whatever rudb the pin there points at, so a regression was found days after the commit that caused it and by somebody moving a pin. Now `cargo xtask conform` runs it against the tree in front of it, the shell built out of this working tree and the library patched to the same tree rather than to the pin, with nothing written to either manifest to do it, because a gate that edits the tree it is checking leaves a dirty checkout behind on the run that fails. `cargo xtask ci` runs it last and says so when there is no harness checked out beside this repository, and the workflow has a job for it in the required list.
- The release job stops retrying the crates.io daily cap. A publish that is refused because the account has hit its limit for the day is not going to succeed in forty minutes, so the retry loop sat there burning a runner and then failed anyway.

## 0.2.27

The release where the second half of the hash aggregate stops working a row at a time. One change, and it is the half #308 said it was deliberately leaving behind. The storage format version is unchanged, because nothing here writes a file.

- A chunk folds into many accumulators in one pass. #308 took the row out of grouping and left it in the aggregate, so what the operator did after it was hash a chunk a column at a time, probe with the hash in hand, and then, for every row and for every call on that row, build a `Value` for the argument and go through an update that matches on which aggregate it is and on what type the value holds before it adds anything to anything. Which aggregate this is was settled when the operator was built and what layout the argument arrives in was settled when the chunk was produced, so two of those three matches are answered before the loop starts, and the `Value` is pure loss: a copy of a word into a wider enum for a fixed width column and a malloc and a free for a string. `update_scattered` is the grouped form of the `update_run` that has folded a whole vector into one accumulator since 2b. It takes a vector, one slot per row saying which accumulator that row belongs to, and a stride and an offset saying where the calls of one group live, which is the layout the hash aggregate already keeps, so nothing is copied to call it and the slots are the probe results the operator has in hand. It cannot reduce the way the ungrouped form does, because two adjacent rows are usually two different groups and there is nothing to add up before the scatter, but everything else goes. A row that went to a spill file and a row a call's `FILTER` threw away point at the same sentinel, so the filter is folded into a copy of the slots rather than read inside the loop that walks them and there is no second mask to hand over. The loops cover the shapes a scan produces, which is flat and dictionary over the fixed width layouts, and they are chosen by the same rules the ungrouped form already uses, with the arms in the same order so the two cannot drift into disagreeing about what a decimal at the wrong scale means. Both counts are answered by the validity mask alone. A shape with no loop falls through to the row at a time update and records itself in the fallback counters the way every other kernel does, so a column that misses shows up as a number rather than as an opinion. Measured on server2 over one million rows of the real ClickBench file, one query per process, three runs, against 0.2.26 and the pinned binary: `GROUP BY RegionID` with `count`, `sum` and `avg` goes from 280ms to 130ms where the binary is 110ms, `GROUP BY SearchPhrase` with four aggregates from 520ms to 340ms, and `GROUP BY UserID` with two from 420ms to 330ms. The low cardinality case is where this shows most, which is the opposite of #308: there the cost was per group and here it is per row, so a thousand groups over a million rows pays it a million times. On the full forty three, q34 goes from 2.70s to 2.18s, q25 from 3.16s to 2.84s, q29 from 0.54s to 0.40s, q24 from 0.41s to 0.28s, q11 from 0.36s to 0.26s and four more move, with every answer byte identical. The ungrouped row does not move, which is right, since that path is untouched. What is left in the operator is `DISTINCT` inside an aggregate, which is still a hash set per group per call and is a grouping of its own keyed on the type grouping used before #237, and giving it the table #237 built is a change of its own.

## 0.2.26

The release where a function that was never implemented stops answering anyway. Two changes and they are the same corner of the transformer seen twice, first as the bug and then as the work it was hiding. The storage format version is unchanged, because nothing here writes a file.

- A grammar rule that wrote a keyword is not stepped through on the way to its one argument. `SELECT trim('  a  ')` answered the untrimmed string and `SELECT length(trim('  a  '))` answered 5 against the pinned binary's 1, with nothing said about it. The expression dispatch stepped through any rule with exactly one child, on the theory that such a rule is a precedence level that said nothing about the value, and that is true of the ten chain rules it was written for and false of any rule that spells a keyword, because a keyword is not a child of the node that spells it. `TrimExpression <- 'TRIM' Parens(TrimArguments)` has one child, so the loop walked past the `TRIM` and transformed the argument. Three other rules had the same shape and all three were being walked through too: `row(1)` answered 1 where upstream answers the struct `(1,)`, `try('a'::INT)` raised the conversion error upstream answers NULL for, and `unpack([1])` tried to build a list. `trim` is the one worth a p0 of the four, because it is the only one that answers a row rather than raising something, and because a query that trims a column and groups by it got the wrong groups. Two arguments hid it, since `trim('xxaxx', 'x')` has two children and has always said it is not supported. What replaces the count is a comparison of the spans: a precedence rule with one child covers exactly the text its child covers and a rule that wrote a keyword or a bracket covers more, so the step is taken only when the two are equal. That is a rule rather than a list of the names that happened to be wrong, which matters because the vendored grammar has eleven hundred rules and the ones with a keyword above a single child are not enumerable by reading the ones somebody noticed. `ParensExpression` is the one rule that covers more text and still says nothing, since its brackets are grouping, and it has an arm of its own.
- `SUBSTRING`, `POSITION`, `TRIM` and `OVERLAY` are calls. Each of the four is a grammar rule of its own, the transformer had an arm for none of them, and the plain spellings behind them were missing from the signature table as well, so neither `substring('abcdef', 2, 3)` nor `substr('abcdef', 2, 3)` could be written. Each rule lowers to the call DuckDB's own parser writes, read off the pinned binary as the column name of each statement rather than worked out from the grammar, and three of the lowerings move something: `POSITION` swaps its arguments so the haystack comes first, `TRIM` turns a direction into a different function so `LEADING` is `ltrim` and `TRAILING` is `rtrim`, and `substring('abcdef' FOR 3)` is three arguments with a 1 filled in rather than the two argument call it looks like. The index rules were measured one statement at a time, the way the subscripts were, because not one of them follows from the others. The window starts where the index says and is clipped afterwards, so `substring('abcdef', 0, 3)` is `ab` and not `abc`. A negative start counts back from the end, and a start still off the string after counting back leaves nothing when there is a length and the whole string when there is not. A negative length runs the window backwards from the start rather than being empty, so `substring('abcdef', 4, -2)` is `bc`. An index has to be a whole number already and is not rounded, which is upstream's rule and the same one the subscripts follow. `trim` with no characters named strips the space alone and leaves a tab where it is, which was measured rather than assumed, and with characters named it strips any of them as a set. `overlay` takes the replacement's own length when it is told a negative one, which is the one place it parts company with `substring`. Everything counts characters and not bytes, so `substring('héllo', 2, 2)` is `él`. Ninety seven statements through both shells agree on every value and every error message, and the only disagreements left are the column names upstream quotes because the name is a keyword, which is #251.

## 0.2.25

The release where three things that could not be written at all can be written, and the hash aggregate stops being the largest cost left in ClickBench. Brackets, `typeof` and the three spellings of a null check share a common thread, which is that every one of them was a grammar rule the transformer walked past rather than a function nobody had implemented. The fourth change is unrelated to those and is the p0. The storage format version is unchanged, because nothing here writes a file.

- Grouping hashes a chunk a column at a time and keeps its keys in columns, which is the shape a chunk wants them back in. The finding, when the operator was taken apart, was that the hashing was never the problem. A group cost the allocator four times: a `Vec<Value>` built per row to ask the question, a clone of that vector into the map on a miss, a second `Vec<Value>` per group to hand the answer back, and a clone of every key value while transposing those rows back into columns to make a chunk. Two of those are per row and two are per group, and the ClickBench queries that group on something close to one group per row were spending most of the operator there rather than in the table. What replaces it is a purpose built open addressed table that never materializes a row: one pass per key column folds the whole chunk into one hash per row with the type matched on once instead of once per value, the probe walks the buckets with the hash already in hand, and a stored key is compared against the vector in place, through `text_at` for a string so that a dictionary column is not copied per row. The keys already live one column per vector, so the answer is built straight out of them and both transposes are gone. The one invariant worth stating out loud is that the same column arrives in more than one form, because a `VARCHAR` read out of a parquet file is a dictionary in one chunk and flat in the next, and if the typed path and the general path disagreed by so much as a discriminant then a group by would answer with the same string twice, so the general path does not mix a discriminant either, since a typed arm over a run of `i32` has none to mix. The rule that folds one word and the rule that spreads the result are free functions used by both the digest and the table, because two hash functions that are meant to be the same one are two hash functions that will eventually differ. Measured on server2 over one million rows of the real ClickBench file, one query per process, against the pinned binary: `GROUP BY WatchID` at a million groups goes from 1201ms to 369ms where the binary is 192ms, and `GROUP BY WatchID, ClientIP` from 1515ms to 693ms where the binary is 166ms. Low and mid cardinality grouping was already at parity and stays there, which is what said the remaining cost was per group rather than per row. On the full forty three, q34 goes from 3249ms to 1959ms, q41 from 2253ms to 1722ms, q20 from 1032ms to 692ms, q25 from 2522ms to 2182ms, q35 from 1116ms to 886ms and eight more move, with every answer byte identical to 0.2.24. What is left in the operator is the per row aggregate update, a dynamic dispatch per row per call with a key built per row per call for the argument, and a `DISTINCT` argument that is still a hash set per group per call, both deliberately untouched here. Four queries looked worse on the first sweep and none survived being run three times, and the one that took longest to dismiss, q30, turned out to be spending ten of its eleven seconds inside `REGEXP_REPLACE` over 921,225 rows where the binary does the whole query in one, which is filed as #310 against the regex engine rather than against the aggregate.
- A bracket indexes and slices, which is two function calls and is how DuckDB's own transformer reads it. One index becomes `array_extract`, a range becomes `array_slice`, and the bounds the query left out are filled in before the binder sees them: a missing begin is 1, a missing end is -1, and the lone hyphen in `x[1:-]` is a range with no end rather than a subtraction of nothing. `x[]` is the one subscript the parser takes and the transformer refuses, in upstream's words. Every rule under this was measured against the pinned binary case by case, because almost none of it is what a reader would guess. Indices count from one. An index off the end of a list is null and an index off the end of a string is the empty string. A range clamps rather than raising and the clamping is not symmetric, so a begin below one moves up to one and an end past the length moves down to it, while an end that is still negative after counting back from the end stays where it is, which is why `'abcdef'[-99:-98]` is empty. A step is a list only feature and a step on a string is a not implemented error with a suggested rewrite in it. A slice of a list answers a list, and there is no LIST vector yet, so those stop with the same message `SELECT [1, 2, 3]` already stops with, which is #302. What this closed in passing is a statement in `corpus/dialect.sql` that had nothing to do with subscripts: `SELECT x[1:2] FROM t` has no table `t`, and rudb refused the slice before it ever went looking for the table, so the two engines disagreed about a catalog error.
- `typeof` is answered in the binder rather than by a kernel. The type of an expression is settled the moment the expression is bound and nothing about it changes per row, so the fold happens in `bind_call` and the executor never sees the call. The argument still goes through the aggregate rules before it is dropped, which is not a detail: upstream refuses `SELECT typeof(x), count(*) FROM t` for the same reason it refuses a bare `x` there, even though neither of them reads a value, and folding without that check would have accepted it. The names are the ones `LogicalType` already prints and they turned out to be right for every case measured, including the one the issue had guessed wrong. `typeof(NULL)` is six characters and not four, because the quotes are part of the name upstream prints, which is visible in `typeof([])` coming back as `"NULL"[]`.
- `COALESCE`, `NULLIF` and `IFNULL` can be written. The first two are grammar rules of their own and the transformer had an arm for neither, so neither could be written at all, while `coalesce` had a signature row, a kernel and its exception to the null in null out rule underneath the whole time. `COALESCE` is written with the canonical name and the binder prints the column in capitals, because upstream calls the column `COALESCE(NULL, 1)` whatever case the query used: it is an operator there rather than a function name its parser folded. `IFNULL` is a plain call that upstream's parser rewrites into that same operator, qualifier and all, and the wrong number of arguments to it is a parser error there rather than the binder's arity message, so it is one here too. `NULLIF` is a macro upstream, `CASE WHEN a = b THEN NULL ELSE a END`, and it is a function here because the column is named after the call and not after the expansion. Both things that follow from that macro were measured. A null on the right hands back the left value, since `1 = NULL` is null rather than true, which makes this the second function after `coalesce` that has to sit above the null rule. And the answer keeps the first argument's own type while the comparison happens at the type the two promote to, so `nullif(2, 2.5)` is the INTEGER 2 rather than null or a decimal.

## 0.2.22

The release where a group by that does not fit in the memory limit finishes anyway. One change, and it is the only reason any ClickBench query fails to produce an answer at all. The storage format version is unchanged, because the spill file is temporary, is read back by the process that wrote it and is removed when the query ends.

- The hash aggregate spills to a file when its table fills the budget, and it splits the input by key rather than by row. A pass that runs out of room keeps the groups already in its table and writes any row whose key is not one of them to a file, whole and unfolded. Nothing already in the table ever goes out, so a key is either finished in this pass or absent from it entirely, and the next pass can aggregate the file knowing nothing about the rows that came before. That is the whole of why no aggregate state is written. Three memory problems turned up on the way and all three are fixed here, because a spill that spills and then dies converting is no better than one that never spilled. The table charge was still held while the table was being turned into rows, even though the map had already been consumed by that loop, so a new `Reservation::shrink` gives part of a reservation back and the aggregate gives the table back and keeps holding the accumulators. The conversion asked for one block of twenty four bytes per group plus sixty four per aggregate per group, which for a million groups is the largest single allocation the query makes, and it now converts one vector of groups at a time and gives the charge back after each one. Finished chunks were carried across passes, which turned the second pass into the first pass plus everything the first pass produced, and each pass now builds its chunks at its own end. On a four thousand group test the peak went from 2.46 MB to 2.03 MB before any spilling happens at all. What is left undone is named rather than hidden. The answer is still held in memory, so a query whose output alone fills the budget still runs out, correctly. Each pass rereads the whole file from the start, so a query needing many passes reads it many times, and hash partitioning the spill so a pass reads one partition is the obvious next thing. A file that would take more than sixty four passes is refused early with an out of memory error rather than run for an hour, using the rows already written divided by the groups a pass finished as a floor on the passes left.

- A group key is charged for the copy the table keeps rather than for the buffer it was read into. ## 0.2.16

The release where the optimizer starts changing what the operators have to do rather than only where they do it, and where a database opened with no settings has a memory limit. The storage format version is unchanged, because nothing here writes a file.

- Top N, so an order by with a limit holds the limit and not the input. The plan for `ORDER BY x LIMIT 10` was a limit over a sort, and a sort has to see every row before it can emit the first one, so it held everything and the limit above it threw almost all of that away. `Node::TopN` is the one operator the pair collapses into, under the name `top_n`, which is what `duckdb_optimizers()` calls the same rewrite. The offset is on the node rather than left above it, because the rows that get skipped still have to be found before there is anything to skip them from, so what is kept is `count + offset` rows. The operator collects until it holds twice the bound, then sorts and keeps the better half, which is not the textbook heap and is chosen for a reason: the sort promises that rows tying on every key come out in the order they went in, and a heap does not, because sifting moves equal elements past each other. The cost is the same either way. On one million rows of the ClickBench table, `ORDER BY "EventTime" LIMIT 10` goes from 2.29 seconds to 0.48 and `ORDER BY "URL" LIMIT 3` from 4.85 to 0.88, with the answers byte identical to what the sort produced.
- Null rejecting predicates, so an outer join becomes the join it really is. An outer join exists to produce rows padded with nulls, and a predicate above it that cannot be true of a padded row means those rows were never wanted, so the join that made them becomes a join that does not. `WHERE b.z > 5` over a left join is an inner join, and a full outer join with a rejecting predicate over one side becomes the one sided join that side leaves. The analysis is a six element lattice over one expression, which answers null, true, false, dropped, present or unknown for a row whose padded side is entirely null, and the sixth element is the one that matters: `unknown AND null` is not unknown, it is an expression that is never true, and a five element version of this quietly loses that. Only `coalesce` is tolerant of a null argument, everything else in the function set is strict, and `CASE` and aggregates are always unknown. It is worth an order of magnitude on its own, since the converted join then takes the predicates and the transitive predicates that a left join refused: two forty thousand row tables joined and filtered went from 37.0 seconds to 0.86.
- Transitive predicates, so a join key carries a filter to the other table. An equality between two columns means anything said about one of them is said about the other, and without that a query that restricts one table and joins on a key gives the other table nothing to narrow with. The derived predicate goes through the pushdown rules like any other, so it lands wherever it can land, and it is compared by structure rather than by arena position before being added, because a predicate the query already had would otherwise be written down twice and the pass would produce a different plan every time it ran.
- A memory limit by default, which is eighty percent of physical memory, the fraction DuckDB uses. Eight of the forty three ClickBench queries used to end in `memory allocation of 128 bytes failed`, which is the Rust allocator's abort handler and not something a program can catch. The accounting that raises `Out of Memory Error` instead has worked since 0.2.12 and had no limit to check against. Reading how much memory there is is per platform and lives in `rudb-io`, because two of the three calls are C calls: Linux takes the smaller of `MemTotal` and the control group limit, macOS asks sysctl for `hw.memsize` and Windows calls `GlobalMemoryStatusEx`. The control group half needed a second pull request to work at all, since it read the file at the root of the cgroup mount and a process is almost never in the root group. The group to ask is the one in `/proc/self/cgroup` and every parent of it, because a limit on a parent binds a child as much as its own does and systemd routinely puts the limit on a slice rather than on the scope inside it.
- A hash table is charged for the room it took rather than for what it put in it, which is what makes the limit above stop anything. The aggregate accounted for about two fifths of what it really held, so on server3 with a twelve gigabyte cap and the budget correctly set, ClickBench q16 was still killed by the kernel at 12.5 GB resident and never raised `Out of Memory Error`. What was missing is everything that is not the entries: a `Vec` doubles and so sits between half empty and full, a `HashMap` fills to seven eighths and then doubles as well, and a group allocates four separate blocks each of which costs the allocator a header and an alignment, which on seventeen million groups is seventeen million of those. The containers are now charged for their capacity, once per input chunk, and the per group charge covers only the blocks.
- `SELECT count(*) FROM (SELECT DISTINCT region FROM sales)` came back as 1 on any table with a row in it. Column pruning narrows a projection to what something above it reads, nothing above a `DISTINCT` under a `count` reads anything, so the projection lost every column and the operator underneath was left deduplicating rows with nothing in them to tell them apart. A plain `DISTINCT` is distinct on everything its input produces and names none of it, which is the same shape a set operation has, and it now gets the same treatment: its input is left alone. A `DISTINCT ON` binds to what it reads and still narrows underneath. Found by the committed corpus in tamnd/rudb-compat when the pin there moved to 0.2.15.

## 0.2.15

The release where a query's plan gets rearranged before it runs, and where a pass can be turned off from SQL to prove it. The storage format version is unchanged, because nothing here writes a file.

- Filter pushdown, in two pull requests because the second one is where a wrong answer would come from. The first moves a predicate through the operators that have one input: the conjunction is split so half of an `AND` can reach the scan without the other half, a predicate goes through a projection rewritten in terms of what the projection computes from, through a group by when it is over group keys only, and through a sort and a plain `DISTINCT` unchanged, and it stops at a limit, at `DISTINCT ON` and at a set operation. The second crosses a join, which needs to know which tables an expression reads, so the table set analysis this milestone asks for arrives with it as a bitset cached by expression. A predicate moves into a side when what it reads is a subset of what that side produces and the join keeps every row of that side, which is true of both sides of an inner join, of the left of a left, semi, anti or single join, of the right of a right join and of neither side of a full or positional join. A predicate that reads both sides becomes a condition on an inner join and stays where it was over anything else. It was written, measured and taken back out before the merge. On server2 with ten thousand rows against fifty thousand, the cross product with a filter over it is 1.25 seconds and the inner join with the same predicate as a condition is 10.7, and the same cross product with every column pruned away is 0.060, so producing the pairs is not what costs. Every join is a nested loop that runs its condition over one left row against a chunk of the right side, where a cross product hands whole chunks on and lets the filter run over a chunk of pairs at once. Writing the better plan for the slower operator is how an optimizer makes a query slower while every test still passes, so the rewrite waits for the executor and the pass says so in its own documentation with the numbers in it.
- `SET` and `RESET` as statements, with `disabled_optimizers`, `memory_limit` and `threads` behind them. The first is the one this milestone needed, because turning a pass off from SQL is how a wrong answer gets attributed to a pass, and a corpus file that does it is already written in DuckDB's spelling. A pass name nobody has fails at the `SET` rather than at the next query. Moving `memory_limit` moves it for the queries already running, and a query already holding more than the new limit allows keeps what it has and is refused the next time it asks, which is what the binary does and is the only reading that does not turn a setting into a way of killing whatever happens to be running. `threads` is recorded and not obeyed until the executor has more than one. A `RESET` goes back to what the database was opened with rather than to a compiled in default. All three are global, which is the scope DuckDB gives them, and `SET LOCAL` and `SET SESSION` are refused with the two different sentences the binary prints for them.
- `1GB` and `1GiB` are two different numbers, which corrects the 0.2.10 notes. That entry said they are the same number here for the same reason DuckDB makes them the same number, and DuckDB does not make them the same number. Measured on the pinned binary, `SET memory_limit='1GB'` reads back as `953.6 MiB` and `SET memory_limit='1GiB'` reads back as `1.0 GiB`, so `KB`, `MB`, `GB` and `TB` are powers of a thousand and the `i` spellings are powers of 1024. The stated reason for the old behaviour, that a script saying `10GB` has to get the same number from both engines, is the reason for the new one. A fraction is allowed because the binary allows one, and a limit prints back in the family it was written in.

## 0.2.13

The release where DuckDB's own ClickBench entry runs against rudb with nothing about it changed, and the first release with a correctness number over the real file to go with it. The storage format version is unchanged, because nothing here writes a file.

The grammar has `:=` and `=>` and it has no rule at all for `name = value`, which parses as an equality and is picked apart afterwards the way DuckDB's own transformer does it, and that third spelling is the one the entry uses. - The CSV writer quotes a field on the bytes the binary quotes it on. This was found by the first differential run of all forty three queries, which matched on two of them with nothing wrong with any of the answers. The writer quoted on the separator, a double quote and a line break, which is RFC 4180, and the shell does not follow RFC 4180. It carries a table and quotes on every byte under `0x20`, both quote characters, `0x7f` and the whole of `0x80` to `0xff`. Thirty two of the forty three queries return Russian text, so almost every output differed. - Constant folding, and the machinery a sequence of optimizer passes needs. The pass is `expression_rewriter`, in DuckDB's spelling, because a corpus file that says `SET disabled_optimizers = 'expression_rewriter'` was written to turn this off. It folds an expression whose operands are all constants and then applies what folding exposes, so a true operand drops out of an `AND`, a comparison against a null constant is a null boolean, and a `CASE` arm with a false condition is gone. Everything it computes goes through the same kernels the executor calls for the same expression, so a folded answer and a computed answer are the same answer by construction rather than by testing every function twice. Three things stop a fold: a kernel that returns an error, which leaves `CAST('abc' AS INTEGER)` alone so the error still comes from running the query, a volatile function, of which rudb has none yet so the list is defensive, and a value whose type is not the type the plan recorded. The passes run in a fixed sequence rather than to a fixed point, because a pair that undo each other runs forever and the version that stops after a few rounds has a plan that depends on how many rounds it was given, and in a debug build the whole sequence runs a second time and the two plans have to print the same. Folding comes before pruning, since folding removes column references and pruning drops the columns nothing refers to.
- Parquet files written in zstd read. Dictionaries are refused by name rather than decoded without one, since Parquet does not use them and decoding without one produces bytes rather than an error. Eleven frames from the zstd command line tool are committed and run through, chosen for what a frame contains rather than what it looks like, and the two real bugs both turned up there and were silent wrong answers rather than crashes.

Thirty two of the forty three outputs are byte identical. The other eleven are every one of them a `LIMIT` over an `ORDER BY` whose key ties across the cut, or a `LIMIT` with no `ORDER BY` at all, the ordering key multiset is identical on all of them, and which ten rows come back is not something the SQL decides. That is the base number the kernel work has to move and it is the first one that means anything, because it is the same SQL over the same file compared byte for byte.

- A `Database` is a cheap clonable handle rather than a thing with `&mut self` on every method, so a program can use it from more than one place. `Database::connect` gives a `Connection`, which is the same sharing with a name that says what it is for. `Database::open` says what a database name means in one place: the empty string and `:memory:` are in memory, which are DuckDB's two spellings of it, and anything else needs a storage format and so is an error.
- Prepared statements, with all four ways DuckDB lets a parameter be written: `?` numbered by where it is, `?1` and `$1` numbered by hand, and `$name`. The statement is bound again for each set of values rather than planned once and filled in, which is the opposite of what a transactional database does and is the right way round here, because a plan built without knowing whether `$1` keeps one row in a million or half the table is a plan built blind. Parsing is the part that is pure overhead and that happens once.
- `read_parquet(['a.parquet', 'b.parquet'])`, the second overload of both file readers. A list is not a glob written differently, which is the part worth testing. A glob is sorted and deduplicated because it comes from a directory and nobody chose the order, and a list was written by somebody, so it keeps their order and reads a file named twice twice.
- A CSV read over several files sniffs every one of them rather than taking the first file's answer. That is right for Parquet, where a file states its schema, and wrong for CSV, where a file states nothing and a directory of daily exports would come out BIGINT or DOUBLE depending on which day sorted first. Measured at two, three, four and six files. Each file is then told the types the whole read settled on before it parses a row, including the first one.

The pages of a column chunk are found by walking, because there is no index inside a chunk: decode a header, take the body it sized, start again at the byte after. Then a page becomes a vector, with the wire type deciding how to read and the logical type deciding where to put it, so a `UTINYINT` that arrives as four byte integers lands one byte a value and is checked per value rather than assumed. A chunk that runs out of buffer with values still owed is an error and not the end of the chunk, since a column with fewer rows than the one beside it is a wrong answer, and that is exactly what a short read from the I/O layer will look like. And a dictionary page does not count against the chunk's value total, so a reader that decremented on every page stops one page early on most of `hits`.
- `Vector::slice` exists because of that reader. Two columns of one row group are free to page differently, so a chunk ends wherever the first projected column runs out of its page, and the first version cut with `Vector::gather` and got a flat vector back every time. A writer puts 2048 rows in a page and a chunk holds 1024, so almost every page of every dictionary column gets cut, and cutting with a gather means no dictionary column ever reaches an operator as a dictionary. A slice keeps each form as itself: a dictionary slices its codes and keeps its dictionary, a sequence moves its start along, a constant stays a shorter constant, and a flat body is the only one that copies.

ClickBench files come from all of them, so a reader that only reads what DuckDB writes is not a Parquet reader. The pool was being built inside the timed region, so every sample paid for spawning and joining its threads and the pool lost to the plain `read_at` loop on every pattern. It is a pull decoder rather than a deserializer, with no derive and no intermediate tree, because a tree allocates a node per field of a footer that on `hits` has a hundred and five columns in every row group and every node would be read once and dropped. It is not met at 64 and 128 bits, where Int64 is 1.13, UInt64 1.22, Int128 1.52, UInt128 1.82 and Float64 3.52.

So the boundary worth optimizing against is `Validity::Mask` against `Validity::AllValid`, and a mask of all ones is the case to catch, not a low null rate.
- 129 of 618 cells fell through to the row at a time path and the table stars every one of them, which turns two missing loops from a counter nobody prints into a column. Comparison has no loop for a dictionary against a flat vector, 60 to 120 nanoseconds a row for fixed width against 1.0 to 1.9 for the same dictionary against a constant. The function call path has no dictionary loop at all, so both dictionary columns of the arithmetic table are the oracle's numbers at 73 to 105.
- The compaction crossover says noise when the gap between the two pass columns is smaller than the spread of the two timings it came out of. That is not a cosmetic choice: a depth computed from a gap that size swings between seven and never between two runs of the same binary, and a table that prints one of those is worse than a table that admits it did not measure it. Where it is firm, one bigint column says 7 to 8 later passes and four say 6 to 9, and the shape with a varchar column says noise or never at every selectivity.

The curve flattens after 1024 and never turns back up, so the L1d residency argument is not what this machine says, and the sweep is there to find out whether it holds on a machine with a smaller one.

## 0.2.1

Layer one of the engine plan, continued. The data plane's last three interface decisions and the list the kernels generate their loops from. Every box on M2b is ticked and the storage format version is unchanged, because nothing here writes a file.

- The physical layouts are one list, in `rudb-vector`, and every kernel generates its per layout loops from it. Each kernel already wrote its body once and let a local macro repeat it, so the loops were never the problem. The list was: the set of layouts each macro is expanded over was written out at ten call sites across four files, and a list written ten times is a list that is wrong in one of them. That failure is not a compile error, it is one layout missing from one kernel's match, falling through to the row at a time path, and what anybody notices is that one column type is thirty times slower than the others. `for_each_layout` hands a named group to a caller's macro, each entry being the variant, the element type and the value that fills a slot whose row is null.
- The groups have rules rather than membership lists. `ordered` is the layouts whose SQL order is the derived order of the element type, which is why neither the floats nor the strings are in it. `exact` is the integers whose every value fits in an `i128`. `narrow` is the integers under 128 bits, which is both the group whose whole vector totals inside an `i128` and the group a run of `i128` narrows into, and those two rules having the same answer is why there is one group rather than two.
- The list is checked rather than trusted. `Data::len` is generated from the `all` group and its match has no wildcard arm, so a variant added to `Data` without being added to the list does not compile. Every other group is pinned to `all` by a test, each one plus the layouts it deliberately leaves out being exactly the group above it, so a new fixed width layout that nobody adds to `ordered` fails a test with the name of the layout in the message. Deriving the groups from one list instead of checking them against it would need a macro that can compare two identifiers, which `macro_rules` cannot do, and the alternative is a procedural macro crate for nine lists.
- The payload of a flat vector is a `Buffer<T>` rather than a `Vec<T>`, which is the seam the buffer manager arrives through. At layer three a scan reads a page and the vector should point into it rather than copy out of it, and that copy is the largest one in the system because it is every byte of every column every query reads. The decision that had to be made now is how the borrow gets expressed, and it is a reference counted pin handle rather than a lifetime parameter: a lifetime on the buffer is a lifetime on `Data`, on `Vector`, on `Chunk`, on every operator's state and on every queue the scheduler puts a chunk into, and the two ways out of that are unsafe code or a copy at the thread boundary, which is the copy the borrow existed to avoid. The enum lands with only the owned variant in it, so adding the borrowed one later is a change inside `rudb-vector` rather than a change to every signature in the workspace. Readers were migrated by the `Deref`, since everything outside the crate reads a slice and a slice is what both variants hand back, and writers were migrated to `Buffer::to_mut`, which is the one function that has to grow a copy on write case.
- `StringColumn::over` and `StringColumn::push_in_place` are the other half of the same seam. A column can now be built over an arena that already holds the bytes, recording where each string is instead of copying it, which is what a Parquet page of strings wants. A string short enough to sit inside its view is still copied into the view, which is at most twelve bytes and is what lets it be read without going near the arena. The range is checked and the bytes are validated as UTF-8, because `StringColumn::get` hands back a `&str` and a column that cannot produce one for a string it claims to hold is a wrong answer rather than a slow one.
- Two columns holding the same strings are now equal whatever their arenas look like. Derived equality was equality of the representation, which was the same question as equality of the strings only because the arena was fully determined by the order of the pushes. Building a column over a page breaks that, and without the change every test that compares two vectors would have been asserting on how a column was built.
- `Chunk` is asserted `Send` at compile time. That is the scheduler's half of the data plane contract and it is not free: it rules out an `Rc` anywhere in a vector and any borrow of thread local state, and it is what the pin handle is protecting. A static assertion rather than a comment, because every one of those mistakes compiles perfectly well on its own and would otherwise be found eight layers later.
- A dispatched release run builds the tag it names. Every checkout in the release workflow takes the dispatch input rather than the default branch, which is what it always meant to do: without it a dispatch checks out `main` and then verifies the tag it was given against whatever version `main` is on, which is never the version of an older tag.
- Measured on `server3`, six interleaved rounds of each build, the wrapper costs nothing: flat against constant comparison 0.44 nanoseconds a row against 0.43, flat against flat 0.36 against 0.31, building a flat vector 0.11 against 0.09, gathering half a chunk 4.11 against 4.17, building a string column 9.83 against 9.55, comparing one against a literal 12.15 against 11.92, and compacting half a chunk 10.06 against 10.11. An earlier pair of runs said the string comparison had lost a nanosecond a row, which is why the numbers above are minimums over interleaved rounds rather than a back to back pair: this machine moved the same binary by five nanoseconds a row between two runs of that benchmark.

## 0.2.0

M1, the format experiment, closed. The minor version moves because a milestone finished, and this one finished by failing its exit criterion in the way the criterion was written to allow.

The milestone asked whether the three multi-column compression techniques in `spec/06-compression.md` deliver the ratios the resource claim was built on, and named 6 GB on ClickBench `hits` as the number above which the claim is wrong and the specification gets amended rather than defended. `hits` came out at 9.65 GB. All three answers are no. Shared dictionaries are worth 4 MB of a 9.65 GB file on `hits` and 17 KB on the one other corpus out of ten where they apply at all. Shared symbol tables are more than twice the size of encoding the columns apart. Recomputation rules held once in eight named rules on `hits` and once in twenty eight candidates across everything else, and the one that held saves eighteen megabytes. What did work was front coding a sorted dictionary, which is a single column technique that is in nobody's list of things DuckDB cannot do, and which took `hits` from 11.65 GB to 9.65 GB on its own.

Ten corpora, 47.53 GB of Parquet into 31.58 GB of rudb, every chunk verified by decoding it back. That is 1.51 times smaller than Parquet and 2.12 times smaller than DuckDB's published `hits`. Documents 00, 02 and 03 say 2.1x on disk now instead of 10x, with the measurement written out and the paragraph that made the original prediction left in place so the difference can be checked. Sections 6.4, 6.5 and 6.6 are demoted to optional mechanisms scheduled for no milestone. Float encoding and a general block compressor at the end of the cascade are scheduled, the second because the one corpus where rudb lost did so by 2.26x on a single column of polygon text and a cascade with no block compressor at the end of it has no floor. The chooser encoding every candidate in full, which runs the write path at 5 MB/s against a read path at 186, is named as the thing that blocks the storage engine.

The report is at https://github.com/tamnd/rudb-bench/blob/main/reports/m1-the-format-experiment.md and the measurements pass by pass are on https://github.com/tamnd/rudb/issues/2.

Alongside it, the first four pull requests of M2b landed in `rudb-vector` and `rudb-kernels`, and the storage format version is unchanged because nothing in this release writes a file.

- The release workflow no longer lets GitHub's hosted macOS queue decide when a release exists. The matrix is two jobs now, the hosts that get a runner immediately and the hosts that do not, the GitHub release waits only for the first, and the darwin archives are attached to it when they are ready. Nothing is dropped from the release and a host that fails to build still fails the run. This is the same move the crates.io upload already made after the 0.0.2 tag, applied one job further along after the 0.1.2 tag went live on crates.io while its GitHub release sat in draft behind two macOS jobs that had not started. The build and package steps moved into `.github/actions/build-archive` so the two halves of the matrix cannot drift apart.

- `cargo xtask rowloop` fails the build on a loop over the rows of a vector that builds a `Value`, and it runs in the gate. The rule exists because this repository has had the same defect twice and found it both times by reading rather than by testing: `Vector::flatten` was collecting a `Vec<Value>` of a whole vector and pushing every value back into the layout it had just taken it out of, which was 2.6 times the result path of a returning query, and the comparison kernel was building two owned `Value`s a row before it was rewritten around a typed loop. A loop that means to work a row at a time says so in a comment reading `row at a time:` and then a reason, on the loop or in the comment block above it. Twelve loops say it today. Five are the kernel fallbacks, which are meant to be slow and already count themselves. Seven are debt, and each of those names the sub-milestone that removes it, which turns the list from something you find by reading the tree into something you find with `grep`.
- `range` and `generate_series` build their chunk as a run of `i64` rather than as a list of tagged values that then has to be read back one at a time to find the run again. That function is the source every microbenchmark in `rudb-bench` reads from, so a chunk of it costing a `Value` a row would have meant measuring the generator instead of whatever was downstream of it.

- `StringColumn` holds one arena rather than a `Vec<Vec<u8>>` of 16 KiB blocks, so reading a long string is one load from a base the compiler can keep in a register instead of two dependent loads through the outer vector. The offset in a view is the whole 8 bytes now rather than a block index and an offset within it, which is what Arrow spends them on because an Arrow array is a list of buffers and this is not. On `server3`, over a chunk of 1024 strings, comparing the column against a literal went from 14.9 nanoseconds a row to 13.2 at 40 bytes a string and from 14.2 to 12.9 at 120, gathering half the rows went from 29.5 to 25.3 and from 36.9 to 29.1, and building the column went from 12.0 to 8.9 at 40 bytes. The case that used to need a block of its own, a string longer than a block, is gone.
- Building a column whose payload passes 128 KiB went the other way, 14.6 nanoseconds a row to 41.0, and it is worth writing down what that is. It is not the copy and not the doubling, it is glibc: an allocation that size comes from `mmap`, goes back to the kernel when the column is dropped, and faults every page in again for the next chunk, where 16 KiB blocks come back off a free list already faulted. With `MALLOC_MMAP_THRESHOLD_` raised the arena builds that same column in 9.6 nanoseconds a row against the blocks' 16.2, so the design is not what is slow there. The fix is a chunk's payload coming from a pool the engine owns rather than from `malloc` per chunk, which is the buffer manager at layer three. `StringColumn::reserve_bytes` is the part available now and recovers a quarter of it, and `Vector::gather` calls it, because the views carry their lengths so the byte count is known before any byte is copied.

- `Vector::dictionary` composes a dictionary over a dictionary into one level instead of stacking them, so the form has a depth of one however many filters a chunk has been through. The cost of stacking was a cliff and not a slope: every loop in `rudb-kernels` reaches for the values behind the codes with `Vector::data`, a dictionary pointing at a dictionary has no data to hand back, so the second level did not make the kernels slower, it turned them off and dropped the work onto the row at a time path that exists to be correct rather than fast. On `server3`, over a chunk of two numeric columns selected twice and read by two vectorized passes, that was 3.5 nanoseconds a row becoming 104, and the third and fourth levels cost almost nothing more because the first one had already given up everything there was to give. With the same chunk in three columns, one of them strings, it was 16.8 becoming 252. Composing is one pass over the outer codes, which the range check on the way in was already making. The one level it does not compose past is a dictionary carrying a validity of its own, because that vector is saying its nulls are at that level rather than in the values and pointing the outer codes straight at the values would read through the holes instead of stopping at them.

## 0.1.2

The compute kernels, and the gate that made it possible to measure them.

Ten pull requests. Seven of them are layer 2b as `spec/engine/07-execution.md` describes it, which is the six vectorized kernels in `crates/rudb-kernels` and the typed copy in `crates/rudb-vector` that they all read through, and the rest are the gate, the benchmark command and the M1 finding written back into the specification.

- `Vector::gather` copies the values at a list of positions with a typed loop per physical layout, walking a dictionary chain to its leaf and composing the codes on the way down so the copy runs once over the data rather than once per level. `Chunk::compact` is that over every column and is the copying counterpart to `Chunk::select`. The caller that mattered was `Vector::flatten`, which was collecting a `Vec<Value>` of the whole vector and then pushing each of those values back into the layout it had just taken them out of. `Database::run` flattens every chunk it returns, so on two million rows on `server3` `SELECT a, b FROM t WHERE a > 0` went from 137.6 ms to 53.5, `SELECT a, b FROM t WHERE a > 499` from 80.7 to 32.2 and `SELECT a FROM t WHERE a > 499` from 44.1 to 20.3.
- Nothing in the pipeline calls `Chunk::compact` yet, and the measurement is the reason. The obvious rule is a selectivity threshold, and measured the deciding variable is not selectivity but how many times the kept rows are read again afterwards, which is a property of the plan above the filter rather than of the chunk. Compacting loses at every selectivity with one later pass over the chunk and wins at every selectivity with sixteen, and a filter today feeds an aggregate or a projection, which is one pass or two. A threshold was wired into `Filter`, measured in both orders, and taken back out rather than shipped as a constant the numbers do not support.
- The comparison kernel dispatches once on the form pair and the physical type and then runs a loop with no branch in it. The index mapping is a generic parameter rather than a function pointer in a tuple, because a `fn(usize) -> usize` behind an indirection is a call the compiler will not inline and that alone was most of the cost.
- The scalar functions, the three-valued logic and the numeric casts, each on the same shape. Three lessons came out of them and are written into the module documentation: a per-row `checked_*` with an immediate `Err` return stops the loop being a shape that unrolls, so the check belongs at the vector boundary with an accumulator wide enough to carry it; reading validity one bit at a time costs a bounds check, a divide and a shift per row, and `Bitmap::word` with `Validity::from_run` is the fix; and matching on the `Validity` enum inside the row loop costs about three quarters of a nanosecond on top of an addition that takes one, so the three-way dispatch is hoisted out of every row loop.
- The aggregates, where a vectorized float sum has to stay sequential because floating point addition is not associative, and has to carry the running total into the vector rather than total the vector on its own.
- Turning a boolean vector into the rows it keeps is a kernel rather than a loop in the filter operator, and it is branchless because the branch in `if kept { push(index) }` is unpredictable by construction. Every row writes its index at the current length and only a kept row moves the length on. The row at a time path cost 21.9 ns a row at one percent selectivity and 29.0 at fifty, which is the mispredict; the branchless one is flat at about 1.0 across every selectivity, and `SELECT sum(a) FROM t WHERE a > 500` over two million rows went from 59.8 ms to 15.9.
- The fallback path increments a counter per kernel and form pair that the benchmark harness dumps, so a hot combination that is falling through to the general path is a signal to specialize rather than a guess.
- `range` and `generate_series`, which is the first table function and is what a query can be written against without a file to read.
- `cargo xtask bench <suite>` runs the whole comparison from one command. It finds a `tamnd/rudb-bench` checkout beside this one or wherever `RUDB_BENCH_REPO` points, builds rudb and builds the harness, and hands the first to the second through `RUDB_BENCH_RUDB`, which is the entire coupling between the two repositories. `spec/engine/13-measurement.md` section 13.8 asks for one command on the grounds that a result which needs a sequence of steps is a result that gets reproduced once. Without a suite name the task is what it always was, which is the front end table, so CI and the README are unaffected.
- The focused gate compiled every library crate when `xtask` changed and did not compile `xtask`. Its own tests therefore only ran under `--full`, which is the mode nobody uses while they are working, so a change to the task runner was the change least likely to be tested before it landed. The task runner is a gate member now, and a change to `rudb-parse` reaches it the same way a change to `rudb-parse` reaches anything else that links it.
- On `server3`, `smoke` against DuckDB v1.5.5, ClickHouse 26.9.1.1138, DataFusion 55.0.0 and Polars 1.44.2, all four agreeing on all six queries: 848.818ms, 4.440s, 1.253s and 3.007s hot. rudb abstains, because there is no path from a file on disk into a chunk yet, and the harness prints the reason and the sub-milestone that closes it rather than a blank column.
- `CREATE TABLE`, `DROP TABLE` and `INSERT`, from the written statement to the catalog. The grammar already accepted all three, so this is the transformer, the binder and the execute path, and none of it is a new plan node. A DDL statement produces no rows, has no cost and cannot be pushed past anything, so a `Node::CreateTable` would be a node every optimizer rule has to be told to leave alone. What the binder returns instead is a `Bound`, which is a plan for a query and a resolved catalog operation for the other three, and `Database::execute` dispatches on it.
- `VALUES` as a query and in a `FROM`. It was the missing half of `INSERT`: the grammar spells `INSERT INTO t VALUES (1)` as an insert whose source is a select statement whose body is a values clause, so the two arrive at the binder in the same shape and the insert walker has one arm rather than two. The column types are what every row in that position promotes to, which is the rule a set operation already used.
- An `INSERT` arrives at the append with a plan whose output is exactly the target's columns, in the target's order, with the target's types. The casts and the nulls for columns the statement did not name are in the plan, so the append is a loop over chunks and has no decision left to make. The source also runs to completion before anything is appended, which is what makes `INSERT INTO t SELECT * FROM t` read the rows that were there when it started.
- A decimal can be written into any of the four runs its precision chooses. The read path handled all four widths and the write path only accepted the 128 bit one, so `SELECT 2.5` bound fine, planned fine, and then failed with an internal error saying the value did not belong in the vector. Anything narrower than `DECIMAL(19, s)` was unstorable.

A `NOT NULL` column constraint, because nothing carries a nullability yet and accepting it would let an insert of a null succeed where DuckDB raises. `PRIMARY KEY`, `UNIQUE`, `CHECK`, `DEFAULT` and `REFERENCES`, for the same reason. `RETURNING`, `ON CONFLICT`, `BY NAME` and `OR REPLACE` on an insert. Each of those changes what the statement means, and a dropped clause is a wrong answer.

Each value stores the length of the prefix it shares with the value before it and the bytes after that, and what is left over is a string column that goes back through the chooser, so `DICT(FRONT(FSST))` is a shape that falls out of the recursion rather than one anybody named. It is the answer to the finding below about `URL`: a dictionary sorts its entries, so a dictionary of URLs is a sorted list of URLs, and the value before each entry is the closest thing in the column to it. On the first five million rows of `hits`, against the same slice on the same machine before the change, `URL` goes from 129.68 MB to 83.78 MB, `Referer` from 176.52 to 131.14, `OriginalURL` from 66.34 to 43.89 and `Title` from 108.99 to 84.52. Six levels, chosen one candidate at a time by a chooser that knows nothing about URLs.

- The milestone wants the file under 4 GB and says the resource claim is wrong at 6 GB or above, so at 9.65 GB the claim is still wrong and the gap is no longer explainable by any single column. That is the M1 finding and section 5 of the exit criterion says amending the specification is the success case here.
- The candidate is offered when neighbouring values share at least a twentieth of the column between them, which is a pass of byte comparisons that stop at the first difference, so a column with nothing to share pays almost nothing to find that out. What it does cost is the encode of the columns where it does apply, and the chooser prices every candidate that applies: those four columns went from 203 CPU seconds to 418.
- The shared symbol table strategy front codes each column before compressing it. It has to beat encoding the columns apart and encoding a column apart can front code, so a shared table that could not was measuring itself against a baseline nobody had written it for, and on the generated URLs in the tests that gap was a factor of two. Front coding a column whose neighbours share nothing costs a run of zeros, which the integer chunk stores in a few bytes, so there is no decision to make.

On the test corpus the crossover is between two and four thousand values a column, 21,319 bytes shared against 22,223 apart at two thousand and 41,002 against 39,750 at four. The gain from a shared table is a small column's gain, which is what section 6.4 said it was.
- The empty value is left out of the overlap question. This lab stores a null as an empty string, and on `hits` most of the string columns are mostly null, so the sketches said that sixteen columns which share no vocabulary at all overlap enough to want one dictionary. They have the empty string in common and nothing else. With it left out, `hits` has exactly one pair of string columns worth grouping, `UTMSource` and `UTMCampaign`, out of 5,460 pairs. The dependency question still counts the nulls, because a column that is always null really is determined by everything and the point is to see that.
- `stats` prints the whole shape of the first chunk for the twelve columns that carry the file, under the table. The table has room for the head of a shape and the head is what says which shape won, but `DICT` on a column of nineteen million URLs is the same word whether the dictionary went back through the chooser and came out FSST or whether it is sitting there as plain bytes, and those two are a gigabyte apart. That is how the finding about `URL` below was found.
- One table for the grammar. `NODES`, `FIRST` and `NULLABLE` were three arrays read at the same index for every node the matcher entered, and they are one array of twenty four byte nodes now. A `Rule` node carries the index of its body as well as the index of the rule, so entering a rule does not read `RULES` either. The argument for the parallel arrays was that the filter could reject a node without loading it, and it counted the node the filter rejects rather than the node it accepts, which is the one that is loaded a line later. It is worth saying that this did not show up in the times: alternating runs of the two layouts on three machines put the difference inside the noise, so whatever the walk is spending twenty nanoseconds a node on, it is not five array reads. The layout is kept for being one table rather than three, and the question of where the time goes is still open.
- A choice skips the alternatives that cannot match before it pushes anything. It used to enter each one and let the guard at the top of `enter` say no, which is a step and a stack push and a stack pop for a test that is a load and an AND, and `Statement` has thirty six alternatives. The twelve query workload went from 22,142 steps to 20,038, and the test that says work stays proportional to the query came down from 400 steps a token to 200. Steps are counted rather than timed, so that number does not depend on which machine ran it.
- The sharing and recomputation pass, `format-lab groups`, which turns the two pairwise answers into bytes. It picks groups out of the sketches with `multi::dictionary_groups`, encodes each group three ways with `multi::strategy_sizes` and subtracts, and prices a named dependency by building the mapping in first appearance order of the determining column and encoding that instead of the column. It counts violations while it builds, because a rule that holds on a sketch does not have to hold on the rows.
- The pairwise pass, `format-lab pairs`, which is boxes three and five of the milestone. It answers which column determines which other column and how much two string columns overlap, for every pair of a 105 column table, on one walk over the file.
- `sketch::pair_of` in `crates/rudb-encoding`, the pair hash of two values whose hashes are already known. Testing 5,460 pairs by hashing the two values again for each of them would hash every value of every column 104 times over, and the lab hashes each column once a row and combines instead. It is the same answer, and it is the difference between a pass that finishes in an afternoon and one that does not.
- The format lab, in `experiments/format-lab`, which is the first thing in this repository to read a real file. It streams Parquet a chunk at a time, runs every column through the chooser, decodes it again and checks it, and prints per column what Parquet stored the column in against what rudb produced. It is a separate workspace with its own lock file so that linking arrow-rs does not put an external dependency anywhere near a published crate, and it is not in the gate.
- The whole of ClickBench `hits`, 99,997,497 rows and 105 columns, through the chooser on a four core machine in 77 minutes, before front coding existed. Parquet with Snappy holds the columns in 13.76 GB and rudb produces 11.65 GB, which is 0.85 of Parquet and 0.57 of DuckDB's 20.46 GB. The milestone wants under 4 GB and says that at 6 GB or above the resource claim is wrong, so on single column cascades alone the claim is wrong and the earlier extrapolation from the first million rows, which said somewhere near 9 GB, was optimistic.
- All 814 chunks of all 105 columns decoded back to exactly what went in. That is 85,470 column chunks of values nothing in this repository generated.
- Three columns are 6.11 GB of the 11.65, which is 52 percent of the file in `URL`, `Referer` and `OriginalURL`, and the chooser loses to Snappy on all three: 0.99, 0.92 and 1.26. It is not for want of cascading. The dictionary entries do go back through the chooser and do come out FSST, `DICT(FSST[255](...), ...)` on every one of them, and a 255 symbol table on a column of URLs still loses to a general purpose block compressor. FSST compresses each string on its own and Snappy has the previous few kilobytes of the page to point back into, and on URLs sharing a host and a path prefix that is most of the redundancy there is. A sorted, front coded dictionary is the shape that gets at it, and that is the thing to try next.
- The chooser costs 133 CPU seconds a gigabyte of values, so the pass was 3.7 CPU hours, and decode runs at 149 MB/s a core against encode at 7. A write path twenty times slower than a read path is not a shippable write path.
- Peak resident size for a 105 column streaming pass at DuckDB's row group of 122,880 rows is 986 MB on the whole file, against 441 MB on the first million rows. The difference is the per column sketches filling up, and it is still a number a five gigabyte machine can hold.

## 0.1.1

The encodings M1 needs, and nothing that reads a real file yet.

Six pull requests, all of them inside `crates/rudb-encoding`: bit packing, the integer encodings and the cascade over them, FSST, the string column, a bottom-k sketch, and multi-column compression. That is the machinery `spec/06-compression.md` sections 6.2 to 6.5 describe, with the parts of 6.4 that are correlation encodings and the whole of 6.5 still missing.

None of it has seen real data. Every number below is from a synthetic corpus that is more repetitive than a real URL column, which makes them useful for saying which mechanism beats which and useless for saying what `hits` will come out at. The milestone's exit criterion is a report on real files and this release is the thing that will produce it, not the thing that answers it.

One result is worth pulling out of the list because it changes what to build next. On these columns a shared dictionary saves a third and a shared symbol table saves under 3 percent, so the two forms of sharing in section 6.4 are not comparable in value and only one of them is obviously worth a storage engine.

- Multi-column compression, in `crates/rudb-encoding`. A group of string columns encoded together, choosing between encoding them independently, one FSST symbol table trained over all of them, and one dictionary holding the union of their values with every column becoming codes into it. Section 6.4 calls this the mechanism that has no equivalent in DuckDB, and on ClickBench `hits` the case it exists for is `URL` and `Referer`, which are the same universe twice.
- The numbers from the tests, and they do not say the same thing about the two forms of sharing. Two columns of 20,000 URLs with three quarters of their values in common are 433,162 bytes encoded independently and 295,585 sharing a dictionary, which is a saving of a third. Two columns of 8,000 URLs from different hosts with no values in common are 196,132 independently and 190,817 sharing a symbol table, which is 2.7 percent. Sharing a dictionary is where the money is on this data and sharing a table is a rounding error next to it, which is worth knowing before any of this is built into a storage engine.
- Splitting the training sample evenly between the columns of a group is wrong and there is a measurement rather than an argument for it. A group of one column of 20,000 values and one of 40 is dominated by the first, and giving the first half the budget costs it more than the second gains: on exactly that pair an even split made the shared table 220,755 bytes against 218,099 for the two columns encoded independently, so sharing lost. The budget is now shared out in proportion to column size with a 2 KB floor, and the same pair comes out at 217,333.
- `dictionary_groups` is the pruning step section 6.4 asks for. It runs on sketches rather than on data, so the 5,460 pairs of a 105 column table cost a Jaccard estimate each rather than a pass over a column, and grouping is transitive because a dictionary is a set union and a chain of overlapping columns still stores fewer values once than three sets store separately. What comes out of it is a candidate list and not a decision, which is why it feeds the size measurement rather than the writer.
- A bottom-k sketch, in `crates/rudb-encoding`. Hash every value in a column and keep the k smallest distinct hashes, which is a uniform sample of the distinct values chosen by a rule that does not depend on the order they arrived in. That one structure answers the three questions every decision in sections 6.4 and 6.5 starts with: how many distinct values a column has, how much two columns overlap, and whether one column is determined by another. The distinct count is within 2 percent at the default k of 4096, which is 32 KB per column, and a sketch that never filled up holds every hash there was and is exact rather than estimated.
- Section 6.5 says HyperLogLog for the distinct count and this is not that, deliberately. HyperLogLog answers the counting question in a kilobyte where this wants tens, and it cannot answer the other two: a register holds a leading zero count rather than a value, so two of them merge into a count of the union but cannot say which values the union kept, and the intersection they give by inclusion and exclusion is the difference of three noisy numbers. Keeping actual hashes makes an intersection a set intersection, so the error is the error on the sample rather than the error on a difference. For 105 columns that is 3 MB for a whole table, against the 5,460 pairs section 6.4 says have to be pruned before a load can test any of them.
- The string column, in `crates/rudb-encoding`. Four shapes, which are CONSTANT, PLAIN, FSST over the raw bytes, and DICT holding the distinct values and an array of codes. `DICT_FSST` from the section 6.2 table is not a fifth shape: a dictionary's entries are a string column, encoding them goes back through the same chooser, and a dictionary whose entries came out FSST compressed is what that produces whenever it is smaller. The same recursion gives run length encoded strings for nothing, because the codes are an integer chunk and the integer cascade already knows what to do with runs.
- The measurements from the tests. A column of 20,000 distinct URLs, 1,342,434 bytes with four byte offsets, comes out at 235,053, and PLAIN on the same column is 1,272,664. A column of 50,000 values over 500 distinct URLs, 3,277,400 bytes, comes out at 51,953 as `DICT(FSST(RLE(...)), DELTA(DICT(...)))`, against 524,272 for FSST on its own and 3,109,101 for PLAIN. Real data will be worse than both because the synthetic corpus is more repetitive than real URLs, which is why the milestone measures `hits` rather than this.
- Lengths are stored rather than offsets. Offsets are a monotonic sequence whose differences are the lengths, and it is the differences that compress, so writing lengths gets to where DELTA would have got without spending a level of the cascade on it. A column of 100,000 fixed width values costs 13 bytes for all of its lengths, and the prefix sum that turns them back into offsets is one add per value.
- The sample the symbol table is trained on is taken at random skips rather than at a fixed stride, and this was not a precaution. The first version took every `n`th value, and on a test column whose period the stride happened to divide it trained a table 3.4 times worse than one trained on the whole column, because it learned eight byte symbols that only line up with the phase it saw and had no shorter symbols left to fall back on. Column data is frequently periodic and a fixed stride aliases with it. The generator is a fixed seed xorshift so the sample is still a function of the column and the same input still encodes to the same bytes.
- Bit packing, in `crates/rudb-encoding`. FOR, DELTA and DICT all end in a packed integer array, so this is the kernel that will run over more bytes than anything else in the system, and it is the first piece of M1 to exist. Packs and unpacks 1024 values at any width from 0 to the width of the type, for `u8`, `u16`, `u32` and `u64`, with a round trip test on every one of those 122 combinations.
- The layout is the FastLanes unified transposed one and not the obvious one. Writing value 0 in the low bits of the first word and value 1 above it means unpacking value `n` needs to know where value `n - 1` ended, which is a dependency chain that a SIMD implementation has to fight with a different shuffle per width. FastLanes sees the 1024 values as a matrix of `T` rows by `1024 / T` lanes and packs down the rows of every lane at once, so every lane runs the same bit schedule with no cross lane movement, and one scalar implementation and one AVX-512 implementation agree bit for bit by construction. It costs nothing in space: a packed vector is `width * 1024` bits either way, and there is a test asserting that.
- Values come out permuted within the vector and that is the price. `spec/06-compression.md` section 6.2 says why it is acceptable, which is that no operator cares what order the rows inside one vector are in, so the permutation is undone only when a vector is materialized in row order. The transpose is therefore a separate function from the pack rather than folded into it, so that data written by the storage layer can stay permuted through a whole pipeline and be reordered once at the end instead of twice per operator.
- FSST, in `crates/rudb-encoding`. A table of at most 255 symbols of one to eight bytes, trained on a sample in five generations the way the paper describes, and compression is replacing the longest matching symbol at each position with its one byte code. The synthetic URL corpus in the tests goes from 41,490 bytes to 7,656, and real URLs will do worse than that because the corpus is more repetitive than real data, which is the point of also measuring on `hits`.
- The reason it is FSST and not a general compressor is not the ratio, and section 6.2 says so. It is that every string is compressed independently against a shared table, so reading row 4,000,000 does not decompress the four million before it, and that a substring search can run against the compressed bytes by compressing the needle with the same table. The second property is what turns `URL LIKE '%google%'` into a scan rather than a decompress and scan, and it is worth more on ClickBench than any ratio improvement. Using it is M3 work, because a greedy match on a needle standing alone can segment it differently from the way the same bytes were segmented inside a longer string, so a hit is a candidate that has to be verified and a miss is not a proof.
- Training is deterministic and there is a test that says so. Two runs over the same sample produce byte identical tables, which they would not if the ranking fell back on hash map iteration order, and a table that differed run to run would make every size in the M1 report unreproducible.
- The single column integer encodings and the cascade over them, in `crates/rudb-encoding`. CONSTANT, frame of reference with bit packing, DELTA, RLE, DICT and SPARSE, each of which encodes its own output by calling back into the chooser, so that RLE over a dictionary over a bit packed code array is something that happens by construction rather than a case somebody wrote out. A million consecutive integers come out as 26 bytes, because the deltas are a constant chunk under the delta.
- The chooser encodes every candidate and keeps the smallest. That is the honest baseline for M1, which is a measurement of what the format can do rather than of how fast a writer can decide, and it is not what a write path can afford. Section 6.3 describes the real thing, which evaluates candidates on a systematic sample rather than on the first N rows. Building the sampler first would mean this milestone measures the sampler and not the format, with no way to tell how much the sampling leaves behind.
- A frame of reference base and a bit width per 1024 values rather than per chunk. A timestamp column over a day spans a range that needs 47 bits and spans a few seconds inside any one unit, which needs 12, and one base per row group would pay the 47 on every value in it.
- There is a second bit packing layout for arrays shorter than a unit. The transposed layout is all or nothing, since a value lives at a row and a lane and the lanes are interleaved through the whole buffer, so a unit holding 3 values costs exactly what a unit holding 1024 costs. Every nested array in a cascade is short, a five entry dictionary or a run length array or an exception list, and storing three numbers in 5 KB is not a compressed format. The tail packer is the sequential layout with the dependency chain the transposed one exists to avoid, which is affordable there and nowhere else, because a tail is at most 1023 values and is decoded once while a full unit is on the hot path of every scan.
- Everything a decoder reads off a disk is checked before it is used. A dictionary code that is not in the dictionary, a negative run length, a chunk that says it holds more values than it decoded to, a truncated buffer at any byte offset, an unknown tag. There is a test that truncating a chunk at every one of its byte offsets produces an error and not a panic, because the bytes come off a disk that has been there longer than the process has.
- A value that does not fit in the width it is being packed at is an error rather than a truncation. This is a private kernel whose caller has always just computed the width from the data, so the check should never fire, and the reason it is there anyway is that the failure it prevents is silent wrong answers in a column of numbers that nothing downstream can distinguish from correct ones.

## 0.1.0

M0 is finished. Its exit criterion was `cargo test` running, `cargo xtask bench` producing a table, and a trivial query executing end to end on all three hosts, and all three clauses now hold: 502 tests green on macOS aarch64, Linux x86_64 and Windows x86_64, a front end table on each of them, and `SELECT * FROM t WHERE x > 5` answering correctly on every one.

This is the first release with a database in it. There is a parser for `SELECT`, a binder, a logical plan with a textual form that reads back into the same plan, a catalog, an in-memory table, the tier 0 kernels and a tier 0 interpreter, and an embedding API over the top of them. What is not here is most of a database: no storage format, no optimizer, no transactions, no `CREATE TABLE`, and every join is a nested loop. Those are M1 and M2 and they are on the milestone issues rather than in a wish list.

The reason to tag it is that a query running end to end is the thing that makes every later number mean something. Until this release there was nothing to measure, and a project aiming at an order of magnitude that cannot yet produce a row is a project whose claims cannot be checked. Now they can be, on the slowest possible implementation, which is exactly where a differential test wants to start.

- `SELECT * FROM t WHERE x > 5` runs end to end. That is the second line of M0's exit criterion and it is the first query this project has ever answered. Text goes to tokens, tokens to a parse tree, the parse tree to a bound plan, the plan to a tree of operators, and the operators to rows, with no step of that pipeline missing and nothing stubbed in the middle of it.
- The compute kernels, in `crates/rudb-kernels`. Casting between every pair of scalar types, the six comparisons plus the two null safe ones, the arithmetic with its overflow checks, three-valued logic, the string functions the binder can already resolve, and the six aggregates. Everything takes vectors and values and knows nothing about plans, operators or catalogs, which is what makes the same function callable from the interpreter, from the fused kernels of tier 1 when they exist, and from a test that wants to check one conversion in isolation.
- The comparison enum here is this crate's own rather than the plan's. `rudb-kernels` is rank 3 and `rudb-plan` is rank 9, so a kernel cannot name a plan type, and the cost of that separation turned out to be two eight line translation functions in the evaluator. That is the layer rule doing exactly what it was put in for: the price of keeping compute independent of representation is visible, small, and in one place.
- Arithmetic that leaves the range of its type is an error and not a wraparound. `2147483647 + 1` over `INTEGER` reports an out of range error the way DuckDB does, rather than producing `-2147483648` and letting it flow into a sum. Rust's release profile wraps silently on overflow, so this is a checked operation per value and it is not free, and it is worth it because the alternative is the class of wrong answer that nothing anywhere reports.
- The tier 0 interpreter, in `crates/rudb-exec`. Pull based, one `next` per operator returning a chunk at a time, with scans, filters, projections, limits, aggregates, sorts, distinct, all eight join kinds, cross products and the three set operations with and without `ALL`. `spec/08-codegen.md` section 8.1 says tier 0 is never removed and never optional because it is the reference every faster tier is differentially tested against, so it is written to be read rather than to be fast, and every place where the fast version is a different algorithm rather than a tuning of this one says so in its own documentation.
- `Schema` is the whole of column resolution. An operator carries the `ColumnBinding` for each of its output columns beside the field, and `Schema::position_of` turns a binding from the plan into an offset into a chunk. Without it every operator would need its own rule for where a column went, and the two places that would disagree first are a join, where the right side's columns start after the left side's, and an aggregate, where the output is the groups then the aggregates and neither is a column of the input.
- Grouping, `DISTINCT` and the set operations share one definition of row identity, in `Key`. SQL's answer to have I seen this row before is not its answer to `=`: two nulls group together, `SELECT DISTINCT` collapses two null rows into one, and `NULL = NULL` is null. Writing the rule three times is how an engine ends up with a `GROUP BY` that produces one group per null row while its `UNION` on the same column produces one row, and there is a test asserting that anything the equality accepts also hashes identically, because a key that hashes apart is a group that is created twice and found never.
- `CASE` is evaluated through selections rather than by evaluating every arm and choosing afterwards. `CASE WHEN s <> 'oops' THEN CAST(s AS INTEGER) ELSE -1 END` has to answer `-1` for the row where `s` is `'oops'`, and the implementation that evaluates both arms over the whole chunk fails that query with a cast error on a row the query excluded. Each arm sees only the rows still undecided when it is reached, and there is a test that would fail against the naive version.
- Sort direction and null placement are two independent decisions. `ORDER BY x DESC NULLS LAST` is not `ORDER BY x NULLS FIRST` reversed, so the comparator applies `reverse` to the value comparison only and never to the null placement, which is what DuckDB does and what the standard says. The sort itself is stable, so `ORDER BY x` on a table with ties hands back the ties in the order they arrived.
- `EXCEPT ALL` and `INTERSECT ALL` are multiset operations and are implemented as such. Three copies of a row minus one copy is two copies, not zero and not three. It is in the standard, DuckDB has it right, and it is the sort of thing an implementation gets wrong once and nobody notices for a year, because nothing in a normal query has duplicates in it. There is a test for each that a set based implementation fails.
- A positional join pads rather than truncates, which is DuckDB's behaviour and is not obvious: joining a table of four rows positionally against one of two gives four rows with nulls in the last two, not two rows.
- Every join is a nested loop, and that is the one place in this crate where the M0 operator is not merely slower than what replaces it but asymptotically worse. The hash join from `spec/07-execution.md` section 7.4 is the single largest performance item in the executor and it is M1 work. Writing the nested loop first is not a shortcut: eight join kinds each have their own rule about what happens to a row with no match, those eight rules fit on a page here where they can be read against the standard, and they do not fit on a page in a hash join with a build side, a probe side, a match bitmap and a spill boundary. The way to find out whether the hash join has them right is to run both and diff.
- The executor's tests are written against the plan's textual form rather than against SQL. A test in `rudb-exec` that says `SELECT count(*) FROM t` is a test of the parser and the binder as much as of the operator, and it breaks when either of those changes for reasons that have nothing to do with the operator it names. `Plan::parse` on the dump is what the round trip format in `spec/04-architecture.md` was for, and this is the first thing to use it for something other than testing itself.
- `Vector::flatten` lost a null behind a dictionary. It read the dictionary's own validity, which says nothing about nulls, because a dictionary keeps them in the vector it points at. `Chunk::select` produces exactly that vector, so a filter over a nullable column followed by anything that flattens turned every null into a zero, which is how it was found: a `LEFT JOIN` with a `WHERE` clause above it padded with `0` instead of `NULL`. It reads the values now.
- The top level API, in `crates/rudb`. `Database::new`, `create_table`, `append`, `query`, `plan` and `value`. `query` takes `&self`, so a query cannot change the database and two of them can run at once with the compiler enforcing that nothing is being written while they do, which is the whole of the concurrency story until `rudb-txn` has one.
- There is no `Connection` type yet and that is deliberate. DuckDB has one because a connection carries a transaction, a set of temporary tables and a prepared statement cache, and none of those three exist in M0. An empty struct added now to look like the shape it will have later is a struct the API can never remove.
- `CREATE TABLE` and `INSERT` are not in the M0 grammar, so `Database::create_table` and `Database::append` are how rows get in. Those are a real part of the API and not a test helper, since an embedded analytical database gets most of its data from the program it is embedded in rather than from a string of SQL, and when the DDL statements do arrive they bind to the same catalog calls these make.
- A result is materialized rather than streamed. A streaming result would have to hold the operator tree, which borrows the plan and the catalog, and that makes a result set a value nobody can put in a struct. The streaming result from `spec/07-execution.md` section 7.5 is M1 and it arrives as a second type beside this one rather than as a change to it, because the overwhelming majority of queries somebody embeds a database to run produce a result that fits in memory, and the API for those should not be the harder one.
- There is still no optimizer. `rudb-opt` is a scaffold, `spec/09-optimizer.md`'s pass sequence is M1 work, and a plan today runs in the shape the binder built it. That is worth stating plainly rather than leaving to be discovered from a slow query: filters are not pushed down, joins are not reordered, and the nested loop join above means a three table query is doing exactly what it looks like it is doing.
- `cargo xtask smoke`, which is M0's exit criterion as a command. The milestone ends with a trivial query executing end to end on all three hosts, so there has to be one thing to run on a host that says whether it worked. It creates a table, runs `SELECT * FROM t WHERE x > 5` and six queries around it that cover each pipeline breaker, and compares every row against what it should be. A wrong answer fails the command rather than printing a table for somebody to read, because a check that needs a human to notice is not a check.
- The binder, in `crates/rudb-bind`. It takes an `Ast` and a `Catalog` and produces a `Plan`, which is the pass that turns what somebody wrote into what it means. `SELECT x FROM t` is a parse tree until something says which table `t` is, which column `x` is and what type it has, and everything after this point works on that answer rather than on the question: the optimizer never resolves a name and the executor never decides a type. It handles `FROM` with cross products, joins, `ON`, `USING`, `NATURAL` and subqueries, `WHERE`, `GROUP BY` including `ALL` and positions and aliases, `HAVING`, the target list with star expansion, `DISTINCT`, `DISTINCT ON`, `ORDER BY` including `ALL` and positions, `LIMIT`, `OFFSET`, and `UNION`, `EXCEPT` and `INTERSECT`.
- The clause order is the operator order and not the written order. Binding goes `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `DISTINCT`, `ORDER BY`, `LIMIT`, which is the order the operators end up in, and that is the reason `WHERE` cannot see an output alias and `HAVING` cannot see a column that was not grouped. Doing it in the order the clauses are written means special casing both of those, and every implementation that has tried it has ended up with a scope stack that nobody can reason about.
- A column that is neither grouped nor aggregated is caught by rewriting rather than by scanning. Target expressions are bound against the input first, aggregate calls are pulled out into the aggregate's list as they are found and replaced by a reference to where their result lands, and then the whole expression is walked once against the group list: a subexpression equal to a group becomes a reference to that group, and a column reference that survives that walk is the error every SQL user has seen. Doing it this way means `SELECT *` in a grouped query, an alias, and a repeated `counter + 1` are all the same code path rather than three, and the comparison is on the bound form, so `counter+1` and `COUNTER + 1` are one group and not two.
- Two identical aggregates are one column. `SELECT sum(x), sum(x) / count(*)` computes one sum, because an aggregate is deduplicated structurally against the ones already found before it is given a position. That is not an optimization that could wait for the optimizer: the aggregate list is the operator's output schema, so a duplicate there is a duplicate hash table probe per row per group for the whole life of the query.
- `ORDER BY` over something that is not selected projects it and then drops it. The sort key has to reference a column of the projection below the sort, so an expression that is sorted on and not selected is appended to that projection, sorted on, and removed by a second projection above the limit. Under `SELECT DISTINCT` that is refused instead, which is the standard's rule and DuckDB's, because the alternative silently changes which rows survive the duplicate elimination.
- Rewrites that happen in the binder rather than later: `BETWEEN` becomes a pair of comparisons, `NOT BETWEEN` a disjunction of two, `IN` a disjunction of equalities and `NOT IN` a conjunction of inequalities, a simple `CASE` becomes the searched one it means with its operand bound once and shared, `IS NULL` and `IS TRUE` and their negations become null safe comparisons, and `AND` and `OR` become one flat conjunction rather than a right leaning tree. Every one of those is a shape the optimizer would otherwise need a case for in every pass that touches either form, and none of them lose information.
- Output column names follow the catalog rather than the query. `SELECT USERID FROM hits` produces a column called `UserID`, because identifiers match without regard to case and the catalog is what holds the case. An expression with no alias gets a name written back out from the bound expression, so `counter * 2` is `(counter * 2)`, which is close to what DuckDB does and is not exactly it, since DuckDB uses the text the user wrote and the tokens are gone by the time the binder runs. That is a recorded compatibility gap and it is a name rather than a result.
- `LogicalType::promote`, in `crates/rudb-common`. This is the rule that decides the type of `a + b`, of a `CASE` with two arms and of a `UNION` column, and it is one function because those three have to agree. Two integers of the same signedness meet at the wider one, a decimal keeps room for both the integral part and the scale up to the 38 digit cap, a date and a timestamp meet at the timestamp, an interval and a timestamp do not meet at all, and `NULL` takes whatever it is next to.
- A signed and an unsigned integer widen rather than reinterpret. `INTEGER` with `UINTEGER` is `BIGINT` and not either of them, because a rank order that picks the unsigned type produces a type that cannot hold the signed one's negative values. It costs four bytes a value on a case that is rare, and the alternative is an answer that is wrong by 4,294,967,296 with nothing anywhere saying so, which is the worst class of bug an engine like this can have.
- The function signature table, in `crates/rudb-functions`. `resolve` takes a name and the types of the arguments and says which function that is, what each argument has to be cast to and what it returns, which is the other thing the binder cannot type an expression without. It is a table of shapes rather than of exact signatures: `+` is one entry saying both arguments promote, not 169 entries one per pair of numeric types. DuckDB needs the latter because it carries an implementation per pair, rudb has no kernel behind any of these yet, and inventing 169 rows before there is a kernel is inventing the wrong 169.
- `sum` accumulates wider than it reads. A `sum` over an `INTEGER` column returns a `HUGEINT` and over a `FLOAT` returns a `DOUBLE`, because the sum of two billion 32 bit values does not fit in 32 bits and an overflow there is a wrong answer on a query that looks entirely ordinary. `count` and `count_star` take anything and return `BIGINT`, and `avg` promotes to `DOUBLE`.
- `-` is one function with an arity of one or two rather than two functions. The transformer does not have to know whether a `-` it just read is a negation or a subtraction before the binder sees it, which is one fewer place for the two to disagree. A negated number literal is folded into a single constant, so `-2147483648` is the `INTEGER` it looks like and not a negation of a `BIGINT`.
- A number literal takes its type from its shape rather than from its value. No point and no exponent is the narrowest of `INTEGER`, `BIGINT` and `HUGEINT` that holds it, a point with no exponent is a `DECIMAL` of exactly the digits written, and an exponent is a `DOUBLE`. That is what makes `0.1 + 0.2` come out as `0.3` here and as something else in an engine that reads a written decimal as a float.
- `Chunk`, in `crates/rudb-vector`. It is the batch every operator hands to the next one and it is the last piece of the vector layer that the executor cannot be written without. A chunk is some columns and a row count, and the row count is a field rather than the length of the first column, because `SELECT count(*) FROM t` scans no columns at all and a chunk of width zero still has to say how many rows it stands for. That is a small decision that is expensive to change later, since every operator that reads `columns[0].len()` is an operator that breaks the day the first aggregate over no columns runs.
- `Chunk::select` wraps rather than compacts. It takes the chunk by value and puts each column behind a dictionary vector over the selection, so a filter that keeps 3 rows in 2,048 copies 3 indices and not 3 rows of payload, which is what `spec/07-execution.md` section 7.1 asks a filter to produce. There is a test asserting the resulting form is a dictionary and not a flat vector, which exists so that a later edit cannot quietly turn the cheap thing back into a copy while every other test still passes.
- `Vector::from_values`, which is the only public way to build a vector out of `Value`s. It was needed the moment there was somewhere to put rows, and the reason it is one function rather than a builder is that a builder would be the second place that has to know which physical type each logical type lands in. A null keeps its slot in the payload rather than being skipped, and there is a test for that specifically, because the version that skips looks correct until there is a null in the middle and then every value after it is one place to the left.
- `MemoryTable`, in `crates/rudb-storage`. This is the M0 answer to where rows live and it is openly not the storage format: no blocks, no row groups, no statistics, no compression and no buffer manager, all of which are what that crate becomes at M2. What it does get right on purpose is the shape of a read, which is by chunk and by column rather than by row. A row at a time interface here would be an interface every operator above grows against, and unwinding that later is the rewrite this project exists to avoid.
- The copy that is left in a scan is named rather than ignored. `MemoryTable::read` clones the columns it was asked for, because a vector owns its buffer and there is nothing to borrow from yet, and its documentation says that borrowed buffers with a pin are the M2 item that stops it. Asking for the columns wanted rather than taking them all is what keeps that copy proportional to the query instead of to the table in the meantime, which is the same reason projection pushdown exists.
- `crates/rudb-catalog` is real: a name, the rule for comparing two of them, a table, and the registry that turns `catalog.schema.table` into one object. Transactional catalog versions, views, constraints and the dependency graph are M4 work and they hang off `Catalog` rather than replacing it. The rows sit behind `Table::rows` precisely so that swapping `MemoryTable` for the storage format is a change to one field.
- Identifier case folding lives at the comparison and nowhere else. DuckDB is case insensitive and case preserving, and the tokenizer work in 0.0.2 established that the parser lowercases nothing at any point, including a quoted identifier, so the folding has to be here and this is also the only place it can be and still hand back the spelling the object was created with. `same_name` is ASCII only, which is what upstream does on this path, and a Unicode aware comparison is a different function with a different cost that is worth writing when there is a test that fails without it.
- The two part name rule is schema first and catalog second. `information_schema.tables` and `memory.hits` both have two parts and mean different things, so a two part name is tried as a schema in the current database before it is tried as a database name, which is the order DuckDB uses. `Catalog::resolve` hands back the name the object was created with rather than the one that was written, so a plan built from it prints the spelling a person would recognise, and when nothing matches it reports the first reading's complaint rather than the last, since that is the one that names the piece the writer most likely got wrong.
- The catalog error text is DuckDB's, because a great deal of code in the wild asserts on it: `Catalog Error: Table with name t does not exist!` and `Catalog Error: Table with name "t" already exists!`. What is missing is the `Did you mean "hits"?` line upstream appends to a missing entry, which needs a similarity search over the catalog and a tie break that matches theirs, and it is recorded as a known compatibility gap rather than left to be discovered.
- The bound logical plan and its textual form, in `crates/rudb-plan`. Twelve operators and eight expression kinds, held in an arena of `u32` references rather than boxes, with a printer and a reader that are a fixed point over it. `spec/04-architecture.md` says every layer has a textual form and a round-trip parser, and this is the first of the four. It is here before the binder and the optimizer on purpose: the format is what a plan test diffs against, and changing it once three layers write it is three layers of test fixtures to redo.
- Every expression carries its type, so `#1.0::VARCHAR` rather than `#1.0`. That is verbose in a dump and it is the whole reason the reader needs nothing but the text: no catalog, no binder and no inference, which means a plan pasted into a bug report reads back into the same plan on a machine that has never seen the database it came from. Constants are then read type first, so `5::INTEGER` and `19723::DATE` and `12.34::DECIMAL(6,2)` are three different values with no self describing literal syntax and no guessing from the digits.
- A date prints as its day number and not as `'2024-01-15'`. A dump is diffed by a machine, the day number is what the executor holds, and a calendar formatter inside a round trip is a second place for a calendar bug to live. `Value`'s own `Display` is still the user facing rendering and this format is not it.
- An aggregate and a scalar function print the same way, and the slot is what tells them apart. `count_star()` in an aggregate list is an aggregate and the same text in a projection is a call to a function of that name. That is real structure rather than a shortcut: an aggregate is legal only as a direct element of `Aggregate`'s aggregate list, which is why that operator has a table index, and `Plan::validate` refuses a plan that puts one anywhere else, so the plan with the other reading cannot be printed in the first place.
- `Plan::validate` is the invariant from `spec/09-optimizer.md` section 9.1, and the reader runs it before it hands a plan back. It is not a type checker and it does not know what any function returns. It knows what this crate can get wrong on its own: an index that points at nothing, an index that points forwards, a projection with more expressions than names, a ragged `VALUES`, a filter on something that is not boolean, a one armed conjunction, and an aggregate outside an aggregate list. Cycles are not detected, they are impossible, because a child index is always smaller than its parent's and building bottom up is the only way to get a reference at all.
- The types the printer emits and the types the reader accepts are held together by a test rather than by care. It walks every scalar type, then a list, an array, a map, a struct and a union of each, prints them, and asserts the reader finds the same end of the text that the printer wrote. That caught `TIME WITH TIME ZONE[]`, where the reader looked for the brackets before the time zone words and stopped eight characters early on a type that is only reachable through a list of times.
- `rudb-plan` depends on `rudb-common` and nothing else now. It was declared against `rudb-vector`, `rudb-ir` and `rudb-catalog` when it was an empty crate, none of which the plan representation turned out to need, and a dependency edge that nothing uses is a build cost and a claim about the layering that is not true.
- `cargo xtask bench` prints a table. This is the last line of M0's exit criterion in `spec/17-milestones.md` and it is deliberately not a benchmark: whole queries against whole engines are `tamnd/rudb-bench`, and this is the smaller question of whether the change you are about to push made the front end slower. Twelve statements, tokenize and match and transform measured separately, the whole text to AST path measured on its own rather than summed from the three, and the median of nine samples with the interquartile range because reporting rule two says never a minimum. `cargo xtask` is an alias for a debug `cargo run`, so the task re-runs itself under the `bench` profile rather than documenting a longer command that people will get wrong, and the discriminator is `debug_assertions` rather than a flag, so there is no way to ask for the number that does not mean anything.
- The first thing it says is that the front end runs at 2.7 MB/s of SQL text, which is about a microsecond a token, and that the matcher is 83 percent of it against 5 percent for the tokenizer and 10 percent for the transformer. 22,142 table nodes are entered for 250 tokens, so 89 steps a token at roughly 10 nanoseconds a step, and steps per token runs from 30 on a set operation to 120 on a `WHERE` clause with three operators in it. None of that is backtracking, it is three separate lookups per node in three separate arrays, which is exactly the thing the rule table layout change is for. Now there is a number to hold it to.
- `parse_ast` tokenized the query twice. It called the tokenizer and then called `parse`, which tokenizes again, so about a tenth of the front end was work already done. It hands the tokens to both halves now. This is the first bug the table found and it was found by the table not adding up.
- The benchmark workload is not the parser's test corpus, and there is a test that says so. The corpus grows every time somebody covers another piece of the grammar, which is what a corpus is for and what makes it useless as a workload, because a total that got bigger because a test was added is indistinguishable from a total that got bigger because the parser got slower. Every case in the workload also has to reach an AST rather than stopping at the parse tree, since the transformer's Not implemented answer is a fast path that does none of the work the transform column claims to be timing.
- The grammar is compiled to a rule table. `cargo xtask gen-grammar` now writes `crates/rudb-parse/src/generated/rules.rs` as well as the keyword table: 1,088 rules in 4,720 nodes, each node twelve bytes with its first token set in a parallel array so the matcher can decline to walk an alternative after reading eight bytes. Two thirds of the work is a meta-parser for the grammar notation, which is the first thing here that reads the vendored files as a language rather than as text to count, and it asserts the shape of what it read against the survey in `spec/20-the-grammar.md` section 20.2 so that an upstream bump which changes the notation fails the build instead of being absorbed.
- Reading the grammar as a graph rather than as a file falsified two more things the specification said, both now corrected in `spec/20-the-grammar.md`. `ReservedKeyword` is one of the 24 matcher overrides and the matcher it is overridden to is the one that does no keyword check at all, so it matches any word rather than the 75 in the reserved list, which reverses what `ColLabel` and `DefArgKeyword` appear to say when you read them. And the claim that the matcher never reaches a character level node is no longer a claim: the generator walks the graph from the two roots, none of the nine character classes or two captures or the single negative lookahead is reachable, `PlainIdentifier` and `QuotedIdentifier` do not appear in the table at all, and one that did appear would fail generation naming the rule.
- The generator refuses a repetition whose body can match the empty string. Upstream's `RepeatMatchProcess` loops while its child succeeds and has no empty match guard, so that shape hangs DuckDB rather than failing it. The nullable analysis that computes the first token sets already knows which bodies those are, so the check is free. The vendored grammar has none, which is the answer we expected and not one worth assuming will stay true.
- The matcher, in `crates/rudb-parse/src/matcher.rs`. It walks the rule table over a token vector and produces a parse tree, and it is the first thing in the repository that turns SQL text into structure. Sixty two statements covering every statement kind M0 has to reach parse today, and the same sixty two produce an identical tree with the first token filter switched off, which is the property that makes the filter safe to keep. There is no Rust recursion in it: the frame stack is a `Vec` with a cap of 262,144 and the cap reports a parser error, because `SELECT ((((...))))` nests as deep as the person typing it and a thread stack answers that with a segfault rather than a message.
- Two facts about the dialect came out of writing it, and both were invisible from the grammar text. A `.` between two names arrives as a number token, because `.5` is a number and the tokenizer cannot know which it has until it has read past the dot, which is why upstream's `NumberLiteralMatcher` carries a rule rejecting a lone dot and why a symbol is matched on its text rather than on its token kind. And `typefunc_keyword_map`, which decides whether a keyword may be a function name, is filled from the `TypeFuncKeyword` rule in the grammar rather than from a sixth keyword list, so the category and the rule are the same union and cannot drift.
- A parse is measured, not asserted to be fast. `Tree::steps` reports how many table nodes the walk went into, a test holds every statement in the corpus under 400 of them per token, and today's numbers are 4,925 steps for a 56 token ClickBench query in 100 microseconds. That is about 20 nanoseconds a step, which is three separate table lookups per node rather than any backtracking: no rule is entered more than 32 times and the parse is already linear in the query. The table layout is the next thing to change and it is a change to the generator, so it is not in this pull request.
- The transformer and the AST, in `crates/rudb-parse/src/transform.rs` and `crates/rudb-parse/src/ast.rs`. This is the boundary between DuckDB's grammar and ours: nothing downstream of it reads a parse tree, because an upstream bump is allowed to rename `BetweenInLikeExpression` and that must not be a rewrite of the binder. The AST is arenas of `u32` indices rather than boxes, so a node is an index and a list of children is a start and a length. `spec/20-the-grammar.md` section 20.14 is what the design decisions were and why.
- Total over the rule table means every rule reaches a defined answer, and a refusal counts. There are 1,088 rules and there is no version of this where each gets a match arm, so the expression chain descends by default: a node with exactly one child is stepped through rather than named, which is what most of the twenty precedence levels are on most queries, and an upstream release that inserts a twenty first level costs nothing. What is ruled out is a panic and a silently dropped clause. Nineteen of the sixty two corpus statements transform today and the other forty three fail with an error naming both the text and the grammar rule, so `SELECT * FROM t TABLESAMPLE 10 PERCENT` says which rule to go and implement instead of quietly returning the whole table.
- A third thing the vendored source falsified, and this one was in the grammar text rather than around it. `OperatorLiteral <- Identifier` reads as though any bare word can be written infix, so `SELECT a foo b` should parse, and it does not. That rule is one of the 24 matcher overrides and the matcher it points at reads a run of operator characters, so `SELECT a <=> b` parses and binds to a function named `<=>` while a word is a syntax error. `SELECT a <-> b` is also an error, for a different reason one layer down: `->` is a special operator the tokenizer checks for before it scans a run.
- The thirty odd grammar rules for a qualified name collapse into one walk rather than thirty match arms. `NestedSchemaTableColumnName` and `CatalogReservedSchemaTableColumnName` and the rest exist because whether a part may be a reserved word depends on how many parts there are, which the matcher has to know and the AST does not, so the transformer collects the leaf tokens in order, unquotes and interns. Field access, method call and subscript become `struct_extract`, an ordinary call and `array_extract`, which is what DuckDB does and keeps three sets of type rules out of the binder.
- `.github/publish-crates.sh` no longer dies on the first attempt when run by hand on a Mac. Nothing is excluded on that attempt, so the exclude array is empty, and bash 3.2 under `set -u` calls an empty array unbound where the runner's bash 5 does not. It only ever fails on a machine that is not the runner, which is exactly the machine it gets run on when the runner is the problem.
- The release checks the shape of the crates.io token rather than asking crates.io about it. The 0.0.2 run failed with a 401 saying the token did not match the format the registry uses, so a check went in that called `/api/v1/me`, and that endpoint is session only and answers 403 to a live token and a dead one alike. There is no read only endpoint that takes an API token, so the check is `cio` and 32 characters, which is what the 401 was complaining about, and publishing stays the only thing that knows whether a well formed token is live.

Known gap: the differential harness in `tamnd/rudb-compat` can run a query against two engines and compare result sets, and nothing in this release has been run through it against a real DuckDB. Every claim here about matching DuckDB's behaviour, meaning the null placement in a sort, the multiset semantics of `EXCEPT ALL`, the padding in a positional join and the catalog error text, comes from reading the documentation and the source rather than from a diff against a running instance. That is the first thing M1 fixes and it is the reason the harness was built before the engine.

## 0.0.2

Still no database and still no query. What this release settles is where the SQL dialect comes from, and the answer is that it comes from DuckDB rather than from us reading DuckDB. The grammar is vendored verbatim and everything derived from it is generated, so a bump is a diff to read rather than a transcription to redo. The other thing it settles is that every byte the engine will ever write goes through one place, which is a week of work now and a rewrite later.

- The I/O interception shim, `rudb-io`, from `spec/16-testing.md` section 16.5. Every read, write, fsync, rename and truncate goes through one interface, with two implementations behind it: `RealFilesystem` is `std::fs` with positional reads and writes, and `SimFilesystem` is memory that records everything, can be told to fail at a chosen point, and can reorder writes that were not separated by an fsync. It is here rather than at M6, where the crash tests that drive it live, because retrofitting interception into a storage layer written without it means rewriting the storage layer.
- DuckDB's PEG grammar is vendored, at `crates/rudb-parse/grammar`. In v2.0 DuckDB replaced its bison parser with a PEG parser whose grammar ships as 61 KB of declarative text with no semantic actions in it, MIT licensed, and that text is the definition of the dialect this project claims compatibility with. Vendoring it removes 1,086 chances to reject valid DuckDB SQL by hand, and removes them again on every upstream release. `cargo xtask vendor-grammar` is the only thing that writes there, `cargo xtask grammar` fails the build if anything else did, and a nightly job reopens the question when upstream moves. `spec/20-the-grammar.md` is the argument, the measurements, and the three places fidelity still leaks.
- The tokenizer, in `rudb-parse`. It is a port of DuckDB's `base_tokenizer.cpp` rather than an interpretation of it, because the grammar says nothing about string literals, dollar quoting, numeric literal forms, comments or the operator rules, and all of that is 613 lines of hand written C++ with no declarative artifact behind it. Nine states, nine token kinds, twelve bytes a token, no allocation and no decoding. Reading the source rather than the documentation falsified two things `spec/20-the-grammar.md` had said about it, both now corrected: DuckDB does not fold identifier case at any point, including for quoted identifiers, and `SELECT 1e` is one number token rather than `1` aliased `e`.
- `cargo xtask gen-grammar`, which writes the keyword table out of the vendored grammar, and runs in the gate with `--check` so the checked in table and the grammar cannot drift apart. The table is 514 words rather than the 499 in the five class lists, because 15 more are spelled by a rule and are in no class at all. Those get a mask of zero, which makes them matchable as a literal and transparent everywhere else, so `ORDER BY x ASCENDING` works without `SELECT ascending FROM t` becoming a syntax error.
- `cargo xtask grammar` asks git whether the vendored files are tracked and not only whether they are on disk. The checksums are taken from the working directory, so a vendored file that an ignore rule keeps out of the repository is green on the machine that fetched it and missing on every clone of it. That is not a hypothetical: `*.duckdb` was written for database files and also matched `LICENSE.duckdb`, which is upstream's license sitting next to upstream's grammar.
- The crates.io upload no longer waits for the binary matrix. It waits for the gate, which is the part that decides whether the tag deserves to be a release at all. What the registry gets is source, and `cargo publish` compiles and verifies each crate itself on a Linux runner, so a cross build for a host nobody installs from cargo on cannot make that upload more correct. It can stop it happening: the first 0.0.2 run had both macOS jobs sit unassigned in GitHub's hosted queue for over half an hour with every other job green and 27 crates waiting behind them.
- `spec/04-architecture.md` section 4.5 said hand-written recursive descent and that we start where DuckDB ended up minus the generator. Where they ended up is the generator, so that is corrected. Error recovery moves off the query path in the same edit: a PEG matcher that resynchronizes past an error accepts strings DuckDB rejects, so the strict parse is what a query gets and recovery is a second entry point over the same rule table for tooling.

Known gap: everything about the tokenizer is checked against a careful reading of one C++ file, because the differential harness that would check it against a running DuckDB is still an open box on M0. Three claims in the specification were wrong for exactly that reason and were only caught by reading the source. The harness is next.

## 0.0.1

The skeleton and the two interfaces underneath everything else. There is no database here. You cannot run a query. The point of tagging it is that the apparatus which measures the database exists before the database does, and that the two widest interfaces in the system are settled before there is anything built on top of them to make changing them expensive.

- The workspace: 26 library crates and the `rudb` shell, each with an assigned rank in `xtask/layers.toml`. A crate may depend only on crates of strictly lower rank, and `cargo xtask layers` enforces it as a required CI job rather than as a convention.
- `rudb-common`: the error model, the type system and the single value. Errors map to DuckDB's exact message prefixes and a `Result` is the same width as the value in it. Every DuckDB logical type is present, prints the way DuckDB prints it, and parses back from that spelling with the aliases handled. Values print the way DuckDB prints them, which is mostly a long tail of small things like a double printing as `1` and not `1.0`.
- `rudb-vector`: the vector interface. Four physical forms, flat, constant, sequence and dictionary. Validity in three cases rather than a bitmap that happens to be all ones. Selection vectors instead of compaction. The 16 byte string view with the 4 byte prefix. Specified in `spec/07-execution.md` section 7.1 as the widest interface in the system, which is why it is written before the first operator instead of after the fifth.
- `cargo xtask style`, which checks the prose rules in CONTRIBUTING.md over every markdown file: no em or en dashes, no horizontal rules, no sentence broken across two lines.
- `cargo xtask msrv`, which builds the workspace against the oldest Rust the manifest claims. A language feature newer than the floor does not announce itself, it just compiles on whatever toolchain is installed, so this is the only check that finds one.
- `cargo xtask ci`, which runs what the per-commit gate runs, in the order it runs it, so a contributor finds out on their own machine rather than on a pull request. Twice now the local gate has turned out to be weaker than the remote one, and both times the fix was to close the gap here rather than to remember harder.
- The shell's argument handling. `rudb --version` and `rudb --print-config` work and nothing else does, which the help text says plainly.
- CI on Linux, macOS and Windows, debug and release, with a minimum supported Rust version job that reads its floor from `Cargo.toml`, a reproducible build check, and `cargo deny` over licenses, advisories, banned crates and unknown registries.
- The specification, twenty documents, in `spec/`. Written before the code on purpose.

Known deviation from the specification: `StringView` stores a block index and an offset where section 7.1 says pointer. Same size, same prefix trick, no pinning machinery required, and tracked as issue #16 so that M3 measures the two instead of inheriting whichever was written first.
