# Changelog

Notable changes, newest first. This project is pre-1.0 and follows no compatibility promise until it has one, per `spec/18-package-layout.md`. The storage format version is stated in every release, because a file outlives the build that wrote it.

The version number says how far through the plan we are. **The minor version is the number of milestones finished**, so 0.0.y is work inside M0, 0.1.0 is the release where M0's exit criterion passed, 0.1.y is work inside M1, and so on. Patch releases happen whenever enough has landed to be worth a tag, which in practice is every few pull requests. The one exception is at the end: when M10 closes the version is 1.0.0 rather than 0.11.0, because that milestone is named 1.0 and pretending otherwise would be silly. The milestones are the issues at https://github.com/tamnd/rudb/issues.

## Unreleased

- Bit packing, in `crates/rudb-encoding`. FOR, DELTA and DICT all end in a packed integer array, so this is the kernel that will run over more bytes than anything else in the system, and it is the first piece of M1 to exist. Packs and unpacks 1024 values at any width from 0 to the width of the type, for `u8`, `u16`, `u32` and `u64`, with a round trip test on every one of those 122 combinations.
- The layout is the FastLanes unified transposed one and not the obvious one. Writing value 0 in the low bits of the first word and value 1 above it means unpacking value `n` needs to know where value `n - 1` ended, which is a dependency chain that a SIMD implementation has to fight with a different shuffle per width. FastLanes sees the 1024 values as a matrix of `T` rows by `1024 / T` lanes and packs down the rows of every lane at once, so every lane runs the same bit schedule with no cross lane movement, and one scalar implementation and one AVX-512 implementation agree bit for bit by construction. It costs nothing in space: a packed vector is `width * 1024` bits either way, and there is a test asserting that.
- Values come out permuted within the vector and that is the price. `spec/06-compression.md` section 6.2 says why it is acceptable, which is that no operator cares what order the rows inside one vector are in, so the permutation is undone only when a vector is materialized in row order. The transpose is therefore a separate function from the pack rather than folded into it, so that data written by the storage layer can stay permuted through a whole pipeline and be reordered once at the end instead of twice per operator.
- A value that does not fit in the width it is being packed at is an error rather than a truncation. This is a private kernel whose caller has always just computed the width from the data, so the check should never fire, and the reason it is there anyway is that the failure it prevents is silent wrong answers in a column of numbers that nothing downstream can distinguish from correct ones.

## 0.1.0

M0 is finished. Its exit criterion was `cargo test` running, `cargo xtask bench` producing a table, and a trivial query executing end to end on all three hosts, and all three clauses now hold: 502 tests green on macOS aarch64, Linux x86_64 and Windows x86_64, a front end table on each of them, and `SELECT * FROM t WHERE x > 5` answering correctly on every one.

This is the first release with a database in it. There is a parser for `SELECT`, a binder, a logical plan with a textual form that reads back into the same plan, a catalog, an in-memory table, the tier 0 kernels and a tier 0 interpreter, and an embedding API over the top of them. What is not here is most of a database: no storage format, no optimizer, no transactions, no `CREATE TABLE`, and every join is a nested loop. Those are M1 and M2 and they are on the milestone issues rather than in a wish list.

The reason to tag it is that a query running end to end is the thing that makes every later number mean something. Until this release there was nothing to measure, and a project aiming at an order of magnitude that cannot yet produce a row is a project whose claims cannot be checked. Now they can be, on the slowest possible implementation, which is exactly where a differential test wants to start.

- `SELECT * FROM t WHERE x > 5` runs end to end. That is the second line of M0's exit criterion and it is the first query this project has ever answered. Text goes to tokens, tokens to a parse tree, the parse tree to a bound plan, the plan to a tree of operators, and the operators to rows, with no step of that pipeline missing and nothing stubbed in the middle of it.
- The compute kernels, in `crates/rudb-kernels`. Casting between every pair of scalar types, the six comparisons plus the two null safe ones, the arithmetic with its overflow checks, three-valued logic, the string functions the binder can already resolve, and the six aggregates. Everything takes vectors and values and knows nothing about plans, operators or catalogs, which is what makes the same function callable from the interpreter, from the fused kernels of tier 1 when they exist, and from a test that wants to check one conversion in isolation.
- The comparison enum here is this crate's own rather than the plan's. `rudb-kernels` is rank 3 and `rudb-plan` is rank 9, so a kernel cannot name a plan type, and the cost of that separation turned out to be two eight line translation functions in the evaluator. That is the layer rule doing exactly what it was put in for: the price of keeping compute independent of representation is visible, small, and in one place.
- Arithmetic that leaves the range of its type is an error and not a wraparound. `2147483647 + 1` over `INTEGER` reports an out of range error the way DuckDB does, rather than producing `-2147483648` and letting it flow into a sum. Rust's release profile wraps silently on overflow, so this is a checked operation per value and it is not free, and it is worth it because the alternative is the class of wrong answer that nothing anywhere reports.
- The tier 0 interpreter, in `crates/rudb-exec`. Pull based, one `next` per operator returning a chunk at a time, with scans, filters, projections, limits, aggregates, sorts, distinct, all eight join kinds, cross products and the three set operations with and without `ALL`. `spec/08-codegen.md` section 8.1 says tier 0 is never removed and never optional because it is the reference every faster tier is differentially tested against, so it is written to be read rather than to be fast, and every place where the fast version is a different algorithm rather than a tuning of this one says so in its own documentation.
- `Schema` is the whole of column resolution. An operator carries the `ColumnBinding` for each of its output columns beside the field, and `Schema::position_of` turns a binding from the plan into an offset into a chunk. Without it every operator would need its own rule for where a column went, and the two places that would disagree first are a join, where the right side's columns start after the left side's, and an aggregate, where the output is the groups then the aggregates and neither is a column of the input.
- Grouping, `DISTINCT` and the set operations share one definition of row identity, in `Key`. SQL's answer to have I seen this row before is not its answer to `=`: two nulls group together, `SELECT DISTINCT` collapses two null rows into one, and `NULL = NULL` is null. Writing the rule three times is how an engine ends up with a `GROUP BY` that produces one group per null row while its `UNION` on the same column produces one row, and there is a test asserting that anything the equality accepts also hashes identically, because a key that hashes apart is a group that is created twice and found never.
- `CASE` is evaluated through selections rather than by evaluating every arm and choosing afterwards. `CASE WHEN s <> 'oops' THEN CAST(s AS INTEGER) ELSE -1 END` has to answer `-1` for the row where `s` is `'oops'`, and the implementation that evaluates both arms over the whole chunk fails that query with a cast error on a row the query excluded. Each arm sees only the rows still undecided when it is reached, and there is a test that would fail against the naive version.
- Sort direction and null placement are two independent decisions. `ORDER BY x DESC NULLS LAST` is not `ORDER BY x NULLS FIRST` reversed, so the comparator applies `reverse` to the value comparison only and never to the null placement, which is what DuckDB does and what the standard says. The sort itself is stable, so `ORDER BY x` on a table with ties hands back the ties in the order they arrived.
- `EXCEPT ALL` and `INTERSECT ALL` are multiset operations and are implemented as such. Three copies of a row minus one copy is two copies, not zero and not three. It is in the standard, DuckDB has it right, and it is the sort of thing an implementation gets wrong once and nobody notices for a year, because nothing in a normal query has duplicates in it. There is a test for each that a set based implementation fails.
- A positional join pads rather than truncates, which is DuckDB's behaviour and is not obvious: joining a table of four rows positionally against one of two gives four rows with nulls in the last two, not two rows.
- Every join is a nested loop, and that is the one place in this crate where the M0 operator is not merely slower than what replaces it but asymptotically worse. The hash join from `spec/07-execution.md` section 7.4 is the single largest performance item in the executor and it is M1 work. Writing the nested loop first is not a shortcut: eight join kinds each have their own rule about what happens to a row with no match, those eight rules fit on a page here where they can be read against the standard, and they do not fit on a page in a hash join with a build side, a probe side, a match bitmap and a spill boundary. The way to find out whether the hash join has them right is to run both and diff.
- The executor's tests are written against the plan's textual form rather than against SQL. A test in `rudb-exec` that says `SELECT count(*) FROM t` is a test of the parser and the binder as much as of the operator, and it breaks when either of those changes for reasons that have nothing to do with the operator it names. `Plan::parse` on the dump is what the round trip format in `spec/04-architecture.md` was for, and this is the first thing to use it for something other than testing itself.
- `Vector::flatten` lost a null behind a dictionary. It read the dictionary's own validity, which says nothing about nulls, because a dictionary keeps them in the vector it points at. `Chunk::select` produces exactly that vector, so a filter over a nullable column followed by anything that flattens turned every null into a zero, which is how it was found: a `LEFT JOIN` with a `WHERE` clause above it padded with `0` instead of `NULL`. It reads the values now.
- The top level API, in `crates/rudb`. `Database::new`, `create_table`, `append`, `query`, `plan` and `value`. `query` takes `&self`, so a query cannot change the database and two of them can run at once with the compiler enforcing that nothing is being written while they do, which is the whole of the concurrency story until `rudb-txn` has one.
- There is no `Connection` type yet and that is deliberate. DuckDB has one because a connection carries a transaction, a set of temporary tables and a prepared statement cache, and none of those three exist in M0. An empty struct added now to look like the shape it will have later is a struct the API can never remove.
- `CREATE TABLE` and `INSERT` are not in the M0 grammar, so `Database::create_table` and `Database::append` are how rows get in. Those are a real part of the API and not a test helper, since an embedded analytical database gets most of its data from the program it is embedded in rather than from a string of SQL, and when the DDL statements do arrive they bind to the same catalog calls these make.
- A result is materialized rather than streamed. A streaming result would have to hold the operator tree, which borrows the plan and the catalog, and that makes a result set a value nobody can put in a struct. The streaming result from `spec/07-execution.md` section 7.5 is M1 and it arrives as a second type beside this one rather than as a change to it, because the overwhelming majority of queries somebody embeds a database to run produce a result that fits in memory, and the API for those should not be the harder one.
- There is still no optimizer. `rudb-opt` is a scaffold, `spec/09-optimizer.md`'s pass sequence is M1 work, and a plan today runs in the shape the binder built it. That is worth stating plainly rather than leaving to be discovered from a slow query: filters are not pushed down, joins are not reordered, and the nested loop join above means a three table query is doing exactly what it looks like it is doing.
- `cargo xtask smoke`, which is M0's exit criterion as a command. The milestone ends with a trivial query executing end to end on all three hosts, so there has to be one thing to run on a host that says whether it worked. It creates a table, runs `SELECT * FROM t WHERE x > 5` and six queries around it that cover each pipeline breaker, and compares every row against what it should be. A wrong answer fails the command rather than printing a table for somebody to read, because a check that needs a human to notice is not a check.
- The binder, in `crates/rudb-bind`. It takes an `Ast` and a `Catalog` and produces a `Plan`, which is the pass that turns what somebody wrote into what it means. `SELECT x FROM t` is a parse tree until something says which table `t` is, which column `x` is and what type it has, and everything after this point works on that answer rather than on the question: the optimizer never resolves a name and the executor never decides a type. It handles `FROM` with cross products, joins, `ON`, `USING`, `NATURAL` and subqueries, `WHERE`, `GROUP BY` including `ALL` and positions and aliases, `HAVING`, the target list with star expansion, `DISTINCT`, `DISTINCT ON`, `ORDER BY` including `ALL` and positions, `LIMIT`, `OFFSET`, and `UNION`, `EXCEPT` and `INTERSECT`.
- The clause order is the operator order and not the written order. Binding goes `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `DISTINCT`, `ORDER BY`, `LIMIT`, which is the order the operators end up in, and that is the reason `WHERE` cannot see an output alias and `HAVING` cannot see a column that was not grouped. Doing it in the order the clauses are written means special casing both of those, and every implementation that has tried it has ended up with a scope stack that nobody can reason about.
- A column that is neither grouped nor aggregated is caught by rewriting rather than by scanning. Target expressions are bound against the input first, aggregate calls are pulled out into the aggregate's list as they are found and replaced by a reference to where their result lands, and then the whole expression is walked once against the group list: a subexpression equal to a group becomes a reference to that group, and a column reference that survives that walk is the error every SQL user has seen. Doing it this way means `SELECT *` in a grouped query, an alias, and a repeated `counter + 1` are all the same code path rather than three, and the comparison is on the bound form, so `counter+1` and `COUNTER + 1` are one group and not two.
- Two identical aggregates are one column. `SELECT sum(x), sum(x) / count(*)` computes one sum, because an aggregate is deduplicated structurally against the ones already found before it is given a position. That is not an optimization that could wait for the optimizer: the aggregate list is the operator's output schema, so a duplicate there is a duplicate hash table probe per row per group for the whole life of the query.
- `ORDER BY` over something that is not selected projects it and then drops it. The sort key has to reference a column of the projection below the sort, so an expression that is sorted on and not selected is appended to that projection, sorted on, and removed by a second projection above the limit. Under `SELECT DISTINCT` that is refused instead, which is the standard's rule and DuckDB's, because the alternative silently changes which rows survive the duplicate elimination.
- Rewrites that happen in the binder rather than later: `BETWEEN` becomes a pair of comparisons, `NOT BETWEEN` a disjunction of two, `IN` a disjunction of equalities and `NOT IN` a conjunction of inequalities, a simple `CASE` becomes the searched one it means with its operand bound once and shared, `IS NULL` and `IS TRUE` and their negations become null safe comparisons, and `AND` and `OR` become one flat conjunction rather than a right leaning tree. Every one of those is a shape the optimizer would otherwise need a case for in every pass that touches either form, and none of them lose information.
- Output column names follow the catalog rather than the query. `SELECT USERID FROM hits` produces a column called `UserID`, because identifiers match without regard to case and the catalog is what holds the case. An expression with no alias gets a name written back out from the bound expression, so `counter * 2` is `(counter * 2)`, which is close to what DuckDB does and is not exactly it, since DuckDB uses the text the user wrote and the tokens are gone by the time the binder runs. That is a recorded compatibility gap and it is a name rather than a result.
- `LogicalType::promote`, in `crates/rudb-common`. This is the rule that decides the type of `a + b`, of a `CASE` with two arms and of a `UNION` column, and it is one function because those three have to agree. Two integers of the same signedness meet at the wider one, a decimal keeps room for both the integral part and the scale up to the 38 digit cap, a date and a timestamp meet at the timestamp, an interval and a timestamp do not meet at all, and `NULL` takes whatever it is next to.
- A signed and an unsigned integer widen rather than reinterpret. `INTEGER` with `UINTEGER` is `BIGINT` and not either of them, because a rank order that picks the unsigned type produces a type that cannot hold the signed one's negative values. It costs four bytes a value on a case that is rare, and the alternative is an answer that is wrong by 4,294,967,296 with nothing anywhere saying so, which is the worst class of bug an engine like this can have.
- The function signature table, in `crates/rudb-functions`. `resolve` takes a name and the types of the arguments and says which function that is, what each argument has to be cast to and what it returns, which is the other thing the binder cannot type an expression without. It is a table of shapes rather than of exact signatures: `+` is one entry saying both arguments promote, not 169 entries one per pair of numeric types. DuckDB needs the latter because it carries an implementation per pair, rudb has no kernel behind any of these yet, and inventing 169 rows before there is a kernel is inventing the wrong 169.
- `sum` accumulates wider than it reads. A `sum` over an `INTEGER` column returns a `HUGEINT` and over a `FLOAT` returns a `DOUBLE`, because the sum of two billion 32 bit values does not fit in 32 bits and an overflow there is a wrong answer on a query that looks entirely ordinary. `count` and `count_star` take anything and return `BIGINT`, and `avg` promotes to `DOUBLE`.
- `-` is one function with an arity of one or two rather than two functions. The transformer does not have to know whether a `-` it just read is a negation or a subtraction before the binder sees it, which is one fewer place for the two to disagree. A negated number literal is folded into a single constant, so `-2147483648` is the `INTEGER` it looks like and not a negation of a `BIGINT`.
- A number literal takes its type from its shape rather than from its value. No point and no exponent is the narrowest of `INTEGER`, `BIGINT` and `HUGEINT` that holds it, a point with no exponent is a `DECIMAL` of exactly the digits written, and an exponent is a `DOUBLE`. That is what makes `0.1 + 0.2` come out as `0.3` here and as something else in an engine that reads a written decimal as a float.
- `Chunk`, in `crates/rudb-vector`. It is the batch every operator hands to the next one and it is the last piece of the vector layer that the executor cannot be written without. A chunk is some columns and a row count, and the row count is a field rather than the length of the first column, because `SELECT count(*) FROM t` scans no columns at all and a chunk of width zero still has to say how many rows it stands for. That is a small decision that is expensive to change later, since every operator that reads `columns[0].len()` is an operator that breaks the day the first aggregate over no columns runs.
- `Chunk::select` wraps rather than compacts. It takes the chunk by value and puts each column behind a dictionary vector over the selection, so a filter that keeps 3 rows in 2,048 copies 3 indices and not 3 rows of payload, which is what `spec/07-execution.md` section 7.1 asks a filter to produce. There is a test asserting the resulting form is a dictionary and not a flat vector, which exists so that a later edit cannot quietly turn the cheap thing back into a copy while every other test still passes.
- `Vector::from_values`, which is the only public way to build a vector out of `Value`s. It was needed the moment there was somewhere to put rows, and the reason it is one function rather than a builder is that a builder would be the second place that has to know which physical type each logical type lands in. A null keeps its slot in the payload rather than being skipped, and there is a test for that specifically, because the version that skips looks correct until there is a null in the middle and then every value after it is one place to the left.
- `MemoryTable`, in `crates/rudb-storage`. This is the M0 answer to where rows live and it is openly not the storage format: no blocks, no row groups, no statistics, no compression and no buffer manager, all of which are what that crate becomes at M2. What it does get right on purpose is the shape of a read, which is by chunk and by column rather than by row. A row at a time interface here would be an interface every operator above grows against, and unwinding that later is the rewrite this project exists to avoid.
- The copy that is left in a scan is named rather than ignored. `MemoryTable::read` clones the columns it was asked for, because a vector owns its buffer and there is nothing to borrow from yet, and its documentation says that borrowed buffers with a pin are the M2 item that stops it. Asking for the columns wanted rather than taking them all is what keeps that copy proportional to the query instead of to the table in the meantime, which is the same reason projection pushdown exists.
- `crates/rudb-catalog` is real: a name, the rule for comparing two of them, a table, and the registry that turns `catalog.schema.table` into one object. Transactional catalog versions, views, constraints and the dependency graph are M4 work and they hang off `Catalog` rather than replacing it. The rows sit behind `Table::rows` precisely so that swapping `MemoryTable` for the storage format is a change to one field.
- Identifier case folding lives at the comparison and nowhere else. DuckDB is case insensitive and case preserving, and the tokenizer work in 0.0.2 established that the parser lowercases nothing at any point, including a quoted identifier, so the folding has to be here and this is also the only place it can be and still hand back the spelling the object was created with. `same_name` is ASCII only, which is what upstream does on this path, and a Unicode aware comparison is a different function with a different cost that is worth writing when there is a test that fails without it.
- The two part name rule is schema first and catalog second. `information_schema.tables` and `memory.hits` both have two parts and mean different things, so a two part name is tried as a schema in the current database before it is tried as a database name, which is the order DuckDB uses. `Catalog::resolve` hands back the name the object was created with rather than the one that was written, so a plan built from it prints the spelling a person would recognise, and when nothing matches it reports the first reading's complaint rather than the last, since that is the one that names the piece the writer most likely got wrong.
- The catalog error text is DuckDB's, because a great deal of code in the wild asserts on it: `Catalog Error: Table with name t does not exist!` and `Catalog Error: Table with name "t" already exists!`. What is missing is the `Did you mean "hits"?` line upstream appends to a missing entry, which needs a similarity search over the catalog and a tie break that matches theirs, and it is recorded as a known compatibility gap rather than left to be discovered.
- The bound logical plan and its textual form, in `crates/rudb-plan`. Twelve operators and eight expression kinds, held in an arena of `u32` references rather than boxes, with a printer and a reader that are a fixed point over it. `spec/04-architecture.md` says every layer has a textual form and a round-trip parser, and this is the first of the four. It is here before the binder and the optimizer on purpose: the format is what a plan test diffs against, and changing it once three layers write it is three layers of test fixtures to redo.
- Every expression carries its type, so `#1.0::VARCHAR` rather than `#1.0`. That is verbose in a dump and it is the whole reason the reader needs nothing but the text: no catalog, no binder and no inference, which means a plan pasted into a bug report reads back into the same plan on a machine that has never seen the database it came from. Constants are then read type first, so `5::INTEGER` and `19723::DATE` and `12.34::DECIMAL(6,2)` are three different values with no self describing literal syntax and no guessing from the digits.
- A date prints as its day number and not as `'2024-01-15'`. A dump is diffed by a machine, the day number is what the executor holds, and a calendar formatter inside a round trip is a second place for a calendar bug to live. `Value`'s own `Display` is still the user facing rendering and this format is not it.
- An aggregate and a scalar function print the same way, and the slot is what tells them apart. `count_star()` in an aggregate list is an aggregate and the same text in a projection is a call to a function of that name. That is real structure rather than a shortcut: an aggregate is legal only as a direct element of `Aggregate`'s aggregate list, which is why that operator has a table index, and `Plan::validate` refuses a plan that puts one anywhere else, so the plan with the other reading cannot be printed in the first place.
- `Plan::validate` is the invariant from `spec/09-optimizer.md` section 9.1, and the reader runs it before it hands a plan back. It is not a type checker and it does not know what any function returns. It knows what this crate can get wrong on its own: an index that points at nothing, an index that points forwards, a projection with more expressions than names, a ragged `VALUES`, a filter on something that is not boolean, a one armed conjunction, and an aggregate outside an aggregate list. Cycles are not detected, they are impossible, because a child index is always smaller than its parent's and building bottom up is the only way to get a reference at all.
- The types the printer emits and the types the reader accepts are held together by a test rather than by care. It walks every scalar type, then a list, an array, a map, a struct and a union of each, prints them, and asserts the reader finds the same end of the text that the printer wrote. That caught `TIME WITH TIME ZONE[]`, where the reader looked for the brackets before the time zone words and stopped eight characters early on a type that is only reachable through a list of times.
- `rudb-plan` depends on `rudb-common` and nothing else now. It was declared against `rudb-vector`, `rudb-ir` and `rudb-catalog` when it was an empty crate, none of which the plan representation turned out to need, and a dependency edge that nothing uses is a build cost and a claim about the layering that is not true.
- `cargo xtask bench` prints a table. This is the last line of M0's exit criterion in `spec/17-milestones.md` and it is deliberately not a benchmark: whole queries against whole engines are `tamnd/rudb-bench`, and this is the smaller question of whether the change you are about to push made the front end slower. Twelve statements, tokenize and match and transform measured separately, the whole text to AST path measured on its own rather than summed from the three, and the median of nine samples with the interquartile range because reporting rule two says never a minimum. `cargo xtask` is an alias for a debug `cargo run`, so the task re-runs itself under the `bench` profile rather than documenting a longer command that people will get wrong, and the discriminator is `debug_assertions` rather than a flag, so there is no way to ask for the number that does not mean anything.
- The first thing it says is that the front end runs at 2.7 MB/s of SQL text, which is about a microsecond a token, and that the matcher is 83 percent of it against 5 percent for the tokenizer and 10 percent for the transformer. 22,142 table nodes are entered for 250 tokens, so 89 steps a token at roughly 10 nanoseconds a step, and steps per token runs from 30 on a set operation to 120 on a `WHERE` clause with three operators in it. None of that is backtracking, it is three separate lookups per node in three separate arrays, which is exactly the thing the rule table layout change is for. Now there is a number to hold it to.
- `parse_ast` tokenized the query twice. It called the tokenizer and then called `parse`, which tokenizes again, so about a tenth of the front end was work already done. It hands the tokens to both halves now. This is the first bug the table found and it was found by the table not adding up.
- The benchmark workload is not the parser's test corpus, and there is a test that says so. The corpus grows every time somebody covers another piece of the grammar, which is what a corpus is for and what makes it useless as a workload, because a total that got bigger because a test was added is indistinguishable from a total that got bigger because the parser got slower. Every case in the workload also has to reach an AST rather than stopping at the parse tree, since the transformer's Not implemented answer is a fast path that does none of the work the transform column claims to be timing.
- The grammar is compiled to a rule table. `cargo xtask gen-grammar` now writes `crates/rudb-parse/src/generated/rules.rs` as well as the keyword table: 1,088 rules in 4,720 nodes, each node twelve bytes with its first token set in a parallel array so the matcher can decline to walk an alternative after reading eight bytes. Two thirds of the work is a meta-parser for the grammar notation, which is the first thing here that reads the vendored files as a language rather than as text to count, and it asserts the shape of what it read against the survey in `spec/20-the-grammar.md` section 20.2 so that an upstream bump which changes the notation fails the build instead of being absorbed.
- Reading the grammar as a graph rather than as a file falsified two more things the specification said, both now corrected in `spec/20-the-grammar.md`. `ReservedKeyword` is one of the 24 matcher overrides and the matcher it is overridden to is the one that does no keyword check at all, so it matches any word rather than the 75 in the reserved list, which reverses what `ColLabel` and `DefArgKeyword` appear to say when you read them. And the claim that the matcher never reaches a character level node is no longer a claim: the generator walks the graph from the two roots, none of the nine character classes or two captures or the single negative lookahead is reachable, `PlainIdentifier` and `QuotedIdentifier` do not appear in the table at all, and one that did appear would fail generation naming the rule.
- The generator refuses a repetition whose body can match the empty string. Upstream's `RepeatMatchProcess` loops while its child succeeds and has no empty match guard, so that shape hangs DuckDB rather than failing it. The nullable analysis that computes the first token sets already knows which bodies those are, so the check is free. The vendored grammar has none, which is the answer we expected and not one worth assuming will stay true.
- The matcher, in `crates/rudb-parse/src/matcher.rs`. It walks the rule table over a token vector and produces a parse tree, and it is the first thing in the repository that turns SQL text into structure. Sixty two statements covering every statement kind M0 has to reach parse today, and the same sixty two produce an identical tree with the first token filter switched off, which is the property that makes the filter safe to keep. There is no Rust recursion in it: the frame stack is a `Vec` with a cap of 262,144 and the cap reports a parser error, because `SELECT ((((...))))` nests as deep as the person typing it and a thread stack answers that with a segfault rather than a message.
- Two facts about the dialect came out of writing it, and both were invisible from the grammar text. A `.` between two names arrives as a number token, because `.5` is a number and the tokenizer cannot know which it has until it has read past the dot, which is why upstream's `NumberLiteralMatcher` carries a rule rejecting a lone dot and why a symbol is matched on its text rather than on its token kind. And `typefunc_keyword_map`, which decides whether a keyword may be a function name, is filled from the `TypeFuncKeyword` rule in the grammar rather than from a sixth keyword list, so the category and the rule are the same union and cannot drift.
- A parse is measured, not asserted to be fast. `Tree::steps` reports how many table nodes the walk went into, a test holds every statement in the corpus under 400 of them per token, and today's numbers are 4,925 steps for a 56 token ClickBench query in 100 microseconds. That is about 20 nanoseconds a step, which is three separate table lookups per node rather than any backtracking: no rule is entered more than 32 times and the parse is already linear in the query. The table layout is the next thing to change and it is a change to the generator, so it is not in this pull request.
- The transformer and the AST, in `crates/rudb-parse/src/transform.rs` and `crates/rudb-parse/src/ast.rs`. This is the boundary between DuckDB's grammar and ours: nothing downstream of it reads a parse tree, because an upstream bump is allowed to rename `BetweenInLikeExpression` and that must not be a rewrite of the binder. The AST is arenas of `u32` indices rather than boxes, so a node is an index and a list of children is a start and a length. `spec/20-the-grammar.md` section 20.14 is what the design decisions were and why.
- Total over the rule table means every rule reaches a defined answer, and a refusal counts. There are 1,088 rules and there is no version of this where each gets a match arm, so the expression chain descends by default: a node with exactly one child is stepped through rather than named, which is what most of the twenty precedence levels are on most queries, and an upstream release that inserts a twenty first level costs nothing. What is ruled out is a panic and a silently dropped clause. Nineteen of the sixty two corpus statements transform today and the other forty three fail with an error naming both the text and the grammar rule, so `SELECT * FROM t TABLESAMPLE 10 PERCENT` says which rule to go and implement instead of quietly returning the whole table.
- A third thing the vendored source falsified, and this one was in the grammar text rather than around it. `OperatorLiteral <- Identifier` reads as though any bare word can be written infix, so `SELECT a foo b` should parse, and it does not. That rule is one of the 24 matcher overrides and the matcher it points at reads a run of operator characters, so `SELECT a <=> b` parses and binds to a function named `<=>` while a word is a syntax error. `SELECT a <-> b` is also an error, for a different reason one layer down: `->` is a special operator the tokenizer checks for before it scans a run.
- The thirty odd grammar rules for a qualified name collapse into one walk rather than thirty match arms. `NestedSchemaTableColumnName` and `CatalogReservedSchemaTableColumnName` and the rest exist because whether a part may be a reserved word depends on how many parts there are, which the matcher has to know and the AST does not, so the transformer collects the leaf tokens in order, unquotes and interns. Field access, method call and subscript become `struct_extract`, an ordinary call and `array_extract`, which is what DuckDB does and keeps three sets of type rules out of the binder.
- `.github/publish-crates.sh` no longer dies on the first attempt when run by hand on a Mac. Nothing is excluded on that attempt, so the exclude array is empty, and bash 3.2 under `set -u` calls an empty array unbound where the runner's bash 5 does not. It only ever fails on a machine that is not the runner, which is exactly the machine it gets run on when the runner is the problem.
- The release checks the shape of the crates.io token rather than asking crates.io about it. The 0.0.2 run failed with a 401 saying the token did not match the format the registry uses, so a check went in that called `/api/v1/me`, and that endpoint is session only and answers 403 to a live token and a dead one alike. There is no read only endpoint that takes an API token, so the check is `cio` and 32 characters, which is what the 401 was complaining about, and publishing stays the only thing that knows whether a well formed token is live.

Known gap: the differential harness in `tamnd/rudb-compat` can run a query against two engines and compare result sets, and nothing in this release has been run through it against a real DuckDB. Every claim here about matching DuckDB's behaviour, meaning the null placement in a sort, the multiset semantics of `EXCEPT ALL`, the padding in a positional join and the catalog error text, comes from reading the documentation and the source rather than from a diff against a running instance. That is the first thing M1 fixes and it is the reason the harness was built before the engine.

## 0.0.2

Still no database and still no query. What this release settles is where the SQL dialect comes from, and the answer is that it comes from DuckDB rather than from us reading DuckDB. The grammar is vendored verbatim and everything derived from it is generated, so a bump is a diff to read rather than a transcription to redo. The other thing it settles is that every byte the engine will ever write goes through one place, which is a week of work now and a rewrite later.

- The I/O interception shim, `rudb-io`, from `spec/16-testing.md` section 16.5. Every read, write, fsync, rename and truncate goes through one interface, with two implementations behind it: `RealFilesystem` is `std::fs` with positional reads and writes, and `SimFilesystem` is memory that records everything, can be told to fail at a chosen point, and can reorder writes that were not separated by an fsync. It is here rather than at M6, where the crash tests that drive it live, because retrofitting interception into a storage layer written without it means rewriting the storage layer.
- DuckDB's PEG grammar is vendored, at `crates/rudb-parse/grammar`. In v2.0 DuckDB replaced its bison parser with a PEG parser whose grammar ships as 61 KB of declarative text with no semantic actions in it, MIT licensed, and that text is the definition of the dialect this project claims compatibility with. Vendoring it removes 1,086 chances to reject valid DuckDB SQL by hand, and removes them again on every upstream release. `cargo xtask vendor-grammar` is the only thing that writes there, `cargo xtask grammar` fails the build if anything else did, and a nightly job reopens the question when upstream moves. `spec/20-the-grammar.md` is the argument, the measurements, and the three places fidelity still leaks.
- The tokenizer, in `rudb-parse`. It is a port of DuckDB's `base_tokenizer.cpp` rather than an interpretation of it, because the grammar says nothing about string literals, dollar quoting, numeric literal forms, comments or the operator rules, and all of that is 613 lines of hand written C++ with no declarative artifact behind it. Nine states, nine token kinds, twelve bytes a token, no allocation and no decoding. Reading the source rather than the documentation falsified two things `spec/20-the-grammar.md` had said about it, both now corrected: DuckDB does not fold identifier case at any point, including for quoted identifiers, and `SELECT 1e` is one number token rather than `1` aliased `e`.
- `cargo xtask gen-grammar`, which writes the keyword table out of the vendored grammar, and runs in the gate with `--check` so the checked in table and the grammar cannot drift apart. The table is 514 words rather than the 499 in the five class lists, because 15 more are spelled by a rule and are in no class at all. Those get a mask of zero, which makes them matchable as a literal and transparent everywhere else, so `ORDER BY x ASCENDING` works without `SELECT ascending FROM t` becoming a syntax error.
- `cargo xtask grammar` asks git whether the vendored files are tracked and not only whether they are on disk. The checksums are taken from the working directory, so a vendored file that an ignore rule keeps out of the repository is green on the machine that fetched it and missing on every clone of it. That is not a hypothetical: `*.duckdb` was written for database files and also matched `LICENSE.duckdb`, which is upstream's license sitting next to upstream's grammar.
- The crates.io upload no longer waits for the binary matrix. It waits for the gate, which is the part that decides whether the tag deserves to be a release at all. What the registry gets is source, and `cargo publish` compiles and verifies each crate itself on a Linux runner, so a cross build for a host nobody installs from cargo on cannot make that upload more correct. It can stop it happening: the first 0.0.2 run had both macOS jobs sit unassigned in GitHub's hosted queue for over half an hour with every other job green and 27 crates waiting behind them.
- `spec/04-architecture.md` section 4.5 said hand-written recursive descent and that we start where DuckDB ended up minus the generator. Where they ended up is the generator, so that is corrected. Error recovery moves off the query path in the same edit: a PEG matcher that resynchronizes past an error accepts strings DuckDB rejects, so the strict parse is what a query gets and recovery is a second entry point over the same rule table for tooling.

Known gap: everything about the tokenizer is checked against a careful reading of one C++ file, because the differential harness that would check it against a running DuckDB is still an open box on M0. Three claims in the specification were wrong for exactly that reason and were only caught by reading the source. The harness is next.

## 0.0.1

The skeleton and the two interfaces underneath everything else. There is no database here. You cannot run a query. The point of tagging it is that the apparatus which measures the database exists before the database does, and that the two widest interfaces in the system are settled before there is anything built on top of them to make changing them expensive.

- The workspace: 26 library crates and the `rudb` shell, each with an assigned rank in `xtask/layers.toml`. A crate may depend only on crates of strictly lower rank, and `cargo xtask layers` enforces it as a required CI job rather than as a convention.
- `rudb-common`: the error model, the type system and the single value. Errors map to DuckDB's exact message prefixes and a `Result` is the same width as the value in it. Every DuckDB logical type is present, prints the way DuckDB prints it, and parses back from that spelling with the aliases handled. Values print the way DuckDB prints them, which is mostly a long tail of small things like a double printing as `1` and not `1.0`.
- `rudb-vector`: the vector interface. Four physical forms, flat, constant, sequence and dictionary. Validity in three cases rather than a bitmap that happens to be all ones. Selection vectors instead of compaction. The 16 byte string view with the 4 byte prefix. Specified in `spec/07-execution.md` section 7.1 as the widest interface in the system, which is why it is written before the first operator instead of after the fifth.
- `cargo xtask style`, which checks the prose rules in CONTRIBUTING.md over every markdown file: no em or en dashes, no horizontal rules, no sentence broken across two lines.
- `cargo xtask msrv`, which builds the workspace against the oldest Rust the manifest claims. A language feature newer than the floor does not announce itself, it just compiles on whatever toolchain is installed, so this is the only check that finds one.
- `cargo xtask ci`, which runs what the per-commit gate runs, in the order it runs it, so a contributor finds out on their own machine rather than on a pull request. Twice now the local gate has turned out to be weaker than the remote one, and both times the fix was to close the gap here rather than to remember harder.
- The shell's argument handling. `rudb --version` and `rudb --print-config` work and nothing else does, which the help text says plainly.
- CI on Linux, macOS and Windows, debug and release, with a minimum supported Rust version job that reads its floor from `Cargo.toml`, a reproducible build check, and `cargo deny` over licenses, advisories, banned crates and unknown registries.
- The specification, twenty documents, in `spec/`. Written before the code on purpose.

Known deviation from the specification: `StringView` stores a block index and an offset where section 7.1 says pointer. Same size, same prefix trick, no pinning machinery required, and tracked as issue #16 so that M3 measures the two instead of inheriting whichever was written first.
