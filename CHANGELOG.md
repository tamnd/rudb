# Changelog

Notable changes, newest first. This project is pre-1.0 and follows no compatibility promise until it has one, per `spec/18-package-layout.md`. The storage format version is stated in every release, because a file outlives the build that wrote it.

The version number says how far through the plan we are. **The minor version is the number of milestones finished**, so 0.0.y is work inside M0, 0.1.0 is the release where M0's exit criterion passed, 0.1.y is work inside M1, and so on. Patch releases happen whenever enough has landed to be worth a tag, which in practice is every few pull requests. The one exception is at the end: when M10 closes the version is 1.0.0 rather than 0.11.0, because that milestone is named 1.0 and pretending otherwise would be silly. The milestones are the issues at https://github.com/tamnd/rudb/issues.

## Unreleased

- `cargo xtask bench` prints a table. This is the last line of M0's exit criterion in `spec/17-milestones.md` and it is deliberately not a benchmark: whole queries against whole engines are `tamnd/rudb-bench`, and this is the smaller question of whether the change you are about to push made the front end slower. Twelve statements, tokenize and match and transform measured separately, the whole text to AST path measured on its own rather than summed from the three, and the median of nine samples with the interquartile range because reporting rule two says never a minimum. `cargo xtask` is an alias for a debug `cargo run`, so the task re-runs itself under the `bench` profile rather than documenting a longer command that people will get wrong, and the discriminator is `debug_assertions` rather than a flag, so there is no way to ask for the number that does not mean anything.
- The first thing it says is that the front end runs at 2.7 MB/s of SQL text, which is about a microsecond a token, and that the matcher is 83 percent of it against 5 percent for the tokenizer and 10 percent for the transformer. 22,142 table nodes are entered for 250 tokens, so 89 steps a token at roughly 10 nanoseconds a step, and steps per token runs from 30 on a set operation to 120 on a `WHERE` clause with three operators in it. None of that is backtracking, it is three separate lookups per node in three separate arrays, which is exactly the thing the rule table layout change is for. Now there is a number to hold it to.
- `parse_ast` tokenized the query twice. It called the tokenizer and then called `parse`, which tokenizes again, so about a tenth of the front end was work already done. It hands the tokens to both halves now. This is the first bug the table found and it was found by the table not adding up.
- The benchmark workload is not the parser's test corpus, and there is a test that says so. The corpus grows every time somebody covers another piece of the grammar, which is what a corpus is for and what makes it useless as a workload, because a total that got bigger because a test was added is indistinguishable from a total that got bigger because the parser got slower. Every case in the workload also has to reach an AST rather than stopping at the parse tree, since the transformer's Not implemented answer is a fast path that does none of the work the transform column claims to be timing.
- The grammar is compiled to a rule table. `cargo xtask gen-grammar` now writes `crates/rudb-parse/src/generated/rules.rs` as well as the keyword table: 1,088 rules in 4,720 nodes, each node twelve bytes with its first token set in a parallel array so the matcher can decline to walk an alternative after reading eight bytes. Two thirds of the work is a meta-parser for the grammar notation, which is the first thing here that reads the vendored files as a language rather than as text to count, and it asserts the shape of what it read against the survey in `spec/20-the-grammar.md` section 20.2 so that an upstream bump which changes the notation fails the build instead of being absorbed.
- Reading the grammar as a graph rather than as a file falsified two more things the specification said, both now corrected in `spec/20-the-grammar.md`. `ReservedKeyword` is one of the 24 matcher overrides and the matcher it is overridden to is the one that does no keyword check at all, so it matches any word rather than the 75 in the reserved list, which reverses what `ColLabel` and `DefArgKeyword` appear to say when you read them. And the claim that the matcher never reaches a character level node is no longer a claim: the generator walks the graph from the two roots, none of the nine character classes or two captures or the single negative lookahead is reachable, `PlainIdentifier` and `QuotedIdentifier` do not appear in the table at all, and one that did appear would fail generation naming the rule.
- The generator refuses a repetition whose body can match the empty string. Upstream's `RepeatMatchProcess` loops while its child succeeds and has no empty match guard, so that shape hangs DuckDB rather than failing it. The nullable analysis that computes the first token sets already knows which bodies those are, so the check is free. The vendored grammar has none, which is the answer we expected and not one worth assuming will stay true.
- The matcher, in `crates/rudb-parse/src/matcher.rs`. It walks the rule table over a token vector and produces a parse tree, and it is the first thing in the repository that turns SQL text into structure. Sixty two statements covering every statement kind M0 has to reach parse today, and the same sixty two produce an identical tree with the first token filter switched off, which is the property that makes the filter safe to keep. There is no Rust recursion in it: the frame stack is a `Vec` with a cap of 262,144 and the cap reports a parser error, because `SELECT ((((...))))` nests as deep as the person typing it and a thread stack answers that with a segfault rather than a message.
- Two facts about the dialect came out of writing it, and both were invisible from the grammar text. A `.` between two names arrives as a number token, because `.5` is a number and the tokenizer cannot know which it has until it has read past the dot, which is why upstream's `NumberLiteralMatcher` carries a rule rejecting a lone dot and why a symbol is matched on its text rather than on its token kind. And `typefunc_keyword_map`, which decides whether a keyword may be a function name, is filled from the `TypeFuncKeyword` rule in the grammar rather than from a sixth keyword list, so the category and the rule are the same union and cannot drift.
- A parse is measured, not asserted to be fast. `Tree::steps` reports how many table nodes the walk went into, a test holds every statement in the corpus under 400 of them per token, and today's numbers are 4,925 steps for a 56 token ClickBench query in 100 microseconds. That is about 20 nanoseconds a step, which is three separate table lookups per node rather than any backtracking: no rule is entered more than 32 times and the parse is already linear in the query. The table layout is the next thing to change and it is a change to the generator, so it is not in this pull request.
- The transformer and the AST, in `crates/rudb-parse/src/transform.rs` and `crates/rudb-parse/src/ast.rs`. This is the boundary between DuckDB's grammar and ours: nothing downstream of it reads a parse tree, because an upstream bump is allowed to rename `BetweenInLikeExpression` and that must not be a rewrite of the binder. The AST is arenas of `u32` indices rather than boxes, so a node is an index and a list of children is a start and a length. `spec/20-the-grammar.md` section 20.14 is what the design decisions were and why.
- Total over the rule table means every rule reaches a defined answer, and a refusal counts. There are 1,088 rules and there is no version of this where each gets a match arm, so the expression chain descends by default: a node with exactly one child is stepped through rather than named, which is what most of the twenty precedence levels are on most queries, and an upstream release that inserts a twenty first level costs nothing. What is ruled out is a panic and a silently dropped clause. Nineteen of the sixty two corpus statements transform today and the other forty three fail with an error naming both the text and the grammar rule, so `SELECT * FROM t TABLESAMPLE 10 PERCENT` says which rule to go and implement instead of quietly returning the whole table.
- A third thing the vendored source falsified, and this one was in the grammar text rather than around it. `OperatorLiteral <- Identifier` reads as though any bare word can be written infix, so `SELECT a foo b` should parse, and it does not. That rule is one of the 24 matcher overrides and the matcher it points at reads a run of operator characters, so `SELECT a <=> b` parses and binds to a function named `<=>` while a word is a syntax error. `SELECT a <-> b` is also an error, for a different reason one layer down: `->` is a special operator the tokenizer checks for before it scans a run.
- The thirty odd grammar rules for a qualified name collapse into one walk rather than thirty match arms. `NestedSchemaTableColumnName` and `CatalogReservedSchemaTableColumnName` and the rest exist because whether a part may be a reserved word depends on how many parts there are, which the matcher has to know and the AST does not, so the transformer collects the leaf tokens in order, unquotes and interns. Field access, method call and subscript become `struct_extract`, an ordinary call and `array_extract`, which is what DuckDB does and keeps three sets of type rules out of the binder.
- `.github/publish-crates.sh` no longer dies on the first attempt when run by hand on a Mac. Nothing is excluded on that attempt, so the exclude array is empty, and bash 3.2 under `set -u` calls an empty array unbound where the runner's bash 5 does not. It only ever fails on a machine that is not the runner, which is exactly the machine it gets run on when the runner is the problem.
- The release checks the shape of the crates.io token rather than asking crates.io about it. The 0.0.2 run failed with a 401 saying the token did not match the format the registry uses, so a check went in that called `/api/v1/me`, and that endpoint is session only and answers 403 to a live token and a dead one alike. There is no read only endpoint that takes an API token, so the check is `cio` and 32 characters, which is what the 401 was complaining about, and publishing stays the only thing that knows whether a well formed token is live.

## 0.0.2

Still no database and still no query. What this release settles is where the SQL dialect comes from, and the answer is that it comes from DuckDB rather than from us reading DuckDB. The grammar is vendored verbatim and everything derived from it is generated, so a bump is a diff to read rather than a transcription to redo. The other thing it settles is that every byte the engine will ever write goes through one place, which is a week of work now and a rewrite later.

- The I/O interception shim, `rudb-io`, from `spec/16-testing.md` section 16.5. Every read, write, fsync, rename and truncate goes through one interface, with two implementations behind it: `RealFilesystem` is `std::fs` with positional reads and writes, and `SimFilesystem` is memory that records everything, can be told to fail at a chosen point, and can reorder writes that were not separated by an fsync. It is here rather than at M6, where the crash tests that drive it live, because retrofitting interception into a storage layer written without it means rewriting the storage layer.
- DuckDB's PEG grammar is vendored, at `crates/rudb-parse/grammar`. In v2.0 DuckDB replaced its bison parser with a PEG parser whose grammar ships as 61 KB of declarative text with no semantic actions in it, MIT licensed, and that text is the definition of the dialect this project claims compatibility with. Vendoring it removes 1,086 chances to reject valid DuckDB SQL by hand, and removes them again on every upstream release. `cargo xtask vendor-grammar` is the only thing that writes there, `cargo xtask grammar` fails the build if anything else did, and a nightly job reopens the question when upstream moves. `spec/20-the-grammar.md` is the argument, the measurements, and the three places fidelity still leaks.
- The tokenizer, in `rudb-parse`. It is a port of DuckDB's `base_tokenizer.cpp` rather than an interpretation of it, because the grammar says nothing about string literals, dollar quoting, numeric literal forms, comments or the operator rules, and all of that is 613 lines of hand written C++ with no declarative artifact behind it. Nine states, nine token kinds, twelve bytes a token, no allocation and no decoding. Reading the source rather than the documentation falsified two things `spec/20-the-grammar.md` had said about it, both now corrected: DuckDB does not fold identifier case at any point, including for quoted identifiers, and `SELECT 1e` is one number token rather than `1` aliased `e`.
- `cargo xtask gen-grammar`, which writes the keyword table out of the vendored grammar, and runs in the gate with `--check` so the checked in table and the grammar cannot drift apart. The table is 514 words rather than the 499 in the five class lists, because 15 more are spelled by a rule and are in no class at all. Those get a mask of zero, which makes them matchable as a literal and transparent everywhere else, so `ORDER BY x ASCENDING` works without `SELECT ascending FROM t` becoming a syntax error.
- `cargo xtask grammar` asks git whether the vendored files are tracked and not only whether they are on disk. The checksums are taken from the working directory, so a vendored file that an ignore rule keeps out of the repository is green on the machine that fetched it and missing on every clone of it. That is not a hypothetical: `*.duckdb` was written for database files and also matched `LICENSE.duckdb`, which is upstream's license sitting next to upstream's grammar.
- The crates.io upload no longer waits for the binary matrix. It waits for the gate, which is the part that decides whether the tag deserves to be a release at all. What the registry gets is source, and `cargo publish` compiles and verifies each crate itself on a Linux runner, so a cross build for a host nobody installs from cargo on cannot make that upload more correct. It can stop it happening: the first 0.0.2 run had both macOS jobs sit unassigned in GitHub's hosted queue for over half an hour with every other job green and 27 crates waiting behind them.
- `spec/04-architecture.md` section 4.5 said hand-written recursive descent and that we start where DuckDB ended up minus the generator. Where they ended up is the generator, so that is corrected. Error recovery moves off the query path in the same edit: a PEG matcher that resynchronizes past an error accepts strings DuckDB rejects, so the strict parse is what a query gets and recovery is a second entry point over the same rule table for tooling.

Known gap: everything about the tokenizer is checked against a careful reading of one C++ file, because the differential harness that would check it against a running DuckDB is still an open box on M0. Three claims in the specification were wrong for exactly that reason and were only caught by reading the source. The harness is next.

Storage format version: none written yet.

## 0.0.1

The skeleton and the two interfaces underneath everything else. There is no database here. You cannot run a query. The point of tagging it is that the apparatus which measures the database exists before the database does, and that the two widest interfaces in the system are settled before there is anything built on top of them to make changing them expensive.

- The workspace: 26 library crates and the `rudb` shell, each with an assigned rank in `xtask/layers.toml`. A crate may depend only on crates of strictly lower rank, and `cargo xtask layers` enforces it as a required CI job rather than as a convention.
- `rudb-common`: the error model, the type system and the single value. Errors map to DuckDB's exact message prefixes and a `Result` is the same width as the value in it. Every DuckDB logical type is present, prints the way DuckDB prints it, and parses back from that spelling with the aliases handled. Values print the way DuckDB prints them, which is mostly a long tail of small things like a double printing as `1` and not `1.0`.
- `rudb-vector`: the vector interface. Four physical forms, flat, constant, sequence and dictionary. Validity in three cases rather than a bitmap that happens to be all ones. Selection vectors instead of compaction. The 16 byte string view with the 4 byte prefix. Specified in `spec/07-execution.md` section 7.1 as the widest interface in the system, which is why it is written before the first operator instead of after the fifth.
- `cargo xtask style`, which checks the prose rules in CONTRIBUTING.md over every markdown file: no em or en dashes, no horizontal rules, no sentence broken across two lines.
- `cargo xtask msrv`, which builds the workspace against the oldest Rust the manifest claims. A language feature newer than the floor does not announce itself, it just compiles on whatever toolchain is installed, so this is the only check that finds one.
- `cargo xtask ci`, which runs what the per-commit gate runs, in the order it runs it, so a contributor finds out on their own machine rather than on a pull request. Twice now the local gate has turned out to be weaker than the remote one, and both times the fix was to close the gap here rather than to remember harder.
- The shell's argument handling. `rudb --version` and `rudb --print-config` work and nothing else does, which the help text says plainly.
- CI on Linux, macOS and Windows, debug and release, with a minimum supported Rust version job that reads its floor from `Cargo.toml`, a reproducible build check, and `cargo deny` over licenses, advisories, banned crates and unknown registries.
- The specification, twenty documents, in `spec/`. Written before the code on purpose.

Known deviation from the specification: `StringView` stores a block index and an offset where section 7.1 says pointer. Same size, same prefix trick, no pinning machinery required, and tracked as issue #16 so that M3 measures the two instead of inheriting whichever was written first.

Storage format version: none written yet.
