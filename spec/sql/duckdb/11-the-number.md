# The number

The title of this folder says 100 percent. This document is what that would have to mean before anyone is allowed to say it.

## 11.1 Nobody else publishes one, and the reason is instructive

Every project in this space that claims compatibility with another engine publishes a list of differences rather than a percentage. CockroachDB documents its PostgreSQL differences as a page of named behaviours, including that integer division returns a decimal and that float overflow returns infinity. pg_duckdb documents the places where DuckDB's defaults differ from PostgreSQL's, such as null ordering, and it overrides them. Redshift documents that constraints parse and are not enforced, which is a feature that is present, accepted, and does nothing.

That last one is the shape of the problem. A percentage over a feature list counts a constraint that parses and is ignored the same as one that works. Section 1.2's rule exists because of exactly that, and a rule like that only survives if the number it governs is computed rather than asserted.

The most honest thing anybody in this field ships is not a percentage at all. Babelfish comes with Compass, a tool that scans the SQL Server workload you actually have and reports what fraction of it Babelfish supports. The denominator is your queries. That is the right idea and it is the idea behind the weighted corpus in section 9.2, and it is why document 12 puts building that corpus first.

So: we publish numbers, plural, each with a named denominator, each computed by the harness on a named pin, and we never publish a single headline percentage. A project that reduces this to one number has chosen marketing over measurement, and the number that results is the one nobody can defend in the one conversation where it matters, which is a user asking whether their workload runs.

## 11.2 What the page says

One page, generated by `rudb-compat report`, never edited by hand.

The three level two denominators from section 1.1: statement coverage over 36, function coverage weighted and unweighted over 1159, and corpus pass rate over the upstream suite with the skip count beside it.

The five error levels from section 8.2, each over the count of records where the pinned binary errored.

The skip counts by reason from section 9.3, split into harness gaps and real gaps, because a harness gap in that column is a promise to ourselves rather than a statement about rudb.

The nine failure reasons with counts, because the shape of the failures says more than the pass rate. Fifty thousand `NotImplemented` and fifty `WrongAnswer` is a healthy young engine. The reverse is a crisis, at the same pass rate.

The three resource ratios from section 9.7, rudb over DuckDB on time, CPU seconds and peak resident set, as medians with the interquartile range, at three granularities: the whole corpus, per feature, and the worst twenty records. The worst twenty is the column that gets read, because an engine that is fast on average and two hundred times slower on one shape has a bug rather than a distribution.

Provenance on every one: the rudb commit, the rudb-compat commit, the DuckDB commit and binary hash, the corpus commit, the machine and the seed. Section 9.8 called a percentage without those a rumour and this is where that bites. The resource numbers need it more than the correctness numbers do, because a ratio from a shared machine is not a ratio, which is why server3 is excluded from producing them.

## 11.2.1 The provenance is in, and the seed row is what it took to say properly

The six fields are gathered and written, in `rudb-compat/src/report.rs`, and the corpus page and the function sweep have carried them for a while. The seed row is the one that took work, because five of the six are facts about the machine and the seed is a fact about the run, and for most of that time nothing in the harness generated anything so the row said so.

There are four generated modes now, and as of tamnd/rudb-compat#79 each of them prints the six fields and appends a row to `target/report/generated.tsv`. What goes in the seed row is the command that reproduces the run rather than the bare number, and that is not decoration. A grammar run is a seed and a count and a rule, a TLP run is a seed and a count and a form, and a sqlsmith run is a seed and a count and which build of the extension wrote the queries. A reader given only the seed has to work the rest out, and a reader given the command line can paste it. It is built out of the values the run used rather than written down beside them, so it cannot drift from them, and it gives `--count` and `--seed` even when both were defaults, because a default is a thing that changes and a recorded command should keep working after it does.

One series for all four modes with a mode column, rather than one file each. The three columns that mean the same thing in all four are how many cases were generated, how many said anything at all, and how many of those came out wrong, and the question a series exists to answer is whether generated testing found more this month than last. Four files would make somebody open four of them to answer it. What the modes disagree about is what a case is and what wrong means, and that is what the mode column is for.

## 11.2.2 The three ratios are on the page, carried rather than computed

They are on it as of tamnd/rudb-compat#80, at the three granularities section 11.2 asks for, and the run that writes the page does not compute any of them. That is not a shortcut and it is not going to change. The sqllogictest corpus this page comes out of cannot produce a ratio at all, because a record there only means anything under a session that replayed every record before it, so timing one record would time the replay. The ratios come off the benchmark corpus instead, where every file carries its own load and one query and nothing in it depends on the file before it, and `rudb-compat cost` writes what it found down beside the pages for `rudb-compat report` to read back.

That makes two numbers on this page carried from another run, function coverage being the first, and it is the right arrangement rather than a compromise. A cost run is four measurements per benchmark and five processes per engine per measurement, and it took thirty five minutes on server2 with two thirds of the corpus refused or skipped. A corpus run is minutes and goes on every commit. A page that computed everything on it would either be a page nobody runs or a page with older numbers on it that did not say they were older.

Both carried numbers say when and where they were measured and whether that was the same engine build on the same machine as the corpus numbers above them. That sentence earns more on the ratios than on the sweep. A pass rate from another build is a fact about another build, which is bad enough and is at least a fact. A ratio whose two sides came off different hardware is not a ratio, because the divisor is about the other machine, and that is the whole reason section 11.2 keeps server3 out of producing them.

The file is several rows per run rather than one. Three granularities in one row would mean a column per suite and a column count that moved with the corpus, so a scope column says whether a row is the whole corpus, a suite or a single benchmark, and the rows of a run are read back together by the stamp and the machine they share. The provenance fields repeat on every row, which is denormalised on purpose: the alternative is a row whose meaning depends on another row somewhere above it, and one row of a file like this should say what it is a measurement of on its own.

A run narrowed with `--count` or `--group` is not recorded, and neither is a run against a DuckDB that is not the pin. Both print everything they found and say they were not written down. That is the rule the function sweep already followed and it is section 1.2 applied to a measurement rather than to a feature: a ratio over eleven benchmarks somebody picked is a useful thing to look at and it is not the number the page is about.

What the first recorded run says, on server2 against the pin at `cc7e7bac7f` with rudb at `4561d0da`: over the thirty four benchmarks both engines answer, 0.48 on wall clock, 1.54 on processor time and 0.30 on peak resident set. Ahead on the clock and behind on the meter is an engine taking its speed from cores rather than from work, which is the case three ratios exist to catch and which a report publishing elapsed time alone would have written up as twice as fast. The worst single benchmark is a range join at two hundred times the elapsed time and eight hundred times the processor time, against an engine that has a range join operator where rudb has a nested loop. The median is 0.48 and section 11.6 wants 0.1, so the distance is a factor of five across the corpus as well as two orders of magnitude on the joins.

## 11.3 The weighted function number, exactly

For each of the 1159 distinct names in `duckdb_functions()` on the pin, the weight is the number of records in the real query corpus that call it, counted from a real parse and not a text search. Coverage is the sum of weights over implemented names divided by the sum over all names.

A name is implemented when every overload row for it passes the signature driven differential in section 10.1 on the current run. Not when it appears in our function table. Not when a pull request said so. The distinction is the whole of section 1.2 and putting it in the definition is what makes it automatic.

The unweighted number is printed next to it, always, at the same size. The weighted one flatters us because real queries use `sum` and `count` and `upper`, and a number that only flatters is not a measurement.

Names with weight zero are reported as a third figure: how much of the surface nobody in the corpus has ever called. That number is interesting on its own, because it is the honest estimate of how much of DuckDB's function table exists for completeness rather than for use, and it is the thing that decides whether the last fifteen percent of this project is worth doing at all.

## 11.4 The page is allowed to go down

Three ways, all legitimate, and each has to be visible on the page rather than smoothed over.

**A function falls out.** The generator in 10.1 finds a boundary input where an implemented function disagrees, and the name stops counting until it is fixed. This should happen often, especially early, and every occurrence is the system working.

**The corpus grows.** Adding real queries adds weight to names we do not have. A denominator that only ever shrinks is a denominator somebody is managing.

**The pin moves.** Upstream adds functions, changes behaviour, or renames something. Section 11.5.

A published number that has never gone down in a year is evidence about the publisher, not about the engine.

## 11.5 When the pin moves

The pin is in three places that move together: the vendored grammar under `crates/rudb-parse/grammar/` with its sha256 manifest, the DuckDB binary the harness runs, and the upstream corpus `vendor` fetches. Moving one without the others produces numbers that mean nothing.

The policy: when upstream releases, re vendor all three in one change, and publish the numbers at both pins for one release. That separates "the number moved because upstream changed" from "the number moved because we did", which is the only question anybody reading the page actually has. It also catches the case where upstream changed a behaviour we were matching, which arrives as a batch of new `WrongAnswer` records against code nobody touched and is otherwise extremely confusing.

## 11.6 The resource ratios are allowed to go down too, and that is worse

A correctness number going down is the system working, per section 11.4. A resource ratio going down is a regression, and the two have to be told apart on the page rather than in a person's head.

The rule: a change that lowers the corpus pass rate has to say why, and a change that raises any of the three resource ratios by more than a stated tolerance has to say why. Neither is blocked, because a feature that lands correct and slow is still better than a feature that does not land. Both are visible, because the failure mode this project has already had once is a year of work ordered by corpus records with nobody watching the engine.

The goal is 0.1 on all three. The per milestone gates in document 12 are weaker than that on purpose and they get stricter as the milestones go on, since an engine missing window functions entirely cannot be measured against DuckDB on a corpus that uses them.

## 11.7 What 100 percent would mean

Every one of the 36 statements supported to the standard in section 1.2. Every one of the 1159 names passing the signature differential across its boundary set. The upstream corpus at a pass rate in the high nineties with the skipped fraction in the low single digits and every remaining skip named. The five error levels all high, including level four. Level one, level three and level four of section 1.1 measured by their own suites. And the generators in document 10 running continuously without finding a new reduced case for a sustained period.

That is a real definition and it is reachable, which is what section 2.2's family arithmetic was for. It is also years away, and the useful thing about writing it down is not the destination, it is that every number in it is computable today against a denominator that exists today, at whatever value it currently has.

The sentence this folder was written to replace is `rudb-compat levels` printing that none of the four levels has been measured yet. The replacement is not 100 percent. It is a page with eleven numbers on it, each with a denominator and a provenance, published on every run, allowed to go down.
