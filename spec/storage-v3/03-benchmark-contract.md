# Storage v3: benchmark contract

The four query engines are DuckDB native, DuckDB Parquet, rudb native, and rudb Parquet. The Parquet engines create a view over the same source file for each fresh query process. The native engines open their own previously loaded database files. All four execute the same unmodified query SQL. The load engines execute the same SQL text: `CREATE TABLE hits (<ClickBench schema>); INSERT INTO hits SELECT <projection> FROM read_parquet('<same file>', binary_as_string=True); CHECKPOINT;`. Any compatibility gap must be fixed in rudb rather than hidden by a benchmark-only SQL rewrite.

For each size, measure the load in a fresh child process, then close and reopen the file before correctness checks or timed queries. Record total child wall time, user and system CPU, peak RSS, source read bytes, output write bytes, file size, source hash, native file hash, row count, schema, version, and the exact SQL. Record insertion and checkpoint phases separately when the CLI provides a timer, but keep the whole child counters as the primary load cost. Report native load cost as a cost paid once and query decoding cost as repeated work.

Query timing uses one first run and at least five hot repetitions, with a new child process for every repetition. Engine order rotates by query to limit thermal or background-load bias. Query timer, process wall time, child CPU, peak child RSS, I/O, and answer are retained per repetition. An incomplete run is not averaged into a result. The report shows sums of complete query medians and the largest child RSS; it also includes q23, q24, q29, and q33 individually because they stress distinct storage paths. A deterministic tie retest is a correctness diagnostic, never a timed replacement for the original SQL.

Sizes start at 1k and 10k, then 100k, 1m, and 10m, and end at the full published `hits.parquet`. The 10m sample has 9,999,750 rows, and report text must use its actual count rather than silently calling it exactly ten million. Compare both query-only and load-plus-N-query break-even cost. For example, native is worthwhile after N runs only when its measured one-time load time is recovered by the measured per-query savings. The suite should later expand to TPC-H without changing metric definitions.

The small sizes are a development ladder and nothing more. **No design decision in this series is settled by a measurement below the full size.** A query at one million rows is mostly process startup, the group counts are cache resident, and the string dictionaries fit where they will not fit later; a mechanism can look like a tenfold win there and be a loss at the size the project is judged on. Document 13 is the measurement of that gap and names three decisions in this series that were closed on evidence the last two decades reverse. A document may report a small-scale number, and the number may be encouraging, but it closes nothing. Where a full-scale run is genuinely impractical the document must say so, state the size it did reach, and name the quantity it is assuming stays flat as the table grows.

Prefer a scaling claim to a ratio. A ratio against DuckDB at one size is a scoreboard entry; the growth factor between two sizes at least thirty times apart is a diagnosis, and unlike the ratio it can be checked against rudb alone. Document 14 states the four quantities a query's cost is allowed to depend on and turns each into a growth factor that can be predicted from the file's own metadata before the query runs.

The benchmark must pin binary and input hashes before running. DuckDB and rudb must use the same source Parquet file and matching SQL options. Native file size must be reported alongside peak RSS so a fast query that simply expands data on disk is visible. Ratios are shown against both DuckDB native and DuckDB Parquet; the requested 10 times speed and memory target is assessed against the apples-to-apples native row, with load cost reported separately.
