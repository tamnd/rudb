# Storage v3: file layout and commit model

The file starts with a fixed magic, major and minor version, feature flags, a file identifier, and two footer slots. All multibyte integers are little endian. Each footer slot contains an offset, length, generation, and checksum. The writer appends data and a complete manifest, syncs it, then writes the inactive footer slot and syncs that small header update. Opening chooses the highest valid generation. A torn slot or unfinished append cannot hide the previous valid generation. The initial implementation may create a new file through a temporary path and rename it atomically, but the on-disk contract keeps the two-slot scheme for later append and checkpoint work.

Data is organized as independently readable row stripes. A stripe has one row count and a descriptor for each column page. Column pages are independent byte ranges, not a row-major block. The manifest gives the page offset, compressed and uncompressed sizes, encoding identifier, logical column identifier, validity identifier, and optional minimum and maximum. A query that requests columns 2 and 17 seeks to those pages only. A count without a column can use stripe row counts without opening any page.

The initial target is 8,192 rows per stripe, matching the Parquet development ladder's independently readable groups. This is a test point, not a permanent constant. The benchmark should sweep 1,024, 4,096, 8,192, 16,384, and 65,536 rows and report load wall time, file size, q23, q24, q29, q33, the complete suite, and peak RSS. Very small stripes raise descriptor and seek overhead; very large stripes inflate decoded working sets and reduce parallelism. The winner may differ by table and hardware.

Each scalar page begins with its codec tag and its validity representation. Validity uses one of three forms: all valid, all null, or a bitmap. Fixed-width plain values are stored in native-width little-endian arrays for direct vector construction. Integer alternatives can use frame-of-reference bit packing, delta, run length, or dictionary codes. Strings have offsets and payload bytes for high-cardinality data, dictionary codes for repeated values, and FSST where training and decode cost win. An encoder chooses from a bounded sample and measures its choice; it must never hold the whole table to train a string dictionary. Nested types will use separate child pages and structural validity, with stable row correspondence.

The manifest is a compact directory of catalogs, tables, schema versions, stripes, column pages, and statistics. Page offsets and lengths are checked against file size before allocation. The reader rejects unknown required features and checksum failures. It never follows an unchecked pointer or trusts a claimed decompressed size without a configured bound.

Stripes are immutable after commit. Appends add stripes and a new manifest. A delete or update can later add a compact row-id mask or replacement stripe, with compaction performed as a new generation. The first milestone supports bulk insert and reopen; it must not imply that MVCC or concurrent writers are solved.
