# Expressions

Where the seam is the compiler, not the evaluator.

## 1. What is there now

`rudb-exec/src/expr.rs` was one recursive `evaluate(plan, expr, schema, chunk) -> Result<Vector>` of 161 lines. `rudb-exec/src/prepared.rs` is now 1,046 lines, which means v1's `Prepared` design has landed: a flattened node list with children before parents, a scratch vector per node reused across chunks, column positions resolved once, and constants materialised once at chunk width.

That work is good and this design keeps it. What follows is what it does not yet do.

## 2. The program

An expression is compiled once per query into a program and executed once per chunk.

```rust pub struct Program {
    ops: Vec<Op>,            // flattened, children before parents
    scratch: Vec<Column>,    // one slot per op, reused across chunks
    inputs: Vec<usize>,      // resolved column positions
    constants: Vec<Column>,  // materialised once at chunk width
    result: usize,
}

pub enum Op {
    Input(usize),
    Const(usize),
    Call { func: FuncRef, args: SmallVec<[usize; 3]>, out: usize },
    /// Short-circuiting, with selection threading. See section 3.
    And { branches: Vec<Range<usize>> },
    Or  { branches: Vec<Range<usize>> },
    /// One arm at a time, over the selection that reached it.
    Case { arms: Vec<(Range<usize>, Range<usize>)>, default: Range<usize> },
    /// A fused sequence with no intermediate materialisation. Section 5.
    Fused(FusedKernel),
}
```

The seam is `expr.eval`, and its strategies are compilers rather than interpreters:

```rust pub trait ExprCompiler: Strategy {
    fn compile(&self, expr: &BoundExpr, schema: &Schema, ctx: &Context) -> Result<Program>;
}
```

`tree-walk` is the reference and compiles to one `Call` per node with no fusion. `program` is the default. `fused` is F1's target. A future `jit` strategy compiles to machine code and slots in without anything above it changing, `rudb-jit` is nine lines today and this is where it attaches.

This is the resolution of the granularity problem from [`04-modularity.md`](04-modularity.md) section 3. Expression evaluation genuinely wants a per-node boundary, and the interesting optimisation is removing that boundary. Making the *compiler* the seam means the seam is crossed once per query, and the artefact it produces has no seams inside it.

## 3. Selection threading

The mechanism that makes conjunctions cheap, and the place where nullable booleans make it subtle.

A filter evaluates in **selection mode**: each conjunct receives the selection that survived the previous one and returns a narrower selection. `WHERE a > 5 AND b LIKE 'x%'` never evaluates the `LIKE` on rows where `a <= 5`. On `hits`, where filters are usually highly selective, this is most of the win on ClickBench Q20 through Q27.

A projection evaluates in **value mode**: the result is a full column including rows that would have been filtered out, because `SELECT a > 5 AND b LIKE 'x%'` must produce a value per row, and three-valued logic means that value is not derivable from a selection. The two modes are different code paths in the same program, chosen at compile time from the expression's position, and conflating them is a correctness bug rather than a performance bug.

`OR` threads the complement: the second branch evaluates only on rows the first rejected, and the results union.

## 4. Conjunct ordering

Conjuncts are reordered by observed selectivity divided by observed cost, using a running average over a recent window rather than over the whole scan.

The window is not a detail. `hits` is clustered by `EventTime`, so a predicate's selectivity varies enormously over the scan, and an average over the whole scan converges to the wrong answer and stays there. v1's expression document found this and it is one of the better findings in that directory.

This is `expr.order`, with `as-written` as the reference and `adaptive-window` as the default, and it obeys the adaptivity rules: it never changes an answer, it is bounded, it converges, and the final ordering appears in `EXPLAIN ANALYZE`.

## 5. Fusion

A fused kernel is a sequence of operations executed per tile with no intermediate column materialised. `(a + b) * c > d` is one pass over four inputs producing one mask, rather than three passes producing three intermediates.

The win is bandwidth, and it is the reason fusion is in the twenty-six per cent that [`02-research-2026.md`](02-research-2026.md) section 1.1 prices the whole execution story at, real, worth having, not an order of magnitude.

The scope is deliberately small: arithmetic and comparison over fixed-width types, up to some node count, generated by macro from a pattern list. Anything outside that falls back to per-node evaluation with the counter incrementing. A general fusion engine is a compiler and is `rudb-jit`'s problem, not F1's.

## 6. Functions

Every function gets a prepare step that runs once per query rather than once per chunk. A `LIKE` pattern compiles to a matcher; `rudb-regex` is 2,483 lines and already has the machinery. A constant string comparison precomputes its four-byte prefix so that the common case is a `u32` compare. A cast precomputes its conversion path. An `IN` list over more than a few elements builds a set.

This is where a surprising amount of ClickBench time goes, and it is invisible in a profile because it is spread across every chunk.

## 7. Encoded inputs

The part that belongs to [`13-encoded-execution.md`](13-encoded-execution.md) and is named here because the interface is here.

A `Call`'s function declares, through `FormAware` from [`05-data-model.md`](05-data-model.md) section 8, which forms of its arguments it can consume. A comparison against a constant accepts `Dictionary` and evaluates against codes, producing a mask over the dictionary and a gather. A comparison against a `BitPacked` column with a compatible base and width accepts it and compares packed. An equality against an `Fsst` column accepts it by compressing the constant with the block's symbol table.

Each of those has a property test against the decoded reference path. That is the entire correctness story for encoded execution and it is cheap because the reference path is never deleted.
