# A width the compiler knows

A grouped aggregate whose chunk comes in runs of one group folds every call that can share the walk in one pass over those runs, and since #1806 q01 takes one pass of six calls rather than two of three. What the pass costs is mostly the visiting rather than the values: about seventy instructions a run beyond what it spends per value, over runs that average 2.81 rows.

Most of those seventy are per call, and they were all there because the number of calls was a number the loop read at run time. Per call per run the walk loaded that call's column out of the list, bounds checked the slice of it the run covers, loaded the group's running total out of the locals and stored it back. None of that is work the query needs. It is the cost of not knowing how wide the pass is until it runs.

So the widths a query actually reaches each get a walk compiled for them. One to eight calls dispatch into a function generic over the width, which reads the columns into an array once before the first run and holds the run's totals in an array of that width, and anything wider keeps the loop that reads its calls out of the list as it goes. A pass of no calls keeps it too, since a chunk whose only aggregates are counts still wants the walk and the run lengths and has no column to read. At a known width the columns are registers held across the whole walk, the totals are registers held across the run, and the loop over the calls is not a loop.

On server2 at SF1, one thread, three rounds, median, with the `SELECT 1` baseline subtracted, q01 went from 1708.2 M instructions to 1647.8 M and the suite from 16.94 G to 16.87 G. All 22 answers are unchanged and no query moved the other way at all.

Eight is where the list stops because nothing in TPC-H or ClickBench asks for a ninth folding call over one layout in one grouping, and each width compiles a copy of the walk for every numeric type the kernel is generic over. If a workload turns up that wants more, the number to raise is in one macro call.

What is left on the run visit is the layout vote. Two calls over an `i32` column and an `i64` one still take a walk each, because the value loop is written once per physical type, and q01 only shares one pass because its stored decimals read out into the same `i64` its computed ones are already in. Reading every layout out into one row major buffer up front would make the inner loop a walk over fixed width rows and leave one pass for the whole chunk, at the price of a copy per value. On runs of 2.81 rows that looks like the right trade, and it is the next thing to measure. Before it, finding the runs is still about fifteen instructions a row in `Aggregate::fold`, and the per chunk allocations still show up as `memset` inside `mi_malloc` on the scan's decode buffers.
