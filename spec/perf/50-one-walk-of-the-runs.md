# One walk of the runs for every call

A grouped aggregate whose chunk comes in runs of one group folds each call by walking the runs, and it walked them once per call. What a run costs before any value of it is read, counted out of the disassembly on server2, is twenty one instructions: the run's end loaded, the slice of values it covers bounds checked, the slot read and checked against nothing and against the group count, the local for that slot indexed and loaded, the total stored back and the run pointer advanced. A value inside the run costs four. TPC-H q01's mean run of equal `(l_returnflag, l_linestatus)` is 2.81 rows, so the twenty one was paid once per call over 2.13 million runs to read eleven values each time, and the same walk was most of what the fold spent.

So the walk is one pass now, with every call that can share it folded inside. The locals are one array rather than one per call, a run of totals per group followed by that group's row count, so a run resolves its slot once and the totals it then adds into sit next to each other. The row count is one number for all of them because they all see the same runs, and it was counted per call before. A count of the rows rides along for nothing: what it wants out of a run is the length, which the walk is adding up anyway, so it costs one add per group at the end and nothing at all per run, where before it was a walk of its own for one add a run.

Only calls that read values of one layout share a pass, because the value loop is written once per layout and a loop that asked which layout it was reading, per call and per run, would spend more on the question than the sharing saves. The pass takes the layout the most of the offered calls hold and the caller asks again with what is left, so q01's two computed decimals wide enough to need an `i128` share one pass and anything held in an `i64` shares another.

On server2 at SF1, one thread, three rounds, median, with the `SELECT 1` baseline subtracted, q01 went from 1996.0 M instructions to 1938.0 M and the suite from 18.13 G to 18.07 G. All 22 answers are unchanged and nothing moved the other way past 1.001x.

Two things were tried first and measured worse, both of them attempts on the value loop rather than on the walk. Accumulating the magnitude of the values beside the total and checking it once after the runs, so the adds could go unchecked, made q01 1.071x: the `abs` and the `or` cost about 4.7 instructions a value and never vectorized. Arguing the same bound from the column's declared type instead, which puts nothing at all in the value loop, made q01 1.007x. The reading is that the `jo` the adds carry is free, and that at 2.81 rows a run there is no vector body to reach in the first place. The cost was never in the values.

What is left in q01 is that most of its calls never reach the run path at all. `l_quantity` and `l_discount` are stored as dictionaries, and the run path asks for a flat column, so their sums, their means and their counts all go a row at a time through the scatter. A count over a dictionary with no nulls in it is the run's length exactly as a count over a flat column is.
