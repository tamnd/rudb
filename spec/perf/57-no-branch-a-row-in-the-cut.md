# No branch a row in the cut

This one is worth reading for how it was measured as much as for what it does, because it is the first note in this directory whose win the instruction count cannot see at all.

A grouped aggregate that folds runs of one group has to find the runs first, and `slot_runs_of` does it in one pass over the chunk's slots. The version before this one read sixteen slots at a time, or'd their differences against the slot of the run it was in, and walked the block a row at a time only where that or came out non zero. The idea is that a long run skips whole blocks. On a chunk like q01's it skips nothing: runs of `(l_returnflag, l_linestatus)` average 2.81 rows, so the slot changes somewhere in every block of sixteen there has ever been, the or never once took the fast path, and every one of six million rows went through the row loop and its `slot != current` compare. That branch is taken about a third of the time in no pattern, which is the worst thing you can hand a branch predictor. In the cycle profile it was 16.4 percent of `Aggregate::fold`, and the 18.8 percent sitting on a bounds check that is never taken was the mispredict of the compare before it being charged to the next instruction.

So the cut now has no branch a row. A row starts a run where its slot differs from the slot before it, which is a compare per row with nothing carried from one row to the next, and the block's starts are gathered into a `u64` of one bit a row. The runs are read off that mask by counting its trailing zeroes, so the loop runs once per run rather than once per row. The reformulation that makes it work is dropping `current`: a run that ends before row `at` has whatever slot row `at - 1` holds, so the mask alone gives both numbers a run is made of and nothing has to remember which run it is in. The budget check moved with it, from once a run to once a block against the bits the mask has set, and the output vector is reserved up front so the push stores and does not test.

The measurement. On server2 at SF1, one thread, q01 retires 1.6596 G instructions before and 1.6597 G after, which is the same number, and the suite is 16.75 G against 16.76 G with all 22 answers unchanged. By the instrument this directory has used for every note before it, this change does nothing. What moved is branch misses, 7.61 M to 4.83 M on q01, and cycles, a median of 952.1 M to 895.4 M over five rounds, so 0.940x. Nothing else in the suite gets worse on either: q03, q09, q10, q13, q18 and q21 all come in at or below where they were on misses once the rounds are taken to three.

The lesson to keep is about the instrument rather than the loop. Instructions retired is the primary measurement here because it is immune to what else the box is doing, and that immunity is exactly why it is blind to branch prediction, to cache misses and to everything else that costs cycles without retiring anything. A change that removes a mispredict reads as flat, and a change that adds one reads as flat too, which is the direction that should worry us. Branch misses are the counter to reach for next, because they are a core local per process event and so they are load immune in the same way instructions are, which cycles on a box under load average 24 are not. Cycles were worth taking here only because five rounds of each barely overlapped.

What is left on q01 is no longer in the fold. The per chunk allocations still show up as `memset` inside `mi_malloc` on the scan's decode buffers and the projection's output vectors, and #1801 having made the system allocator the shell's default means that wants a fresh profile before anything is done to it. The layout vote in the shared walk is still there, and reading every layout out into one row major buffer would end it, but the modelling for that was done before the pass width became a compile time constant and it no longer looks worth the copy per value it costs: the per call per run loads and stores it was going to save are the ones #1811 already took out.
