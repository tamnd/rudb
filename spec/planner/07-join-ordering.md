# Join ordering

The only search in the pipeline, stage 13, and the one pass where the difference between the best plan and the worst is not a factor but an exponent. It is also the pass where the literature is deepest and where the temptation to over-build is strongest, so this document spends as much space on the budget and the fallback as on the algorithm.

## 07.1 The problem, stated so the budget makes sense

A join of *n* relations has a number of valid orders that grows super-exponentially in *n*. The join *result* is the same for all of them and the cost is not, because the intermediate results differ by orders of magnitude. Ordering the joins so the small intermediates come first is the single largest algorithmic lever in a query engine, and it is the one thing the current `crates/rudb-exec/src/join.rs`, a nested loop taking whatever order the binder emitted, does not have at all.

Two facts set the scale of what has to be built:

- Almost every query anybody writes has fewer than ten relations. TPC-H's largest is eight. ClickBench has none. Exact dynamic programming is instant at this size.
- A minority of queries have twenty, fifty or a hundred, usually generated by a tool. JOB has queries in the teens. Exact DP is not instant at that size and for some shapes it is not finishable.

So the design is: exact for the common case, a bounded search with a deadline for the rest, and a greedy answer that is always available. Not one algorithm.

## 07.2 The graph

Pass 6 in document 03 builds it and this pass consumes it. Flatten the tree of binary joins into a **hypergraph**: relations are vertices, each join condition is an edge over the table sets its two sides read, and a condition reading more than two tables is a hyperedge. `CrossProduct` contributes no edge, which is exactly why document 02 keeps it as a separate node kind.

Outer joins are the reason this is a hypergraph rather than a graph. A left join cannot be freely reassociated with the inner joins around it: some reorderings change the answer. The standard treatment, Moerkotte and Neumann's conflict detection work, encodes each non-reorderable relationship as an additional hyperedge so that the enumerator's connectivity test refuses the invalid orders by construction rather than by a check bolted onto the cost function. Get this wrong and the result is a wrong answer, not a slow query, which puts it in the same risk class as document 04's join-kind table.

Semi and anti joins are reorderable under more restricted conditions than inner joins and less restricted than outer ones. Treat them conservatively at first, pinned in place, participating in the graph only as vertices, and relax later with corpus evidence. A pinned semi join costs a factor. A wrongly reordered one is a bug report.

## 07.3 DPccp, and then DPhyp

**DPccp**. Moerkotte and Neumann, *Analysis of Two Existing and One New Dynamic Programming Algorithm for the Computation of Optimal Join Orders*, VLDB 2006. It enumerates **connected subgraphs and their complement pairs** directly, in time proportional to the number of such pairs, which is optimal in the sense that every pair it enumerates is a join it genuinely has to consider. The naive "all subsets" DP considers many it does not.

**DPhyp**. Moerkotte and Neumann, *Dynamic Programming Strikes Back*, SIGMOD 2008. The same idea over hypergraphs, which is what makes outer joins and multi-table conditions expressible. This is the one to implement; DPccp is the special case it degenerates to when no hyperedges exist.

Both produce **bushy** trees, not only left-deep ones, and bushy matters here for a specific reason: a bushy tree lets two small builds happen independently and join to each other, which is both cheaper and more parallel than threading everything through one pipeline. There is no reason to restrict the search space to left-deep when the enumerator naturally produces more.

**Cross products.** The enumerator only joins connected subgraphs, so it never produces a cross product on its own. Sometimes one is optimal, two tiny filtered dimension tables crossed before probing the fact table can beat two separate probes. Allow it, but only under a hard size bound on both sides, because a cross product chosen on a bad estimate is the worst single failure mode a planner has.

## 07.4 DPconv, and the constraint it puts on document 06

**DPconv**. Stoian and Kipf, *DPconv: Super-Polynomially Faster Join Ordering*, PACMMOD 2(6), December 2024, selected as a SIGMOD Record Research Highlight in April 2026 (volume 55 issue 1) with an accompanying technical perspective. This is the first asymptotic improvement to exact join ordering in a long time and it is worth understanding before committing to a cost model.

The idea: the DP recurrence over subsets is a **subset convolution** in the (min, ⊗) semi-ring, and subset convolution has a super-polynomially faster algorithm than the naive subset-pair enumeration. The reported result is up to about 30x faster than DPccp on large clique queries, the densest, hardest shape.

The constraint, and it is the reason this appears in document 06 as well: the method requires the cost function `c(T1, T2)` to be **separable into factors that can be sunk into the DP table entries**. The paper is explicit that it cannot handle a cost like `c(T1) · c(T2)`, which is the nested-loop cost. A rows-and-bytes additive model of the kind document 06 specifies is separable; a model that grows a multiplicative term for one operator later is not, and would silently take DPconv off the table.

**What to do with this.** Not implement it first. DPhyp with a good enumerator handles everything rudb will see for a long time, and DPconv's win is concentrated on dense graphs with many relations, which is a shape that arrives with generated SQL rather than with benchmarks. But keep the cost model separable, note in the cost model's own doc comment why, and revisit when a real workload shows DPhyp exhausting its budget on clique-shaped queries. The cheap version of that check is a counter: how often the budget is hit and with what graph density.

## 07.5 The budget and the fallback

Document 03 gives the pipeline a deadline scaled to estimated execution cost. Join ordering is the pass where being cut off is interesting, because it is the only one that can be cut off mid-answer.

**Greedy is always computed first.** Greedy operator ordering, repeatedly join the pair with the smallest estimated result, is O(n³) at worst and effectively instant. Run it, keep its plan and its cost, then start DPhyp. If the deadline fires, return greedy's plan, or the best complete plan DP has found, whichever is cheaper. There is never a state where the pass has no answer.

**A relation-count threshold on top of the deadline.** Below about twelve relations, DPhyp runs to completion and the deadline never fires. Above a hard ceiling, the usual number is in the range of fifteen to twenty and the right one comes from measurement, do not start DPhyp at all; go straight to greedy plus a local improvement sweep. Starting an exponential search that will be abandoned wastes the budget that greedy refinement could have used.

**The middle ground, if it is needed:** iterative dynamic programming, which runs exact DP over bounded-size subsets and greedily combines the results. It is the standard answer for large queries and it is more code than greedy for a benefit rudb has no workload to demonstrate. Do not build it until a workload asks.

**Report it.** When the budget fires, `EXPLAIN` says so. A user whose query got a greedy plan should be able to find that out without reading the source, and a developer looking at a regression should see it in the first line of output rather than inferring it.

## 07.6 Why not Cascades

Stated here rather than only in document 03, because this is the pass a Cascades advocate would point to.

A top-down memo with a rule set gives one unified framework for rewrites and ordering and lets a rewrite be costed against its alternative. Its price is planning time that is hard to bound and hard to predict, and an implementation whose first working version is a year out.

The rudb position, from `spec/engine/11-optimizer.md` section 11.6: almost every rewrite in this folder is unconditionally good and does not need to be costed, and the one decision that genuinely needs search has a dedicated algorithm with a dedicated budget, which is this document. A memo would buy the ability to cost the handful of context-dependent decisions, and document 03 accepts the cost of not having it: those decisions cost themselves locally in document 10.

The line that is worth keeping honest: if rudb later finds that five or six rewrites all need to be costed against each other and the local comparisons start contradicting one another, that is the signal the framework is wrong, and it should be named as such rather than patched. Nothing in this folder is expensive to port into a memo later; the passes are pure functions over an arena.

## 07.7 What the 2026 literature says about learned join ordering

The short version: the search was never the weak component.

The MCTS reproducibility study, arXiv:2603.16474, March 2026, re-evaluates the learned join-ordering line, AlphaJoin, HyperQO and relatives, and reports that the claimed gains do not hold under diverse workloads. Its ablation attributes the instability to the **learned cost models** suffering severe out-of-distribution errors, while finding the Monte Carlo tree search strategy itself sound. Its own proposal, an "Extreme UCT" variant driven by the database's own cost model rather than a learned one, is reported to outperform the published learned systems. *This summary is from the paper's abstract as reported in a September 2026 search; I have not read the evaluation.*

That is a useful result for rudb in a negative way. It says: do not build a learned estimator for this pass, and do not assume the search is where the wins are. DPhyp with a mediocre-but-honest cost model is on the right side of that finding already.

The benchmark side matters more than the algorithm side here. **JOB-Complex** (arXiv:2507.07471, AIDB at VLDB 2025) reports PostgreSQL 16 at an optimization gap of 1.18 on JOB-light and 1.99 on JOB, which is the number to beat and the number that says how much room there actually is. And the *Still Asking* retrospective (PVLDB 18(12), 2025) names robustness rather than search quality as the open problem, which is the thesis document 08 acts on.

## 07.8 Measuring this pass

Join ordering is the one pass where "it made things faster" is not a sufficient test, because the failure mode is a rare catastrophic plan rather than a uniform slowdown.

- **Optimality gap on JOB**, against the best plan found by exhaustive search where exhaustive search is feasible. This is the number JOB-Complex reports and it is directly comparable.
- **Plan stability.** A committed baseline of the chosen order per query, diffed in CI. A change in join order is a change that must be explained by whoever made it. Document 12 specifies the mechanism.
- **Planning time per query**, asserted against a budget, because this is the pass that can blow it.
- **Tail, not mean.** Report the worst query, not the geometric mean, because a 2x average with one query 50x slower is a worse engine than a 1.5x average with nothing regressed. That is the second axis of `spec/02-the-goal.md` applied to this pass.

## What we should take from this document

DPhyp over a hypergraph is the algorithm, with DPccp as its degenerate case, producing bushy trees, with cross products allowed only under a hard size bound.

Outer joins are encoded as conflict hyperedges so the enumerator refuses invalid orders by construction. Semi and anti joins are pinned at first and relaxed only with corpus evidence, because the failure mode is a wrong answer.

Greedy runs first and is always available, DPhyp runs against a deadline, above a relation-count ceiling DPhyp does not start at all, and `EXPLAIN` reports when the budget fired.

DPconv is a real asymptotic improvement worth up to 30x on dense graphs, it requires an additively separable cost function, and the only action it demands today is not to break separability in document 06.

The 2026 reproducibility evidence says the learned-cost-model component is what breaks in learned join ordering, not the search, which is an argument for exactly the shape of pass described here.

Measure the optimality gap on JOB, keep a plan-stability baseline, assert planning time, and report the tail rather than the mean.
