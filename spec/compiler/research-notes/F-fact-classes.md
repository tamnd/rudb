# F. The facts the physical plan uses, and which of them rudb records

Research note for the rudb compiled-execution-engine spec. It answers C1 exit criterion 3 of issue #1829 and question Q8 of `20-open-questions.md`: every fact class `04-the-physical-plan.md` uses, marked as exists, requested or not planned. Compiled 2026-09-25 against `origin/main` at cd8e1914.

Conventions:
- A fact is what `../planner-v2/04-facts-not-estimates.md` section 4.2 calls one: a value with a class (Exact, Certified, Estimated or Unknown) and a provenance. The class column below is the weakest class document 04 accepts for that use.
- **Exists** means rudb writes or keeps the fact today and a planner could read it at plan time. The last column says whether it already reaches `rudb-opt`, because several facts are recorded by storage and never handed to the planner. That is wiring work in the planner, not a request to storage.
- **Requested** means nothing in the tree records it. The note says which layer has to produce it and what it costs to keep correct under writes.
- **Not planned** means the compiler does without it, and the note says why that is safe.
- Every entry was checked in the code. Paths are relative to `crates/`.

## 0. Summary

Document 04 relies on 24 fact classes. 20 exist, 1 is requested and 3 are not planned.

The one request is a per row group encoding tag that the planner can read before a morsel is dispatched. Everything else document 04 asks for is already written down somewhere, mostly in the native file's directory, its column summaries (`rudb-stats`) and its graph sections (`rudb-graph`). The gap is not storage. It is that about half of the facts that exist do not reach `rudb-opt`: column uniqueness, maximum string length, the link header counts, the key overlap sketches, and every fact of an in-memory table except its row count, its null counts and its distinct counts below the sketch size. The list of those is in section 2.

## 2. What exists and does not reach the planner

These are not storage requests. The numbers are on disk or in memory already, and each item is a change in `rudb-catalog`, `rudb-plan` or `rudb-opt` to hand them over. They belong on the C2 to C6 checklists next to the operator that first needs them.

- **Column uniqueness (row 9).** The most valuable one for JOB, since almost every JOB join is N:1 into a primary key. `rudb-plan/src/unique.rs` should give a `Get` the keys of `Table::keys` (enforced, so Exact) and of `Summary::unique` (Exact, native only).
- **Maximum string length (row 18).** `rudb_native::zones::widths` already reads the summary and throws away `widest`.
- **Link header counts (row 21) and degree distribution.** `Database::related` reads the header to decide `verified` and then keeps two booleans. The four numbers of `../graph/06-the-optimizer.md` section 6.2 should travel as a `Stat` with provenance `LinkHeader`.
- **Key overlap sketches (row 23).** Written by native loads within their byte allowance, and read by nothing.
- **Dictionary facts (rows 13 and 15).** The planner needs a per column answer to "one dictionary, sorted, not demoted". The reader has all three.
- **Every fact of an in-memory table except rows 1, 5 and 7.** Zones, frequencies, order and widths are kept for memory tables or cheap to keep, but `Rows::zones`, `Rows::frequencies`, `Rows::ascending` and `Rows::widths` answer nothing for them.

## 3. The requested fact

**Row 14, the encoding of each row group.** Producer: `rudb-native`'s writer, as one tag per column per part in the directory or in the part range page it already writes, and `rudb-storage` for memory chunks. It needs no maintenance under updates beyond writing it: a part's encoding is fixed when the part is written, and appended parts carry their own. What it buys is small. Without it the compiled scan keeps the per-morsel encoding tag check of 4.7, which is a compare per morsel and never a wrong answer. With it the planner can drop the guard and the deopt variant for a column whose every part is coded, which is less code to generate. For native string columns row 13 already gives most of that at column granularity: a column with a global dictionary that was never demoted is coded everywhere. So this request is low priority and should not block anything before C6.

## 4. Why the three not-planned facts are safe to skip

**Row 8, group count over several columns.** Document 04 selects GHT only when the count is Exact or Certified, and falls back to thread-local tables and then partitioned aggregation, which is the safe default, with the spill to partitions as a runtime decision point (4.9). An exact count of combinations cannot be kept under appends without the rows, and a certified bound would need a multi-column sketch nobody has a second use for.

**Row 16, a dictionary shared by two columns.** JOB, TPC-H and TPC-DS join on integer keys, and integer keys are not dictionary coded, so rule 1 of 4.6 almost never has two coded sides to match. Where it would, joining on decoded values is correct and costs one decode per build row. Sharing a dictionary across tables would tie two files' write paths together, which the storage layer has avoided so far for good reason.

**Row 24, quantiles and a sample.** Document 04 makes every selectivity-based choice as a Decide use, which takes any class. The stripe interpolation and the frequency leaders of row 20 cover the range and equality cases the benchmarks filter on, and the runtime keep/drop and flip points of 4.4.3 and 4.5 correct for a bad estimate. They stay open in `../planner-v2`, not here.

## 5. Maintenance under writes

A native file never changes, so every fact it records is exact for its generation. The weak point is a table with rows appended since its file was written (`Rows::Grown` in `rudb-catalog/src/table.rs`). For such a table only row counts and null counts stay exact. Distinct counts, extremes, zones, frequencies, order and widths all answer nothing until the next checkpoint writes a new file, and graph sections go stale and are ignored by their generation stamp. That is correct under document 04's rule, since a missing fact means the generic variant, but it means the compiled engine plans a freshly appended table like an unmeasured one. The fix belongs to `../stats/` and `../storage-v3/`, and the ones that matter most to document 04 are rows 3, 7 and 9, which fold or weaken under appends by the rules `rudb_stats::Summary::widen` already implements.
