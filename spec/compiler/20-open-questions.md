# 20. Open questions

This folder settles the shape of the compiled engine, and these are the questions it does not settle. They are ranked by how much of the 10x each one could cost if answered wrong. Each comes with what we currently believe, the measurement that would settle it, and the milestone at which that measurement becomes possible. A question with no settling measurement does not belong on this list. It belongs in a discussion.

## Q1. Can the per-query QIR be small enough for G1 on the largest JOB plans?

**Why it ranks first.** G1 is the hinge of document 18, and there are two ways to miss it. `direct` can be slow per instruction, which is a solved problem: DirectEmit and TPDE show that single-pass emitters run at tens of nanoseconds per IR instruction. Or the translators can emit too many instructions, which nobody has published an answer to for our design. JOB's largest queries have 16 joins and, after the Lookup and Expand split, the reduction cascade, and both probe variants, perhaps 40 pipelines. Umbra's compile time on JOB is dominated by code volume, not by LLVM's per-instruction cost alone, and its lookup-and-filter variant compiles for about 88 s (`research-notes/D-benchmarks.md`).

**What we believe.** Probe variants are already generated lazily, one per pipeline, once the build facts are exact (document 09 Rule I3, document 10 section 10.6). The remaining multipliers are guard fallbacks and the up to 20,000-instruction functions document 06 allows. At document 06's 10 ns generation plus 50 ns `direct` per instruction, a 5 ms query maximum holds about 80,000 QIR instructions after the frontend's share [derived].

**What would settle it.** At C3, the per-query count of QIR instructions and generated bytes on all 113 queries, with the backend time split out.

**If it goes badly, the options in order:**

- Emit rarely taken paths, such as overflow traps and deopt slow paths, as calls to shared precompiled stubs instead of inline code.
- Share pipeline functions across queries by parameterizing table and column identity. That turns JOB's 113 queries into far fewer distinct functions, and it is the code cache of document 09 used across queries rather than across executions.

## Q2. Is the staged probe still worth it after reduction?

**Why it matters.** Document 02 section 2.9 credits staged probes and the hash table with 2x on JOB, and reduction with 1.5x. Caution 1 there says these overlap. Reduction removes the probe tuples that would miss, and misses are where prefetching earns most. If reduction is as good as RPT+ and exact bitmaps make it, the probes that remain may hit tables small enough to be cache-resident, and the fused loop wins.

**What we believe.** The factor moves, it does not vanish. JOB's large dimension tables (`title`, `name`, `cast_info`) produce built tables beyond LLC even after reduction on many queries.

**What would settle it.** The C6 ablation, which switches each mechanism off alone and in pairs. Because the choice is made at runtime from the built size (document 10), a wrong belief here costs a few percent of code volume, not correctness or a redesign.

## Q3. How much of JOB's string work can be done on dictionary codes?

**Why it matters.** Compiled strings are 1.5x of the JOB decomposition. The largest part of that assumes a LIKE on a dictionary-coded column is evaluated once per dictionary entry and becomes a bitmap test in the loop. That depends on the storage layer choosing dictionary encoding for IMDB's text columns, and on the dictionaries being small relative to the column. `title.title` and `name.name` are nearly unique, and dictionary coding does not help a nearly unique column.

**What we believe.** Low-cardinality columns such as `info_type.info`, `company_type.kind`, `keyword.keyword` and `movie_info.info` for most `info_type_id` values get the bitmap path. The high-cardinality name columns need compiled LIKE on the raw bytes, or FSST-domain matching.

**What would settle it.** A C0 side measurement. For every column used in a JOB string predicate, record its encoding under the current storage layer, dictionary size against row count, and the share of JOB's first-engine time spent in that predicate. This is cheap, and it should be done before C7 is scoped.

## Q4. Does the release build need an optimizing tier?

**Why it matters.** Document 19 section 19.4 ships `interp` and `direct` by default, because the zero dependency rule keeps Cranelift behind a feature. On CGO 2024's workload `direct`-class code ran about 5% behind Cranelift and about 17% behind LLVM -O2 (`research-notes/B-backends.md`). On TPC-H SF100 and TPC-DS SF100, where pipelines run for seconds, that is a visible fraction of the 10x target.

**The options:**

- Accept the cost.
- Add a second mode to `direct` for hot loops only: better register allocation over the loop body, loop-invariant hoisting, and a scheduling pass. Flying Start and TPDE both leave these out, and the 5 to 17% gap is roughly their size [derived].
- Argue a second exception to the zero dependency rule for Cranelift, on the allocator's terms: a measured number written into the package layout document.

**What would settle it.** At C12, on TPC-H SF100 and TPC-DS SF100, the execution-time gap between `direct` and `clif` per pipeline, weighted by pipeline time. A weighted gap under 5% closes the question as "accept". Above 10%, the second `direct` mode goes on the schedule.

## Q5. Should the physical planner redo join ordering?

**Why it matters.** Document 03 section 3.2 puts the boundary at A4, the rewritten logical plan, and leaves join order as a grey area. The compiled engine can make choices the first engine cannot: index nested loop through a stored link, a dense array join, a groupjoin. Those change which join order is best. A join order chosen for the first engine's costs is not the best order for the compiled engine's.

**What we believe.** For JOB, the order matters less once the reduction is complete. That is the RPT result: robustness to join order is the point of predicate transfer. So the physical planner keeps `rudb-opt`'s order and chooses build sides and algorithms only. That belief needs a check.

**What would settle it.** At C6, JOB with `rudb-opt`'s order compared against the best order found by exhaustive enumeration on the compiled engine's actual costs, for the queries with 8 joins or fewer. If the gap is under 10% on the total, the boundary stays where it is.

## Q6. Where exactly does the compiled engine match DuckDB's bugs?

**Why it matters.** Document 12 sets the rule: match DuckDB where DuckDB is correct, and record a documented divergence where it is not. Document 10 applies that rule to NULL-aware anti-joins. "Correct" is sometimes a judgment call, for example floating-point summation order, error-message wording, or the result type of an edge-case cast. `rudb-compat` counts every divergence against the 100% compatibility goal.

**What we believe.** The known-divergence registry of document 15 should stay under a few dozen entries, each with a SQL-standard or mathematical citation, and each duplicated as an issue filed upstream.

**What would settle it.** Nothing settles it. It needs a standing owner and a review rule. It is on this list because an unowned registry grows without anyone deciding it should.

## Q7. Is 16,384 the right morsel size on JOB's small tables, and 1,024 the right batch?

**Why it matters.** Morsel size trades scheduling overhead against load balance and deopt rerun cost. Batch size trades the scan kernel's SIMD efficiency against the generated body's working set. The numbers in document 05 come from Leis et al. and from Kersten et al., on hardware from 2014 and 2018, and neither measured an M4's 16 MB of shared L2 against a Zen 3 CCX's 32 MB L3.

**What would settle it.** A C5 sweep: morsel sizes of 4k, 16k and 64k tuples against batch sizes of 256, 1,024 and 2,048 on JOB and TPC-H SF10, on both machines. The sizes are constants in `rudb-qc-pipe`, not assumptions baked into generated code, so the answer is cheap to adopt.

## Q8. How should the compiled engine consume encodings the storage layer has not built yet?

**Why it matters.** Specializing to data facts is claim 3 of document 00. The facts it names include clustering by parent, sort order and value range, and those have to exist as certified facts. `../stats/` and `../storage-v3/` decide which facts get recorded and what they cost to maintain under updates.

**What we believe.** Document 04's rule holds: a missing fact means the generic variant with no guard, correct and slower. The risk is organizational, not technical. The compiler's request list has to reach the storage work early enough to be scheduled.

**What would settle it.** A list in the C1 report of every fact class document 04 uses, marked as exists, requested, or not planned. It gets reviewed with the storage owners.

## Q9. Is the interpreter fast enough to be the tier for short queries?

**Why it matters.** Document 09's Rule I1 runs a pipeline on `interp` only when storage metadata proves its input is at most one morsel, and document 09 runs a failed guard's first fallback on `interp` while `direct` compiles. A single morsel on `interp` at about 3.2x `direct`'s time is bounded, but a single-morsel pipeline with an expensive body (a regex, a wide string join) is not cheap, and the extrapolation cannot rescue a pipeline with no next morsel.

**What we believe.** The exposure is bounded by one morsel's worth of work per pipeline, which is small next to G1 on every suite except ClickBench's regex queries.

**What would settle it.** At C5, the distribution of the ratio (actual time on the chosen tier) / (time on the best tier) across JOB, TPC-H SF1, ClickBench and `rudb-compat`'s corpus. Its 99th percentile should be under 2.

## Q10. Where does worst-case-optimal join belong, if anywhere?

**Why it matters.** Umbra measured WCOJ as the default at 25x slower on JOB (`research-notes/C-joins-job.md`). Document 10 does not make it the default. But CEB and some JOB queries contain cycles, and those are the queries where binary joins produce the intermediate blowup that WCOJ exists to avoid. `../graph/10-milestones.md` G8 schedules a multiway intersect for exactly those queries.

**What would settle it.** After `../graph/` G8, run that operator's translator on the cyclic queries of JOB and CEB, compared against the binary plan with full reduction. The question is only whether the translator goes on the C10-or-later list, and nothing earlier depends on it.

## Questions that were considered and closed

These came up while writing the folder and are closed. They are listed so they are not reopened without new evidence.

- **Whole-query functions.** Closed by document 03 section 3.9: they break tiering, parallelism and cancellation for no measured gain.
- **Source-to-source through `rustc` or a C compiler.** Closed on compile latency: seconds per query against a 1 ms budget.
- **MLIR.** Closed by document 01: the dialect stack's compile latency is LLVM's, and LingoDB's own numbers put it outside G1.
- **Copy-and-patch as the default backend.** Closed by the TPDE comparison in document 01: code 2.32x slower than a single-pass emitter's, at similar compile speed.
- **Learned tier or kernel choice.** Closed on determinism and explainability: a tier choice must be reproducible from the log. Document 09 uses a rule over measured morsel progress.
- **Generating scan and decode code.** Closed by the Data Blocks result cited in document 00: precompiled SIMD kernels are faster and cost nothing to compile.

## What we should take from this document

The two questions that could cost the most are about volume, not speed. Q1 asks whether JOB's plans produce too much code for any backend to meet G1. Q3 asks whether JOB's strings are in a form the compiler can exploit. Both can be measured before C6, and both should be.

Several questions exist because the decomposition in document 02 is a product of factors that overlap: Q2, Q3 and Q5. The ablation switches of document 17 are what turn those into measurements. They are part of the engine, not a benchmark nicety.

The zero dependency rule creates Q4, and it is the one question here that is partly a policy decision. It should be decided on the C12 number, not before it.

Every open question has a milestone at which it becomes measurable. None of them blocks C1 through C5, which is the evidence that the folder has settled what it needed to settle.
