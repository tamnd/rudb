# EXPLAIN, and how each arrow is proven

Six artifacts and five arrows is more machinery than one plan and one answer, and the argument for it in document 03 section 3.7 was that the machinery pays for itself in testability. This is the document that has to make that true, because an architecture whose extra layers are not each independently checkable is just more layers.

## 13.1 Five EXPLAIN forms, one per artifact

From document 03 section 3.8, restated with what each one is for.

`EXPLAIN (LOGICAL)` prints artifact 3. This is DuckDB's `EXPLAIN` and it is the compatibility surface, so `../12-duckdb-compat.md` governs its text and this folder does not get to change it.

`EXPLAIN (LOGICAL, STATISTICS)` prints artifact 4, every number followed by its class and its provenance. A plan built on a guess and a plan built on an exact count look different on the page, which is what `../stats/00-README.md` asks for.

`EXPLAIN (PHYSICAL)` prints artifact 5: every choice, every fact that drove it, every reservation, every layout requirement and whether it was met.

`EXPLAIN (PROGRAM)` prints artifact 6, one block per line with its state and its types. This is the one a kernel author reads and the one a lowering test asserts against.

`EXPLAIN ANALYZE` prints artifact 5 with measured counters, the three runtime transitions from document 12 section 12.2, and per block counters under a flag.

The reason for five rather than one is that the failure modes are different. A wrong answer is a logical plan bug. A slow query with a good plan is a physical plan bug. A slow query with a good physical plan is a lowering or kernel bug. One blob of text conflates all three and the first question anybody asks about a slow query is which of them it is.

## 13.2 What proves each arrow

**Bind.** A corpus of statements, each with an expected bound plan or an expected error. Not this folder's subject.

**Rewrite.** Text in, text out. `Plan::parse` of `Plan::print` is already the identity and `crates/rudb-plan/tests/roundtrip.rs` and `property.rs` are 1,468 lines asserting it, so a pass test is a plan in a file, a pass name, and a plan in a file. No catalog, no data, no executor. This already works and it is the model everything else copies.

**Annotate.** Two things. That the class attached to every fact is the class the supply side says it has, which is a test against `../stats/` rather than against a query. And the q-error distribution published per class, per document 04 section 4.8, which is a measurement rather than a pass or fail but becomes one at a threshold for the `Exact` class, where any q-error other than one is a bug.

**Physical planning.** Assertions on printed fields. `EXPLAIN (PHYSICAL)` on ClickBench Q1 must say `strategy=direct`, and the test is a string comparison. This is the arrow that has no test at all today, because there is nothing to assert against.

**Lowering.** Golden files. A physical plan in, a program out, compared as text. Adding a lowering rule changes some golden files and the diff is the review.

## 13.3 The differential matrix

The tests that make the architecture safe are all of the form "these two ways of running the same query must produce the same rows", and there are six axes. Every one of them is cheap to run because the corpus is shared.

| axis | what varies | what must match |
| --- | --- | --- |
| tier | 0 against 1 against 2 | rows, bit for bit, subject to the thread count caveat |
| strategy | each legal aggregation and join strategy forced | rows |
| reduction | on against off | rows |
| encoded execution | on against off | rows |
| pass | each pass disabled in turn | rows |
| threads | 1 against N | rows, exactly, except where a float aggregate declares `PerThreadCount` |

Two of those already exist in embryo. `SET disabled_optimizers` takes DuckDB's 44 names and `crates/rudb-opt/src/pass.rs` implements it, which is the pass axis. `crates/rudb/tests/seams.rs` and `reproducible.rs` are the beginnings of the strategy and thread axes.

Four do not exist and cannot, because tiers, strategies, reduction and encoded execution are not named things yet. That is the concrete payoff of naming them: **every decision that becomes a printed field also becomes an axis of a differential test**, and a decision that cannot be forced by setting is a decision nobody can test the other branch of.

The rule that follows: **a new choice ships with a setting that forces each of its branches.** Not a debug setting, a documented one, because the corpus runs it on every commit.

## 13.4 Plan stability

A corpus of queries with their plans checked in, at all three plan levels, regenerated by a command and diffed on every commit.

The point is not that plans should never change. It is that **a plan change should be a reviewed diff rather than a discovery.** Today a change to `estimate.rs`'s constants would change plans across the whole benchmark and nothing would say so until a number moved.

Three rules make it workable.

**The corpus runs against a warm statistics service.** Document 04 section 4.4: the first execution on a cold database may get a different plan from the second, because the fact service returns `Unknown` rather than blocking on a load. That is correct behaviour and it would make a stability corpus flap, so the harness warms first and the warming is part of the recorded setup.

**`Unknown` facts print.** A stability diff caused by a cold load must be attributable on sight rather than mysterious.

**A plan diff in a commit needs a sentence.** Not a process ceremony, an actual requirement: the commit that changes a hundred plans says which decision changed and why the new plans are better. A plan diff nobody explained is the failure mode this corpus exists to catch.

## 13.5 The bisector

Given a query that is wrong or slow, the question is always which decision did it, and with six artifacts the search space is large enough to need a tool rather than a habit.

The mechanism is already half there. Every pass has a name and can be disabled. Every seam implementation has a name and can be selected. What document 07 and document 08 add is that every strategy and every tier gets the same treatment.

So the bisector is a search over a set of named switches: disable passes one at a time, force each strategy, drop to tier 0, turn reduction off, turn encoded execution off. It reports the smallest set of switches that changes the symptom, and for a wrong answer that set is usually one switch and the bug is in that thing.

This is worth building as a command rather than leaving as a technique, because the value of a named switch is proportional to how easy it is to search over them, and thirty switches searched by hand is an afternoon.

## 13.6 The churn metric

Document 01 measured commits per crate over the last four hundred and found 352 of them in `rudb-exec`. That measurement is the reason this folder exists, so it should not be a thing somebody did once.

Define it exactly, because a metric with a vague definition gets argued with instead of acted on:

```
git log --since=<window> --name-only --pretty=format: | sort | uniq -c | sort -rn
```

Published weekly, per file, alongside the benchmark numbers.

**What it is for.** It is a design regression detector. If `group.rs` is still taking a third of the commits six weeks after the strategy selection moved into the physical plan, the move did not take and something is still routing decisions into the operator. If the churn moves to `rudb-phys` and `rudb-opt`, the architecture is working as intended, because those are the files where a decision is supposed to be edited.

**What it is not for.** It is not a productivity measure and it is not a per-person anything. A file that legitimately needs work will show up in it, and the response to the metric is a question rather than a rule.

The pairing that makes it useful is churn against line count. A file that takes many commits and stays the same size is being maintained. A file that takes many commits and grows every week is accumulating cases, which is the thing that happened here.

## 13.7 Benchmarks are tests

`tamnd/rudb-bench` is the goal and `../02-the-goal.md` sets the floor: no query slower than DuckDB, ever, and ten times faster in aggregate.

Three things make a benchmark a test rather than a score.

**Per query, not aggregate.** A geometric mean hides a query that got four times slower behind two that got eight times faster. The floor is per query and the gate is per query.

**Regression gated on the commit.** A commit that makes a benchmark query slower by more than noise fails, and the escape is an explanation in the commit, not a flag.

**Run with the differential axes.** The benchmark corpus is also the plan stability corpus and the strategy differential corpus. One set of queries, several harnesses over it, which is what keeps the marginal cost of an axis near zero.

`crates/rudb-cli/tests/clickbench.rs` and `crates/rudb/tests/clickbench.rs` exist, so the wiring is there.

## 13.8 What is honestly not tested today

Worth writing down, because the list is the work.

There is no physical plan corpus, because there is no physical plan. There is no strategy forcing, so `group.rs`'s nine strategies are each exercised only by whichever queries happen to hit them, and nobody knows the coverage. There is no program and therefore no interpreter against compiler differential, which is the test that will matter most once tier 2 lands. There is no plan stability corpus at any level. And the pass axis exists but is not run across the benchmark corpus on every commit.

Five gaps, and four of them close as a side effect of naming things that are currently anonymous. That is the argument in document 03 section 3.7 cashed out: the printers and parsers are not overhead, they are the test harness.

## What we should take from this document

Five EXPLAIN forms, one per artifact, because a wrong answer, a bad plan and a slow loop are three different bugs and one blob of text conflates them.

Every decision that becomes a printed field becomes an axis of a differential test, and the rule that follows is that a new choice ships with a setting that forces each of its branches.

A plan stability corpus at three levels, run warm, where a plan diff in a commit needs a sentence explaining it.

The churn metric is published weekly per file, paired with line count, and it is the detector that says whether this architecture is working.
