# Code generation: four tiers

The compiled-versus-vectorized argument has been running since 2018 and the honest answer from the literature is that neither wins outright. Kersten's "Everything You Always Wanted to Know About Compiled and Vectorized Queries" measured both carefully and found the difference small compared to the differences caused by data layout and memory access, with compilation winning on computation-heavy queries and vectorization winning on memory-bound ones. Umbra's answer was tiers. Photon's answer was to stay vectorized and get adaptive. Both work.

Our answer is tiers, for a specific reason that is not about which is faster: the interpreted tier is the correctness reference, and having a slow, simple, always-available implementation that every faster tier is differentially tested against is worth more to this project than the last 15 percent of any single approach.

## 8.1 The tiers

| Tier | What it is | When | Compile cost |
|---|---|---|---|
| 0 | interpreted vectorized | always, first morsels | none |
| 1 | fused vectorized kernels | expression trees matching known shapes | none, precompiled |
| 2 | Cranelift JIT | pipelines past a tuple threshold | milliseconds |
| 3 | single-pass emitter | only if tier 2 latency is measured to hurt | microseconds |

**Tier 0 is never removed and never optional.** It is the reference implementation. Every other tier is validated against it by running the same query both ways and comparing bit-for-bit, which is document 16.3.

**Tier 3 is explicitly speculative.** It is in this document so that the tier interface is designed to admit it, and it is scheduled past M8 with an explicit condition: build it only if tier 2's measured compile latency is a material fraction of total time on a workload we care about. TPDE demonstrates 10 to 20x faster compilation than LLVM `-O0` at 10 to 30 percent worse code, and Umbra's Flying Start emitter is the production instance of the idea, so the shape is known. Building it speculatively would be a large amount of x86 and ARM encoding work for a benefit we have not shown we need.

## 8.2 Tier 0, the interpreter

A tree of expression nodes, each evaluating its children into intermediate vectors and then applying a kernel. This is what DuckDB does and it is fine.

Its costs are real and worth naming, because they are what the higher tiers exist to remove. Every intermediate result is materialized into a vector, so a three-node expression writes and reads two temporaries of 1024 values each. Every node dispatches through a function pointer. Every node re-checks the physical form of its inputs.

For a scan-heavy query where the expression is `WHERE x > 5`, none of that matters and tier 0 is within noise of anything else. For a query whose expression is fifteen nodes deep it matters a great deal, and that is the shape tiers 1 and 2 target.

## 8.3 Tier 1, fusion

An expression tree is matched against a set of precompiled fused kernels. `a + b * c` becomes one kernel that reads three inputs and writes one output with no intermediates. Comparison chains, arithmetic chains, and the common conjunctions of comparisons are all covered.

**This is where most of the available win is, at almost none of the cost.** The intermediate materialization is the dominant overhead in tier 0 and fusion removes it without a compiler, without a compile pause, without a new failure mode, and without any code that is hard to debug. Fusion is generated by the same kernel generator as document 7.3, from the same table.

The limit is that only shapes present in the table get fused, so a novel expression falls back to tier 0 per node. The table is grown by measurement: profile real workloads, find the common shapes, add them.

## 8.4 Tier 2, Cranelift

**Why Cranelift and not LLVM.** Compile time. LLVM at `-O0` is already too slow to put in a query's critical path for anything but a long query, and at `-O2` it is far too slow. The CGO 2024 study of Cranelift as a query compilation backend is the direct evidence: compile times roughly an order of magnitude below LLVM with code quality close enough that the end-to-end result is better for typical query durations. Cranelift is also a Rust library with a stable API and no C++ toolchain dependency, which for a Rust project that wants to ship one binary is not a small thing.

**Why not build our own IR to machine code.** Because that is tier 3 and it is a year of work. Cranelift gets us the tier-2 benefit now.

**What gets compiled.** A pipeline's expression evaluation and its tuple-at-a-time inner loop, fused across operator boundaries within the pipeline. The generated function takes a morsel and the pipeline state and processes it. Operator boundaries within a pipeline disappear entirely, which is the classic compilation win.

**What does not get compiled.** Anything involving the buffer manager, the catalog, memory allocation, spilling, string allocation, or an aggregate function's state management. Those are calls into precompiled Rust. The generated code is arithmetic, comparison, hashing, control flow and hash table probes, and everything else is a call. This keeps the generated code small, keeps the compile fast, and keeps the amount of logic that exists in two implementations small.

**Compilation is asynchronous.** The pipeline starts on tier 0 or 1, a compile job goes to a background thread, and when it finishes the pipeline switches at the next morsel boundary. A query that finishes before the compile does never pays for it. This is Umbra's model and it is the right one, and it is why the tuple threshold that triggers compilation can be relatively low.

**The compiled and interpreted paths must agree exactly**, including on overflow, on null propagation, on string comparison and on floating point. Floating point is the one that will actually bite: the interpreter's evaluation order and the compiler's must match, which means no reassociation in the generated code and no use of fused multiply-add unless the interpreter uses it too. This is stated as a hard rule because a discrepancy here produces a query whose answer changes when it gets faster, which is the worst class of bug this project could ship.

**Caching.** Compiled code is keyed by the pipeline's structure with constants abstracted out, so a prepared statement executed repeatedly compiles once, and two structurally identical queries share. The cache is bounded and evicted by an LRU on a memory budget.

**Debugging support is not optional.** Generated code gets registered with the perf JIT interface on Linux, so a profile of a running query attributes time to the query rather than to an unnamed address. Cranelift's own IR can be dumped by a session setting. Without both of these, a performance problem in generated code is undiagnosable and the tier becomes a black box nobody can improve.

## 8.5 Expression IR

One IR shared by all tiers. Tier 0 interprets it, tier 1 pattern-matches it, tier 2 lowers it to Cranelift IR, tier 3 would lower it directly.

**It is typed, it is in static single assignment form, and it has an explicit null model.** Nulls are not a side channel: every operation states whether it propagates nulls, and the IR carries the validity computation explicitly rather than leaving it to each kernel's convention. This is more verbose and it is the only way to get three backends to agree.

**It has a textual form that round-trips.** Parse, print, parse again, compare. This is settled in document 00 and it applies at every layer, and here specifically it is what makes an IR-level fuzzer possible: generate an IR program, run it on three tiers, compare.

**Constant folding, common subexpression elimination and null-propagation simplification happen on the IR before any tier sees it**, so all three tiers benefit and none of them reimplements it.

## 8.6 Where the tier is chosen

Per pipeline, at runtime, on observed tuple counts. Not per query and not from an estimate.

The rule: start at tier 1 if the expressions match fused shapes, tier 0 otherwise. After N morsels, if the pipeline has processed more than a threshold of tuples and its expression complexity is above a threshold, queue a tier-2 compile. Switch when it lands.

**Both thresholds are measured and stored as constants with a comment saying which benchmark produced them**, not guessed. A threshold with no provenance becomes folklore within a year.

## 8.7 What the tiers do not solve

Compilation makes computation faster. Document 03's table says most ClickBench time is not computation, it is scanning and hashing and comparing strings, and no amount of code generation makes a memory access faster. Bespoke OLAP's ablation measured code specialization alone at 1.26x against storage specialization at 12.35x, and it is worth restating here so that this document's four tiers are read at their real weight: this is worth around 1.2 to 1.5x on the workloads we care about, it is a real 1.2 to 1.5x, and it is not where the project's claim comes from.

The one place it might matter more is query 28's `REGEXP_REPLACE` over 100 million strings, which is 24.7 percent of DuckDB's total and is genuinely compute-bound. That is not solved by a JIT for arithmetic; it is solved by a better regex engine with a compiled DFA and literal prefiltering, and by not running the regex on rows a prefilter has already excluded. Document 10.5 covers the regex implementation and it is scheduled in M5 as its own piece of work, because on this benchmark it is the single largest line item.
