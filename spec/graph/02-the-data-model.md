# 2. The data model

There is no new data model. There is a relational database with tables, rows and columns, and this document defines four things on top of it: what a row id is, how a declared key maps to one, what a relationship is, and what a null means in each of those. Nothing here is visible in SQL except where section 2.5 says it is, and nothing here changes an answer.

## 2.1 The row id

A rudb native table is stripes of sixty four parts of a thousand rows, appended in order. A row therefore already has an ordinal: its position in append order, zero based, over the whole table. That ordinal is the row id, written `rid`, and it is a `u64` in every interface and narrower than that in every stored form.

Three properties are required of it and each one costs something.

**Stable under append.** Appending a part cannot renumber an existing row, which append order gives for free.

**Cheap to resolve to a physical position.** A `rid` becomes a `(part, offset)` pair through the prefix sum of the per-part row counts, which the reader already holds in `Table::stripes`. Parts are a thousand rows except the last one of a load, so the common case is a shift and a mask and the general case is a binary search over a per-stripe prefix sum with sixty four entries. Document 04 section 4.2 specifies that the prefix sum is materialized once at open rather than walked per lookup, because a join gathers millions of times and an open happens once.

**Invalidated rather than corrupted by a rewrite.** A checkpoint, a compaction or a delete-and-vacuum renumbers rows. Everything in document 03 is therefore stamped with the generation of the table it describes, and a section whose generation does not match the directory's is ignored and rebuilt. This is the cheapest correct answer and it is only cheap because of the invariant in document 03 section 3.1: an ignored section changes no answer.

Deletes before a vacuum do not renumber. A deleted row keeps its `rid` and is excluded by the delete mask the scan already applies, which means a link may point at a deleted row and the gather that follows it produces a row the mask then removes. That is correct and it is one wasted gather, and section 5.9 of document 05 says when it is worth pre-applying the mask to the link instead.

## 2.2 The key map

A link is built from an equality between a child column and a parent column. To build it, the parent column's values have to be turned into `rid`s. That map is the key map and it has three physical forms, chosen by measurement at build time and recorded in the section header.

**Identity.** The parent key is an integer, the values are exactly `base .. base + n`, and every row is distinct and in ascending order. Then `rid = key - base` and nothing is stored but `base` and `n`. TPC-H hits this on `region`, `nation`, `supplier`, `customer`, `part` and `orders` when generated by `dbgen` at a single scale factor without a `-S` split, which is to say on almost everything, and that is not a coincidence, synthetic and real keys alike are usually a sequence.

**Dense offset.** The values are distinct integers in a range whose density is above a threshold, default one in eight. Then the map is a bitmap over the range plus a rank structure, and `rid = rank(key - base)`. Space is `range / 8` bytes plus about twelve percent for the rank index. The threshold exists because below it the bitmap is larger than the sorted form.

**Sorted.** The general case. Store the key values in sorted order in their own page, plus a permutation from sorted position to `rid`, and resolve by branchless binary search or, for numeric keys with a near-uniform distribution, by interpolation with a bounded linear probe. This is what strings get, and for strings it composes with the global dictionary from `../storage-v3/09-global-string-codes.md`: when the parent key column is dictionary encoded with a file-wide stable dictionary, the key map is a map from code to `rid` and the search never touches a byte of text.

A fourth form, a minimal perfect hash, is not specified. It is faster than the sorted form on lookup and much slower to build, and there is no measurement yet that says the lookup is where the time goes. Document 11 keeps it open.

The key map is built only for a column that is the parent side of some declared or inferred relationship. It is not an index on every column and it is not a substitute for one.

## 2.3 What a relationship is

A relationship is a named triple: a child table with a child column list, a parent table with a parent column list, and a cardinality. Every relationship in this design is many-to-one from the child to the parent, because that is the direction a foreign key points and because section 1.2 of document 01 is right that single-cardinality edges belong in a column. A many-to-many relationship in a schema is two many-to-one relationships through the table that represents it, which is exactly what `partsupp` is in TPC-H and what a link table is in every schema that has one.

Multi-column keys are supported and are resolved by the same key map over a composite. The composite is folded into one value the way `crates/rudb-exec/src/table.rs` already folds a group key, column at a time before the row loop, so a two column key costs two folds and not a row allocation. TPC-H needs this exactly once, on `partsupp(ps_partkey, ps_suppkey)`, which is also the only place in the schema with a composite primary key.

The cardinality recorded is one of three, and it is verified at build time rather than trusted:

- **Exactly one.** Every child row matches exactly one parent row. This is the strongest and it licenses the most: a join on this relationship neither adds nor removes rows, so the planner can push an aggregate through it and a `LEFT JOIN` on it is an inner join.
- **At most one.** Every child row matches zero or one parent rows, meaning the child column is nullable or has values the parent does not contain. An inner join on it removes rows; a left join does not.
- **Unverified.** The parent side is not unique. No link is built. This is not an error, it is a relationship that has to be executed as a join, and the planner is told so.

The verification is one pass at build time: the key map construction already discovers whether the parent side is distinct, and the forward link construction already discovers whether every child value resolved. Recording what was actually observed rather than what was declared is what keeps a wrong `FOREIGN KEY` declaration from producing a wrong answer, and a declaration that fails verification is reported through `EXPLAIN` and the metrics rather than silently.

## 2.4 Null

A null child key matches no parent row in an equi-join, and that is the rule the whole layer follows. It is not the `IS NOT DISTINCT FROM` rule that `crates/rudb-exec/src/key.rs` implements for grouping, and the fact that both rules exist in one engine on one type is, as `../engine/08-join.md` section 8.3 says, the thing most likely to be got wrong.

Concretely: the forward link reserves one value, the maximum representable in its width, to mean *no parent*. That covers both a null child key and a child key with no matching parent, and the two are distinguished where it matters, an anti join and a `NOT IN` need to know, by consulting the child column's own validity, which the scan has anyway. The backward adjacency simply omits those rows, so a parent's adjacency list contains only rows that really point at it.

Empty adjacency lists are not stored. Document 01 section 1.2 takes Jacobson's bit vector index from PVLDB 14 for this: a parent with no children contributes no entry and costs a bit. On TPC-H at SF100 this matters for `part` against `lineitem` hardly at all, because almost every part is ordered, and it matters a great deal on any real schema where most parents have no children, which is most real schemas.

## 2.5 How a relationship gets declared

Three paths, in order of how much the user has to do.

**From SQL, using syntax rudb has to support anyway.** DuckDB accepts `PRIMARY KEY`, `UNIQUE` and `FOREIGN KEY ... REFERENCES` in `CREATE TABLE`, and so does rudb. The catalog holds them (`crates/rudb-catalog/src/keys.rs`) and the native file keeps them across a reopen (#1784). Every foreign key is a declared relationship and no new syntax is invented: `rudb_exec::declared` puts one relationship per foreign key after the ones `graph_links` names, the checkpoint builds links for all of them, and `rudb_links()` lists them. This is the only path that is on by default, in the sense that a schema written with its keys needs nothing else to get its links built. Whether a plan reads them is still `graph_sections`, which starts off until the measurement in document 09 says otherwise.

**From a session setting, for data that arrives without constraints.** A Parquet file has no foreign keys and ClickBench and TPC-H both arrive as Parquet. A setting, `graph_links`, takes a list of relationships in the same `child(col) -> parent(col)` form the catalog stores, applied to views and tables alike. It is a setting and not a statement because a statement would be syntax DuckDB does not have, and `SET` of an unknown name is a smaller compatibility surface than a verb DuckDB will reject.

**From what the queries did, for the case where nobody declares anything.** The engine already sees every equi-join it executes. Recording the pairs, and the observed uniqueness of each side, gives a candidate relationship list; building a link for a pair that has appeared in `k` queries and whose parent side was observed unique is a background decision of the same kind as the recompression in `../06-compression.md`. This path is off by default, is gated behind a setting, and is the last of the three to be built, because an index built by inference is an index whose absence has to be indistinguishable from its presence and that is exactly what document 03 section 3.1 guarantees.

## 2.6 What the user sees

`EXPLAIN` shows which relationships a plan used and which it could have used but did not, with the reason. A system table, `rudb_links()`, lists the relationships of the attached databases with their cardinality, their verification result, their physical forms and their byte sizes; it is a table function in the `rudb_` namespace so that it cannot collide with anything DuckDB defines, per `../12-duckdb-compat.md`. Metrics count link builds, link hits, link misses and fallbacks.

Nothing else. There is no `MATCH`, there are no node labels, and there is no graph catalog. GRainDB shipped a graph modelling language beside its predefined joins and was careful to say the two were independent; rudb takes the half that is a query processing optimization and leaves the half that is a modelling language, because the modelling language is where the compatibility axis would break.
